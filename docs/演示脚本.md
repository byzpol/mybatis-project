## 二、逐步脚本

### 步骤 1 · 开场与登录（0:00~0:40）

- **操作**：打开 `http://localhost:8080/cms-mis/` → 用 **`author` / `123456`** 登录
- **讲什么**：
  - 项目定位：**不是"文章发布网站"，是带审批流转的内容运营后台**；4 个业务域，我负责"文章内容与多级审核发布"这条主链 + 公共基础设施（统一返回体/错误码/异常/日志切面/权限切面/分页/审计填充）
  - 技术栈一句话：SSM（Spring 5.3.31 + SpringMVC + MyBatis-Plus 3.5.5）+ Druid + MySQL 9.5 + Vue3/Vite，Tomcat 9
- **预期看到**：登录成功进入后台首页；**左侧菜单只有"我的文章/投稿相关"，没有"审核中心""用户管理"**（这一条本身就是权限管控的证据，后面会回收）

### 步骤 2 · 场景①文章发布：写稿 + 提交（0:40~2:00）

- **操作**：
  1. 进入"文章管理" → 点"新建文章"
  2. 填标题（如「演示稿：CMS 答辩现场」）、选分类、勾 2 个标签、写正文
  3. 点"保存草稿" → 观察状态标签
  4. 点"提交初审" → 观察状态标签变化
- **讲什么**：
  - **状态机不是散落的 `if-else`**：10 个状态、14 条迁移全部集中在一个 `ArticleStateMachine` 类里，对外只有 `transfer(status, action)` 一个入口；Service 层不许自己写 `if (status == 0)` 去判断能不能提交
  - 好处：**改流程只改一处**；非法流转统一抛 `11002`；每个迁移带所需角色与描述（`SUBMIT.description` = "提交初审"，界面按钮文案直接取它）
  - 提交后进入 `PENDING_EDITOR(1)`
- **预期看到**：状态标签 `草稿` → `待编辑初审`；列表页该条目状态列同步变化

### 步骤 3 · 场景②分类（2:00~2:50）

> ⚠️ **如实说明**：分类管理的**增删改与审批接口由成员B交付**，本次演示的是"分类体系已被文章真实引用并可用于筛选"这条链路。

- **操作**：
  1. 在文章编辑页点开"分类"下拉 → 数一下有几个分类
  2. 回到列表页 → 用"分类"筛选项选"技术资讯" → 观察结果条数
- **讲什么**：
  - 库里已有 **9 个分类**、**10 个标签**、**16 条文章-标签关系**（`cms_category` / `cms_tag` / `cms_article_tag`）
  - 分类选完写到文章的 `category_id`，**列表接口用"主表分页 + 批量填充分类名"**拿到 `categoryName`（不是每行一次查询）
  - 分类的表结构、权限码（`category:view`）都已就绪，业务接口由成员B按同一套"入户线"补
- **预期看到**：下拉 9 项；筛选后列表只剩该分类的文章

### 步骤 4 · 场景③审核：编辑初审驳回（2:50~3:50）

- **操作**：
  1. 右上角登出 → 用 **`editor` / `123456`** 登录
  2. 进"审核中心" → 打开步骤 2 提交的那篇
  3. **故意不填意见就点"驳回"** → 看报错
  4. 填上"标题需更具体" → 再点"驳回"
- **讲什么**：
  - **驳回必须填意见**，否则 `11014`；这是业务规则不是前端校验（前端只是提前提示，后端才是底线）
  - 每次审核（通过/驳回）都写一条 **审核流水** 到 `cms_article_audit_log`，谁、什么时候、什么动作、什么意见都留痕
  - **`editor` 看不到主编才有的"发布/下架/归档"按钮** —— 按钮由权限码下发
- **预期看到**：第一次驳回 → 错误提示（不填意见不给过）；第二次成功；状态变 `已驳回`；详情页出现审核时间线

### 步骤 5 · 场景③审核：改稿重提 + 主编终审（3:50~4:40）

- **操作**：
  1. 登出 → `author` 登录 → 打开那篇"已驳回"的稿 → 改标题 → 保存 → **再次提交初审**
  2. 登出 → `editor` 登录 → 初审**通过**
  3. 登出 → `chief` 登录 → 终审**通过**
- **讲什么**：
  - **驳回后能重新编辑再提交**，这是状态机里明确的一条回边（`REJECTED → DRAFT/PENDING_EDITOR`）
  - 两级审核：编辑初审（`PENDING_EDITOR`）→ 主编终审（`PENDING_CHIEF`）→ `APPROVED(3)`
  - **防自审 `11004`**：同一个人不能既写又审 —— 这个后面步骤 6 会现场演示
- **预期看到**：状态依次 `已驳回 → 待编辑初审 → 待主编终审 → 已通过`；详情页审核时间线累计三条

### 步骤 6 · ★ 场景④权限管控：故意演示越权被拦截（4:40~6:00）

> 这是**权限管控的加分点**，也是全场最值得演的一段。三个层次一次演完。

- **准备**：浏览器开发者工具 → Application → Cookies，拿到 `author` 的 `JSESSIONID`（或直接用 ApiFox/curl 的会话）
- **操作 A · 垂直越权（按钮级）**：
  1. `author` 登录状态下看左侧菜单 —— **没有"审核中心"入口**；管理类菜单（用户/角色/日志/报表）也都没有
  2. 指出：菜单与按钮都是按**权限码**下发的，不是写死在前端
- **操作 B · 垂直越权（接口级）**：用 `author` 的会话直接调审核接口
  ```bash
  curl -i --noproxy '*' -X POST \
    -H "Content-Type: application/json" \
    -b "JSESSIONID=<author 的会话>" \
    -d '{"auditAction":1,"auditOpinion":"越权试试"}' \
    http://localhost:8080/cms-mis/api/v1/articles/3/audit
  ```
  → **预期 `HTTP 403`**（`PermissionAspect` 拦截，`author` 没有 `article:audit`）
  > 用 **id=3**（种子数据里 `author` 自己那篇"待编辑初审"的稿）—— 这样能顺带说明：
  > **权限切面在 Service 之前**，所以越权角色拿到的是 403，而不是"状态不对"的 11002
- **操作 C · 水平越权（数据级）**：`author` 去撤回 **`author2`（赵投稿）的已归档文章 `id=20`**
  ```bash
  curl -i --noproxy '*' -X POST \
    -b "JSESSIONID=<author 的会话>" \
    http://localhost:8080/cms-mis/api/v1/articles/20/withdraw
  ```
  → **预期 `HTTP 200` + `code 11003`「无权操作该文章」**（Service 层归属校验）
  > ⚠️ 这条是**刻意的既定行为**：`checkOwnership` **没有超管短路**、且排在"归档只读"双保险之前，
  > 所以对别人的已归档文章调 withdraw/rollback，报的是 **11003（不是你的）** 而不是 11011（已归档只读）。
  > 演示时如果老师追问"为什么不是 11011"，这就是答案。
- **操作 D · 自审拦截（可选，时间够再做）**：`11004`
  > 需要先造条件，完整 4 步：`chief` 建稿 → 提交 → `editor` 初审通过 → `chief` 自己终审 → **11004**
  > 若时间紧就**口头说明**，并指向证据：`ArticleServiceImpl#checkNotSelfAudit`、单测里的自审用例
- **讲什么**（这一段是重点）：
  - **三级失败形态完全不同，别混**：
    | 现象 | 谁拦的 | 含义 |
    |---|---|---|
    | **HTTP 401** | `LoginInterceptor` | 没登录 |
    | **HTTP 403** | `PermissionAspect`（AOP） | 登录了，但没有这个权限码 |
    | **HTTP 200 + 11003** | Service `checkOwnership` | 有权限，但这条数据不是你的 |
    | **HTTP 200 + 11004** | Service 防自审 | 不能审自己提交的 |
  - 权限码**以库表 `sys_permission` 的 20 条为准**（不是文档里写的）：文章域 9 个 + 分类 + 角色 + 报表等；4 个角色分别绑 7 / 9 / 12 / 20 个
  - **为什么用 AOP 而不是每个方法里写 if**：权限是横切关注点，写进注解（`@RequirePermission("article:audit")`）后，**加权限不改业务代码**，也漏不掉
- **预期看到**：403 的 JSON、11003 的 JSON、11004 的 JSON 各一次

### 步骤 7 · 场景⑤数据检索（6:00~7:00）

- **操作**（`chief` 账号）：
  1. 列表页输入关键词（如"国庆"）+ 选状态 + 选时间区间 → 观察结果
  2. 点表头排序
  3. 把分页 `size` 改成 `9999` 再请求（ApiFox/改 URL）→ 观察返回条数
  4. 把排序字段改成注入串（如 `id;drop table`）→ 观察报错
- **讲什么**：
  - **分页方案 B**：主表分页 + 批量填充关联名称。为什么不用 JOIN 分页？**JOIN 会把 `count(*)` 放大**（一对多时一行变多行），页码就不准了
  - `size` 上限 **100**，超出**截断**不报错
  - **排序字段走白名单**，不在白名单里的直接 **400**（防 SQL 注入）
  - 热点查询建了复合索引，`EXPLAIN` 对比在 `docs/SQL优化记录.md`
- **预期看到**：筛选/排序生效；`size=9999` 只返回 100 条；注入串返回 400

### 步骤 8 · 场景⑥用户管理（7:00~8:00）

> ⚠️ **如实说明**：用户/角色/权限的**管理接口由成员C交付**。本次展示的是"权限体系已就绪并被 4 个账号真实驱动"。

- **操作**：用 `author` → `editor` → `chief` → `admin` 依次登录，各看一眼左侧菜单和可用按钮
- **讲什么**：
  - 4 个角色权限数 **AUTHOR 7 / EDITOR 9 / CHIEF 12 / ADMIN 20**；`article:publish` 只有主编和管理员有
  - 权限链路：登录 → Session → `LoginInterceptor` 拦登录 → `PermissionAspect` 校验权限码 → Service 校验数据归属
  - 表已就绪：`sys_user` / `sys_role` / `sys_permission` / `sys_user_role` / `sys_role_permission`（**48 条角色-权限绑定**）
  - 用户管理的 CRUD 与授权审批由成员C按同一套"主干 + 入户线"补，**主干不用改一行**
- **预期看到**：菜单项数量从少到多：作者 < 编辑 < 主编 < 管理员

### 步骤 9 · 场景⑦日志记录（8:00~8:40）

> ⚠️ **如实说明**：日志的**查询接口/页面由成员D交付**。本次直接查库，证明"日志已被真实自动记录"。

- **操作**：打开数据库客户端，执行
  ```sql
  SELECT id, module, oper_type, oper_desc, oper_name, cost_time, status, oper_time
    FROM sys_oper_log ORDER BY id DESC LIMIT 10;
  SELECT username, login_status, message, login_time
    FROM sys_login_log ORDER BY id DESC LIMIT 10;
  ```
- **讲什么**：
  - 操作日志**不是业务代码里手写的**，是 `@OperLog` 注解 + `WebLogAspect` 切面**自动落库**；刚才演示的每一步都在里面
  - **两套状态口径不同**：`sys_login_log.login_status` = 1 成功 / 2 失败；`sys_oper_log.status` = 1 成功 / 0 失败
  - **登录成功与失败都记**（撞到口令错的记录正好是证据）
  - 敏感参数**不落库**：登录接口标了 `saveParams=false`，口令不会进日志
- **预期看到**：刚才的操作一条条在表里，时间、操作人、耗时、结果齐全

### 步骤 10 · 发布与排期（进阶拓展）（8:40~9:30）

- **操作**（`chief` 账号）：
  1. 对步骤 5 已通过的文章点"立即发布" → 状态变"已发布"
  2. 另建一篇走完整链路 → 点"排期发布"，时间设为 **当前时间 + 1 分钟**
  3. 等 1 分钟（期间讲状态机与错误码）
- **讲什么**：
  - 排期把状态置为 `SCHEDULED(6)`，**定时任务每分钟扫一次到期文章**，无人干预自动发布
  - **排期到点发布时没有登录上下文** —— 审计字段怎么办？填**哨兵值 `0`**（`SYSTEM_USER_ID`），这样"系统发的"和"人发的"在数据上能区分；实测 `publisher_id = 0`，`schedule_time` 发布后被清空
  - ⚠️ **下架不可逆**：`OFFLINE(8)` **只有归档一条出边**（指导书里写"下架后可重新发布"是错的，我们以状态机为准）；**撤回可逆**，撤回后能重新发布
- **预期看到**：1 分钟后文章**自动**变成"已发布"，没人点任何按钮

## 三、兜底方案（页面出问题时不冷场）

| 万一 | 兜底动作 |
|---|---|
| 前端页面白屏 / 静态资源 404 | 直接改用 ApiFox 演示接口，并说明"前端产物需先 build 再打包" |
| 登录不上 / 500 | 先跑 `health/ping` 判断应用是否活着；再看 `logs/cms.log` 最后一个 `ERROR` |
| 数据被上一次演示污染 | **当场重跑 `sql/init.sql`**（幂等，几秒完成），声称"回到演示基线" |
| 8080 起不来 | 查端口占用并 `taskkill`；再启动（别忘了 `JAVA_HOME` 和 `cd` 工程根） |
| 排期没触发 | 说明 cron 每分钟一次，最多等 60 秒；顺便讲这是**幂等扫描**不是队列回调 |
| 老师要看代码 | 打开 4 个文件即可：`common/ArticleStateMachine.java`、`aspect/PermissionAspect.java`、`base/AuditMetaObjectHandler.java`、`task/ArticlePublishScheduler.java` |

**备用 curl 命令**（存成一个 `.txt` 放桌面，随时粘贴）

```bash
B=http://localhost:8080/cms-mis/api/v1
# 存活
curl -s --noproxy '*' $B/health/ping
# 登录（存会话）
curl -s --noproxy '*' -c ck.txt -X POST -H "Content-Type: application/json" \
     -d '{"username":"author","password":"123456"}' $B/auth/login
# 当前用户
curl -s --noproxy '*' -b ck.txt $B/auth/me
# 列表
curl -s --noproxy '*' -b ck.txt "$B/articles?page=1&size=10"
```
