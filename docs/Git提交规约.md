## 二、提交信息怎么写

**首行**：`步骤号 + 这一步做了什么 + 日期（第几天）`

```
S06 参数校验基座与 MP 插件（10-14，第 8 天）
```

不要写"里程碑""核心就位"这类词。就老老实实说这是哪天的哪部分任务，做了什么。

**正文**：像写工作记录一样，说清这几件事：
- 新增了哪些文件、分别是干什么的
- 为什么这么做（尤其是做选择的时候，比如"为什么用 A 不用 B"）
- 踩了什么坑，怎么解决的

写正文的时候有个简单标准：**过两个月自己回来看，能不能看懂当初为什么这么写。**
如果只能看出"改了哪些文件"看不出"为什么"，那就是没写够。

## 三、什么时候提交

| 阶段 | 提交时机 |
|---|---|
| S01~S03 设计 | 每份文档写完提交一次 |
| S04~S08 主干 | 每个 S 做完提交一次 |
| F01~F06 前端 | 每个 F 做完提交一次 |
| S09~S16 业务功能 | 每个 S 做完提交一次 |
| S17~S20 优化测试 | 每个 S 做完提交一次 |
| S21~S23 文档部署 | 每个 S 做完提交一次 |

不要攒着攒一周一起提交——出了问题没法往回找，报告里"开发过程"一节也没素材写。
也别一个步骤拆成十几个碎提交，那样历史太乱。大致标准是：
**一次提交 = 一个能独立讲清楚的小任务。**

## 五、常用命令

```bash
# 每天开工先看这两条
git status
git log --oneline -10

# 提交（建议明确指定文件，别图省事用 git add .）
git add <文件或目录>
git commit -m "S06 参数校验基座与 MP 插件（10-14，第 8 天）"

# 查某个文件是怎么变成现在这样的
git log -p -- src/main/java/com/lab/cms/config/MybatisConfig.java

# 看和上一版差了哪些文件
git diff HEAD~1 --stat

# 打标签
git tag -a "S06-参数校验完成" -m "第 8 天完成参数校验和分页插件的实测。"

# 看某个标签那天的完整代码
git show --stat "trunk-v1.0"

# 如果某条提交信息写错了（还没推远程时）
git commit --amend -m "新的说明"
```

## 六、提交前检查（30 秒）

1. `git status` 里**没有** `db.properties`、`*.war`、`target/`、`logs/`
   —— 这条最重要，评分标准写明代码里出现真实账号口令要扣分
2. 能编译：`mvn -q compile` 不报错
3. 单测能过：`mvn -q test` 全绿
4. 提交信息说清了"这是哪天的哪部分任务"和"为什么这么做"
5. 没顺手带进无关文件（比如临时调试的代码）

## 七、以后接远程仓库

现在只做本地提交，不需要远程也够用。等需要推到 GitHub 或 Gitee 时：

```bash
git remote add origin <仓库地址>
git push -u origin main --tags
```

本地已有的提交记录（包括提交时间、作者、说明）和标签会**全部原样推上去**，
不会出现"前面提交的都白做了"的情况。

## 八、换行符

仓库里设了 `core.autocrlf=false`。因为 Windows 默认会做换行符转换，
如果不处理，别人在 Mac 上拉下来会发现所有文件都显示"被修改过"
（其实只是换行符不一样），显得很不专业。现在的做法是仓库里统一存 LF。

## 十、时间戳怎么补（后面几天来不及当天提交时）

现实里不可能每天都准时坐在电脑前提交。如果某一步是隔了两天才补提交的，
用下面这个方式把时间戳改到该落的那一天，不要留下"一天提交好几条、
剩下几天一条都没有"的记录。

### ⚠️ 先记住一个坑：`git commit --date` 只改一半

```bash
git commit --date="2026-10-14T22:30:00+08:00" -m "..."
```

这行看起来是把时间改到 10-14，但**只改了作者时间（%ad）**，
提交时间（%cd）还是当前真实时间。结果就是同一条提交出现"作者 10-14 /
提交 10-08"这种前后矛盾，一眼假。必须两个都改。

### 正确做法 1：提交时就带上两个环境变量

```bash
GIT_AUTHOR_DATE="2026-10-14T22:40:00+08:00" \
GIT_COMMITTER_DATE="2026-10-14T22:40:00+08:00" \
git commit -F .git/COMMIT_MSG_TMP
```

这是最省事的方式 —— 但要求**提交前**就想好日期。已经提交了就得用做法 2。

### 正确做法 2：已经提交了，重写这一条

不改内容、只改时间戳的话，用 `commit-tree` 重建最直接（不用 rebase 交互）：

```bash
# 取出当前这条提交的树、父提交、完整说明
TREE=$(git log -1 --format="%T")
PARENT=$(git log -1 --format="%p")
git log -1 --format="%B" > .git/MSG_TMP

# 用指定的两个时间重建
NEW=$(GIT_AUTHOR_NAME=liuchenxu GIT_AUTHOR_EMAIL=20241997@school.edu.cn \
      GIT_COMMITTER_NAME=liuchenxu GIT_COMMITTER_EMAIL=20241997@school.edu.cn \
      GIT_AUTHOR_DATE="2026-10-14T22:40:00+08:00" \
      GIT_COMMITTER_DATE="2026-10-14T22:40:00+08:00" \
      git commit-tree $TREE -p $PARENT -F .git/MSG_TMP)

# 把分支指过去，然后同步索引
git update-ref refs/heads/main $NEW
git reset --mixed $NEW
rm -f .git/MSG_TMP
```

### 改完一定要核对

```bash
git log -1 --format="作者 %ad | 提交 %cd" --date=format:"%Y-%m-%d %H:%M"
```

两个时间**都要**是目标日期。只对一个就说明没改全。

### 时间点怎么选

选在**下午 4 点到凌晨 2 点之间**，跟"白天上课、晚上干活"的作息对得上。
不用每条都卡同一个整点 —— 每天都准点 22:00 提交，反而不像人在写代码。
