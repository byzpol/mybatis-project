## 二、四个关键设计决策

### 2.1 DTO → 实体只搬「可编辑的 6 个字段」（防批量赋值）

`applyEditableFields` 只搬 `title / summary / coverUrl / content / categoryId / isTop / scheduleTime`。
`status / authorId / viewCount / publisherId / publishTime / version` 一律由 Service 决定，
**绝不从入参取**。

理由：如果直接把 DTO 全字段塞进实体，攻击者可以在"新建草稿"的 JSON 里多带一个
`"status": 3`（已批准）或 `"authorId": 4`（管理员），草稿建出来就是"自己给自己批准了"。
这是 Mass Assignment（批量赋值）漏洞。防法是**白名单搬运**，不是黑名单过滤。

**实测**：新建草稿后查库，`status` 恒为 `0`、`author_id` 恒等于操作人、
`view_count=0`、`version=0`（见证据文档 §2 的 `[S09] 保存草稿` 一行）。

### 2.2 状态推进一律走 `ArticleStateMachine.transfer`

全类搜索不到一处 `setStatus(数字常量)` 或 `if (status == 1)`。四个方法里唯一的
状态推进点是 `submitForAudit`：

```java
Integer fromStatus = article.getStatus();          // 先留旧值给日志用
ArticleStatus next = ArticleStateMachine.transfer(article.getStatus(), ArticleAction.SUBMIT);
```

**为什么用 `transfer` 而不是 `assertTransfer`**：`assertTransfer` 对任何非法情况
都抛同一个 `ARTICLE_STATUS_ILLEGAL(11002)`，而 `transfer` 会区分三种：
`ARTICLE_NOT_FOUND(11001)` / `ARTICLE_ARCHIVED_READONLY(11011)` / `ARTICLE_STATUS_ILLEGAL(11002)`。
前端需要不同的提示语（"文章不存在" / "已归档不可改" / "当前状态不允许提交"）。

⚠️ 日志取值时机有坑：`log.info` 里如果写 `article.getStatus()`，
在 `setStatus()` 之后拿到的已经是**目标状态**，日志就成了"1 → 1"。
所以先留 `fromStatus` 再用。

### 2.3 版本快照取号：`SELECT MAX + 1` + 唯一索引重试，不用行锁

`insertVersionSnapshot` 的流程：

1. `selectMaxVersionNo(articleId)` 取当前最大号（XML 里带 `AND deleted = 0`）；
2. 号 +1，插入快照；
3. 若抛唯一键冲突（`cms_article_version.uk_article_version`），重试，最多 3 次。

**为什么不用 `SELECT ... FOR UPDATE` 行锁**：
- 取号是"低概率、瞬时"的并发事件。项目里同一篇文章**只有作者本人能改**，
  真正并发写同一篇的概率极低；
- 行锁要占住事务直到提交，而这里的插入只是一次 `INSERT`，
  上锁的代价与收益不成比例；
- 唯一索引是**最终一致性保证**：即便取号撞了，冲突也一定被数据库拦下，
  不会出现两条同号快照。重试只是把这个保证变成"对用户透明"。

**取 3 次而不是 10 次**：连续 3 次都撞，说明不是偶发并发，
而是别的地方出了问题（比如有人绕过唯一索引造了脏数据），继续重试只会掩盖问题。

**实测**：单篇文章连续保存 + 修改两次，版本号序列恰好 `[1, 2, 3]`，
`COUNT(DISTINCT version_no) = COUNT(*) = 3`（见证据文档 §3.2）。

### 2.4 ⚠️ 修改草稿**不用** `updateById(entity)`，用 `update(carrier, wrapper)`

这是本步**最重要的一处**决策，因为它是**实测抓出来的静默失效**，详见 §三。

## 三、实测抓到的两个问题（都是本步新增的结论）

### 3.1 ⚠️ `updateById(entity)` 静默跳过 null 字段 → "清空摘要/正文"无效

**发现路径**：读 SQL 日志时发现 `UPDATE cms_article SET ...` 里
**没有 `summary` / `cover_url` / `content` 三列**（因为传进去的是 null），
SET 子句列数比预期少 3 个。

**逐步证伪**：
1. `curl` 建一篇带摘要 + 封面 + 正文的草稿；
2. `curl` PUT 把 `summary / coverUrl / content` 全传 null；
3. 接口返回 **200「草稿已保存」**；
4. 查库 → `summary=原始摘要, cover_url=/a.png, content=原始正文` —— **一个都没改**。

**根因**：MyBatis-Plus 默认字段策略是 `FieldStrategy.NOT_NULL`，
`updateById(entity)` 只会把**非 null** 的字段拼进 SET 子句。
所以在"整体替换（PUT）"语义下，用户想把摘要清空是**根本表达不出来**的。

**修复**：改用 `baseMapper.update(carrier, wrapper)`，
用 `LambdaUpdateWrapper` 显式列出要写的每一列：

```java
private LambdaUpdateWrapper<CmsArticle> updateEditableColumns(CmsArticle src) {
    return Wrappers.<CmsArticle>lambdaUpdate()
            .eq(CmsArticle::getId, src.getId())
            .set(CmsArticle::getTitle, src.getTitle())
            .set(CmsArticle::getSummary, src.getSummary())     // 显式 set，null 也写
            .set(CmsArticle::getCoverUrl, src.getCoverUrl())
            .set(CmsArticle::getContent, src.getContent())
            .set(CmsArticle::getCategoryId, src.getCategoryId())
            .set(CmsArticle::getIsTop, src.getIsTop())
            .set(CmsArticle::getScheduleTime, src.getScheduleTime());
}
```

**修复后实测 SQL**：

```sql
UPDATE cms_article SET version=?, update_by=?, update_time=?,
  title=?, summary=?, cover_url=?, content=?, category_id=?, is_top=?, schedule_time=?
WHERE deleted=0 AND (id = ? AND version = ?)
```

参数里 `null` 被**真正绑定**，复验三列都成了 `<NULL>`。

**为什么载体只带 `id` + `version`**：`update(entity, wrapper)` 会把
**entity 非 null 字段** 和 **wrapper 显式 set 的列** 拼进同一个 SET 子句。
若 entity 是查出来的完整文章、wrapper 又 set 了同样的列，
SQL 就变成 `SET title=?, ..., title=?` → MySQL 报 **1060「Column 'title' specified twice」**。
所以载体只给 `id`（定位）+ `version`（乐观锁插件要读它才能追加 `SET version=version+1`）。

**排除了的方案**：给字段挂 `@TableField(updateStrategy = FieldStrategy.IGNORED)`。
理由：它会让**全项目所有** `updateById` 无条件写 null，
将来 S13/S14 里如果出现"只带要改字段的局部实体"去 `updateById`，
就会把没带的标题、正文**整段抹掉** —— 用一个全局开关换一处便利，不划算。

**新增回归断言**：`testUpdateDraftCanClearNullableFields`（写值 → 全传 null →
**查库**断言三列为 NULL，不是断言内存实体）。

### 3.2 唯一键冲突抛出的**就是** `DuplicateKeyException`（纠正了我自己的错判）

写 `isDuplicateKey` 时的**先验判断**是："本项目手工装配 + MyBatis `@Mapper`，
没有走 Spring 的异常翻译，撞唯一键应该抛
`org.apache.ibatis.exceptions.PersistenceException` 包 `SQLIntegrityConstraintViolationException`"。

**实测（`VersionSnapshotDuplicateKeyTest` 打印异常全链）**：

```
org.springframework.dao.DuplicateKeyException :
  Cause: java.sql.SQLIntegrityConstraintViolationException:
  Duplicate entry '95-1' for key 'cms_article_version.uk_article_version'
```

**抛出的就是 `org.springframework.dao.DuplicateKeyException`** ——
mybatis-spring 2.1.2 在这套装配下**确实做了异常翻译**，我的判断是错的。

**好在代码本来就对**：`isDuplicateKey` 是按"沿 cause 链逐一识别三种形态"
（`DuplicateKeyException` / `SQLIntegrityConstraintViolationException` / `SQLException` 且 `errorCode=1062`）写的，
所以宽口径识别能兜住。但注释里那句错话必须改掉（已改 `ArticleServiceImpl` 与
`VersionSnapshotDuplicateKeyTest` 的类注释）。

**这条的价值**：整轮里"推理框架行为"是唯一出错的地方，
而"跑一次看它抛什么"纠正了它。如果当时按错判断写成"只 catch `PersistenceException`"，
重试逻辑就是一段**永不执行的死代码**，症状只会是"并发时偶发提交失败"，几乎无法复现。
