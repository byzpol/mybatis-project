## 二、六个关键设计决策

### 2.1 入参**不带** `auditStage`，环节由状态反推

手册 S10 要求 DTO 带 `auditStage`（1 初审 / 2 终审）并在 Service 里校验它与状态匹配。
**不采纳**，两个理由，第二个是决定性的：

1. **冗余入参必然打架**。"该谁审"由文章当前状态唯一决定（`PENDING_EDITOR` 就是初审）。
   让客户端再声明一遍，就等于允许它说"我认为现在是初审"，而这个声明可能与库里的状态不一致。
   这与契约 §4.1 底下明确否掉"拆成 `/audit/first` 与 `/audit/final` 两个 URL"
   （第 72 行："审核阶段由文章当前状态决定"）是同一个理由，只是把问题从 URL 搬到了请求体。
2. **⚠️ 前端已经按"不带 stage"实现了**：`frontend/src/api/modules/article.js` 的
   `auditArticle()` 注释里写着"⚠️ 不传 stage！审核阶段由文章当前状态决定"，
   F06 的 `ArticleAudit.vue` 也是照这个口径调的。
   **后端若改成必传 `auditStage`，已跑通的前端会立刻全部 400。**

所以 DTO 与契约 §5.2 一致：`{auditAction, auditOpinion}`。
（字段名用 `auditAction` 而不是表里的列名 `result`：入参表达"动作"，落库表达"结论"，
值域相同但语义角度不同，前端/契约/DTO 统一用 `auditAction`。）

### 2.2 初审与终审**合并成一个方法**

手册 S11 也要求"两段逻辑合并成一段，无法合并要说明为什么"。这里可以合并，且**必须**合并：
两个环节除了"从哪个状态出发、到哪个状态去"之外，其余每一步完全相同
（查文章 → 推环节 → 防自审 → 驳回校意见 → 状态机推进 → 写流水）。
唯一会变的那部分已经全部封装在 `ArticleStateMachine.transfer` 的静态表里，
方法本身不需要知道"初审能到哪、终审能到哪"。

**代价对比**：拆成两个方法意味着上面五步各复制一份，
于是"哪天给审核加一条规则（比如加敏感词校验）"必然漏改一处。
实测正反两面都覆盖了：同一方法在 `PENDING_EDITOR` 下写出 `audit_stage=1`、
在 `PENDING_CHIEF` 下写出 `=2`（证据文档 §3.2）。

### 2.3 权限校验分两层，各管各的

| 层 | 内容 | 放在哪 | 为什么不放另一处 |
|---|---|---|---|
| 功能权限 | `article:audit` | Controller 的 `@RequirePermission` + `PermissionAspect` | 同一份权限规则写两遍，改的时候必漏一处 |
| 业务级越权 | 作者不能审自己的稿 | Service 的 `checkNotSelfAudit` | 这不是"有没有 `article:audit`"的问题 —— 编辑和主编**都有**这个权限，拦住他们的是"这稿子是不是你自己写的" |

**实测**：投稿人（无 `article:audit`）经 HTTP 调审核 → **403**
（`{"code":403,"message":"没有该操作权限，需要：article:audit"}`）；JUnit 里作者调 Service → **11004**。
两层都验证到了。

### 2.4 ⚠️ 步骤顺序改为"先改状态、后写流水"（与手册不同，有意为之）

手册 S10 的顺序是"5. 插审核流水 → 6. 更新文章状态"。实现里**反过来**。
理由是一条**能否被验证**的差别，不是风格偏好：

- 手册自己也强调这条不变式：**"写流水和改状态必须在同一事务里，否则会出现状态改了但流水丢了"**。
- 按手册顺序（先流水后状态），要制造"流水写完、状态改失败"的场景，必须让**状态更新**失败 ——
  而 `updateById` 在没有并发干扰时不会失败，只能去 mock 框架内部。
  等于说这条不变式**测不了**。
- 反过来写之后，只要让**流水插入**失败即可，而它是**确定性、可构造**的：
  给一个超过 500 字的 `opinion`，MySQL 严格模式（本机 `sql_mode` 含 `STRICT_TRANS_TABLES`）
  会抛错误 1406。跑完断言"状态仍停在 `PENDING_EDITOR`、流水表 0 行"，
  才算真正证明了两个写操作在同一事务里。

顺带一个好处：乐观锁冲突（`updateById` 返回 0）是**最先**被发现的，此时还什么都没写，
不会留下一条随后要被回滚的流水。

### 2.5 ⚠️ **不**做"该阶段已审核过"的存在性检查

`CmsArticleAuditLog` 的类注释把"防重复审核"列为这张表的用途之一，
实现方式写的是"查 `(article_id, audit_stage)` 是否已有记录，有则拒绝"。**按字面实现会打断主链路**：

```
提交 → 初审驳回（写入 stage=1 的流水）→ 作者改稿 → 再次提交
     → 初审（此时 (article_id, 1) 已经有记录了 → 被误判为"重复审核"）
```

而"初审驳回 → 改稿 → 再初审"正是 S11 主链路自测清单里必须走通的一步。
实测证明它走得通：**同一环节累计 2 条流水，result 序列 `[2, 1]`**（证据文档 §3.4）。

真正拦住重复审核的是**状态机 + 乐观锁**，而且比查流水更彻底：
**"在同一个环节上审两次"在结构上根本不存在** —— 审核成功后状态必然改变，
第二次调用会被推导成**另一个环节**（见 §3.1）。
**已登记**：该实体注释的这句话与实际实现不符，应在 S18 重构时改正。

### 2.6 `articleVersion` 记"业务快照号"，不是乐观锁号

- `cms_article.version` = MP 乐观锁号，每次 UPDATE +1；
- `cms_article_version.version_no` = 业务快照号（创建草稿=1、改一次+1、提交再审+1）。

库表 `cms_article_audit_log.article_version` 的注释写明对应**后者**，
所以取 `versionMapper.selectMaxVersionNo(id)`。
**返回 null 时不兜底成 0** —— 0 是个看起来合法的版本号，会把"没有快照"伪装成"第 0 版"；null 才诚实。
实测：提交后快照号=2、乐观锁号=1，流水里记的是 **2**（证据文档 §3.3）。

此外，审核**不创建**版本快照（审核不改内容），实测"快照数 2 → 2"不变。

## 三、本步实测抓到的两个问题

### 3.1 ⚠️ "初审通过后再初审应被拒"是**错的** —— 它会被当成终审并成功

**发现路径**：第一条测试就是这么写的（期望 11002），跑出来**失败**：
`期望抛出 BusinessException(11002)，但调用成功了`。20 条里 19 过 1 挂。

**真实行为**：

```
第 1 次 audit → 状态 PENDING_EDITOR(1) → 推环节=编辑初审 → 通过 → 状态变 PENDING_CHIEF(2)
第 2 次 audit → 状态 PENDING_CHIEF(2)  → 推环节=主编终审 → 通过 → 状态变 APPROVED(3)
```

**这不是 bug，是"环节由状态反推"的必然结果**：审核成功后状态必然不再是原来那个，
所以"在同一个环节上审第二次"在结构上就表达不出来。
想让状态回到 `PENDING_EDITOR`，只能走"驳回 → 作者改稿 → 重新提交"，那是**新的一轮**审核。

**由此得出两条结论**：

1. **"防重复审核"靠状态机就够**（见 §2.5），不需要查流水表；
   真正并发的重复请求由乐观锁兜住（第二个 `version` 不匹配 → 11010）。
2. ⚠️ **同时暴露一个真实缺口**：只要账号有 `article:audit`，就能把一篇文章
   从初审一路审到 `APPROVED`。因为库里文章域**只有一个审核权限码**
   （`article:audit`，没有 first/final 之分），而环节又由状态推导 ——
   于是"初审归编辑、终审归主编"这条业务分工**在当前权限模型里表达不出来**。

   **实测双重确认**：JUnit（同一账号完成 `stage=[1,2]` → APPROVED）+
   真机 HTTP（editor 连续两次调 `/articles/201/audit` 均 200，查库 status=3=APPROVED）。
   已登记为**挂起待定**（见 §七），**本步不擅自修**：这既不是手册要求
   （手册只要求"作者不能审自己的稿"），也会改动权限模型（属成员C 主责范围）。

   这条测试**保留**下来（`testSecondAuditCallBecomesFinalAuditNotDuplicate`），
   把这个事实显式钉住，而不是假装不存在 —— 免得评审时才发现，或将来有人无意中改坏。

### 3.2 我第一版注释里的两句话是错的，已改正

- 接口注释里曾写"初审通过后状态已变成 `PENDING_CHIEF`，**再调初审会因状态不支持而 11002**" ——
  与 §3.1 的实测直接矛盾，已改为"同一环节重复在结构上不存在"并加了一句"以本条为准"。
- 会话中我一度以为 `expectBusinessCode` 的用法有误，核对后确认断言本身没问题，
  是**测试的预期**错了（把"合法的终审"当成了"非法的重复初审"）。

**教训**：这次不是"代码有 bug"，而是**我对系统的行为有一个想当然的模型**
（"同一环节审两次会被拒"）。这个模型错在忽略了"环节是从状态推出来的"这一设计前提。
**跑一次、看它实际做了什么**纠正了它。
