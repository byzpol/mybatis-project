# 数据库设计说明书

> 项目：企业级 CMS 内容管理系统（课程项目）
> 模块：成员A —— 文章内容与多级审核发布 + 公共基础设施
> 数据库：`cms_db`　字符集：`utf8mb4` / `utf8mb4_0900_ai_ci`　引擎：InnoDB
> 脚本：`sql/init.sql`（可重复执行，连跑两遍无报错）
> 目标版本：MySQL 9.5（本地实测环境）

## 一、设计原则

本设计遵循课程"企业级"要求，并把**不查太严但必须存在**的工业习惯一次性建齐。

| 原则 | 落地方式 | 说明 |
|---|---|---|
| 审计字段统一 | 每张表都带 `create_by / create_time / update_by / update_time` | 谁在什么时候改的，永远查得到 |
| 逻辑删除统一 | 每张表都带 `deleted TINYINT DEFAULT 0` | 业务表一律不物理删除；MP 用 `@TableLogic(value="0", delval="1")` |
| 主键统一 | `id BIGINT UNSIGNED AUTO_INCREMENT` | 无业务含义的自增代理键 |
| 无物理外键 | 全部使用**逻辑外键**（列上建索引，不建 `FOREIGN KEY`） | 避免分库分表与批量导入时的锁表问题，关联完整性由 Service 层保证 |
| 外键列必带索引 | 所有 `*_id` 关联列均建 `idx_*` | 见 §五 索引汇总，实测无遗漏 |
| 注释齐全 | 每张表、每个字段都有 `COMMENT` | 可直接导出为数据字典 |
| 时间语义 | 全部 `DATETIME`，不使用 `TIMESTAMP` | 避开 2038 与时区隐式转换 |
| 金额/枚举 | 状态一律 `TINYINT`，取值注释与状态机编号严格一致 | 见 §四 |
| 文本可检索 | 标题建索引；正文用 `LONGTEXT` 走检索表 | `cms_article_index` 承担全文与热度检索 |

**脚本可重复执行**：脚本开头 `CREATE DATABASE IF NOT EXISTS` → `SET FOREIGN_KEY_CHECKS = 0` → 按依赖倒序 `DROP TABLE IF EXISTS` 17 张 → 按正序 `CREATE TABLE` → 灌入字典与演示数据 → 末尾执行校验查询。因此**全新环境首次执行、已有环境重复执行，结果一致**。

## 四、核心表字段说明

### 4.1 `cms_article`（文章主表）—— 全项目最关键的一张表

| 字段 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| `title` | VARCHAR(200) | 否 | — | 标题，建索引支持模糊检索 |
| `summary` | VARCHAR(500) | 是 | NULL | 摘要 |
| `content` | LONGTEXT | 否 | — | 正文（富文本 HTML） |
| `cover_image` | VARCHAR(500) | 是 | NULL | 封面图 URL |
| `author_id` | BIGINT UNSIGNED | 否 | — | 作者，**水平越权校验依据** |
| `category_id` | BIGINT UNSIGNED | 否 | — | 分类，逻辑外键 |
| `status` | TINYINT | 否 | 0 | **文章状态，取值与状态机编号严格一致** |
| `is_top` | TINYINT | 否 | 0 | 是否置顶：0 否 / 1 是 |
| `view_count` | INT UNSIGNED | 否 | 0 | 浏览量 |
| `version` | INT | 否 | 0 | **MP 乐观锁 `@Version` 版本号**，每次更新 +1 |
| `reject_reason` | VARCHAR(500) | 是 | NULL | 最近一次驳回意见 |
| `schedule_time` | DATETIME | 是 | NULL | 定时发布时间（`status=6` 时有效） |
| `publish_time` | DATETIME | 是 | NULL | 实际发布时间 |
| `offline_time` | DATETIME | 是 | NULL | 下架时间 |
| `create_by` / `create_time` / `update_by` / `update_time` | — | 否 | — | 审计四字段 |
| `deleted` | TINYINT | 否 | 0 | 逻辑删除：0 未删 / 1 已删 |

**`status` 取值（10 种，与 `docs/状态机图.md` 完全对齐）**

| 值 | 枚举名 | 中文 | 演示篇数 |
|---|---|---|---|
| 0 | `DRAFT` | 草稿 | 2 |
| 1 | `PENDING_EDITOR` | 待编辑初审 | 2 |
| 2 | `PENDING_CHIEF` | 待主编终审 | 2 |
| 3 | `APPROVED` | 已通过（待发布） | 2 |
| 4 | `REJECTED` | 已驳回 | 2 |
| 5 | `PUBLISHED` | 已发布 | 3 |
| 6 | `SCHEDULED` | 定时发布中 | 1 |
| 7 | `WITHDRAWN` | 已撤回 | 2 |
| 8 | `OFFLINE` | 已下架 | 2 |
| 9 | `ARCHIVED` | 已归档（**终态**） | 2 |

> 20 篇文章覆盖全部 10 种状态，用于前端状态分色标签、状态筛选、状态机单测的全量演示。

### 4.2 `cms_article_audit_log`（审核流水表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED | 主键 |
| `article_id` | BIGINT UNSIGNED | 文章 ID，逻辑外键 |
| `audit_stage` | TINYINT | 审核阶段：1 编辑初审 / 2 主编终审 |
| `audit_action` | TINYINT | 审核动作：1 通过 / 2 驳回 |
| `auditor_id` | BIGINT UNSIGNED | 审核人 |
| `auditor_role` | VARCHAR(50) | 审核人角色码（留痕，防角色变更后追溯不清） |
| `audit_opinion` | VARCHAR(500) | 审核意见 |
| `from_status` | TINYINT | 变更前状态 |
| `to_status` | TINYINT | 变更后状态 |
| `audit_time` | DATETIME | 审核时间 |
| `article_version` | INT | 审核时的文章版本号（与 `cms_article_version.version_no` 对得上） |
| `create_by` / `create_time` / `update_by` / `update_time` / `deleted` | — | 审计 + 逻辑删除 |

> **M3 里程碑判定依据**：一篇正常文章走到 `APPROVED`（`status=3`）时，`cms_article_audit_log` 中该文章流水恰好 **2 条**（编辑初审 1 条 + 主编终审 1 条）。若做 5 级审核则对应 5 条。

### 4.3 `cms_article_version`（版本快照表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED | 主键 |
| `article_id` | BIGINT UNSIGNED | 文章 ID |
| `version_no` | INT | 版本号，与 `cms_article.version` 对应 |
| `title` / `summary` / `content` / `category_id` | — | **快照内容**（回滚时整体覆盖写回主表） |
| `snapshot_type` | TINYINT | 快照类型：1 自动（提交审核）/ 2 手动（用户主动保存） |
| `modifier_id` | BIGINT UNSIGNED | 修改人 |
| `change_summary` | VARCHAR(500) | 变更摘要 |
| `create_by` / `create_time` / `update_by` / `update_time` / `deleted` | — | 审计 + 逻辑删除 |

唯一索引 `uk_article_version(article_id, version_no)` —— **同一文章同一版本号只允许一条**，这是回滚正确性的硬保障。

### 4.4 `sys_user`（用户表）

| 字段 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| `username` | VARCHAR(50) | 否 | — | 登录名，唯一索引 `uk_username` |
| `password` | VARCHAR(100) | 否 | — | BCrypt 哈希（**永不存明文**） |
| `nickname` | VARCHAR(50) | 否 | — | 显示昵称（前端右上角、审核人展示用） |
| `phone` | VARCHAR(20) | 是 | NULL | 手机号（脱敏展示） |
| `email` | VARCHAR(100) | 是 | NULL | 邮箱 |
| `avatar` | VARCHAR(255) | 是 | NULL | 头像 URL |
| `status` | TINYINT | 否 | 1 | 账号状态：**0 禁用 / 1 正常** |
| `last_login_time` | DATETIME | 是 | NULL | 最近登录时间（登录成功时更新） |
| `create_by` / `create_time` / `update_by` / `update_time` | — | — | — | 审计四字段（`create_time`/`update_time` 有 `CURRENT_TIMESTAMP` 默认值） |
| `deleted` | TINYINT | 否 | 0 | 逻辑删除：0 未删 / 1 已删 |

> ⚠️ 注意 `status` 的默认值是 **1（正常）**，与 `cms_article.status` 默认 **0（草稿）** 语义方向不同 —— 这是刻意的：账号默认可用，文章默认未提交。写 MP 实体时不要想当然复用同一个"默认值约定"。

### 4.5 `sys_apply_approval`（授权申请审批表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED | 主键 |
| `applicant_id` | BIGINT UNSIGNED | 申请人 |
| `target_user_id` | BIGINT UNSIGNED | 被授权（申请目标）用户 |
| `apply_type` | TINYINT | 申请类型：1 角色授予 / 2 权限授予 |
| `apply_content` | VARCHAR(500) | 申请内容（角色码或权限码，逗号分隔） |
| `apply_reason` | VARCHAR(500) | 申请理由 |
| `status` | TINYINT | 审批状态：0 待审批 / 1 已通过 / 2 已驳回 |
| `approver_id` | BIGINT UNSIGNED | 审批人（可空，待审批时为空） |

| `create_by` / `create_time` / `update_by` / `update_time` / `deleted` | — | 审计 + 逻辑删除 |

> 本表是"**审批流程 → 授权生效**"的落地：审批通过后由 Service 层写 `sys_user_role` / `sys_role_permission`，与文章审批形成"双审批链"对照。

## 六、设计决策记录（ADR）

| # | 决策 | 备选方案 | 选择理由 |
|---|---|---|---|
| 1 | 用自增 `BIGINT` 主键 | UUID / 雪花 ID | 单机课程项目无需分布式唯一；自增利于 InnoDB 聚簇索引顺序写入，且调试时肉眼可读 |
| 2 | 无物理外键，只用逻辑外键 | 建 `FOREIGN KEY` | 演示数据批量导入不被外键顺序绑定；删除分类/标签时不必级联；完整性由 Service 层显式校验（更符合"业务规则不下沉到数据库"的企业习惯） |
| 3 | 逻辑删除而非物理删除 | `DELETE FROM` | 审核流水与版本快照必须可追溯；`deleted` 配合 MP `@TableLogic` 全局生效 |
| 4 | 状态用 `TINYINT` 不用 `ENUM` | MySQL `ENUM` | `ENUM` 改值需 DDL、Java 侧枚举映射麻烦；`TINYINT` + Java 枚举 + 状态机映射表更可控 |
| 5 | `cms_article.version` 走乐观锁 | 悲观锁 `SELECT ... FOR UPDATE` | 编辑与审核并发场景是"同一文档偶发冲突"，重试成本低；乐观锁不占用数据库连接 |
| 6 | 正文与检索分离 | 直接在 `cms_article.content` 上做全文索引 | `LONGTEXT` 全文索引体积大、写入慢；独立 `cms_article_index` 可改索引策略而不动主表 |
| 7 | 分类只做两级 | 无限级树 | 课程演示够用；两级用 `parent_id` 足够，避免递归查询复杂度 |
| 8 | 演示数据覆盖全部 10 状态 | 只放几条 | 前端状态分色、状态筛选、状态机测试需要全量数据，一次到位 |

## 七、外键依赖顺序（建表/清表顺序依据）

**建表正序**（被依赖的先建）

```
sys_user → sys_role → sys_permission → sys_user_role → sys_role_permission
         → sys_apply_approval
         → cms_category → cms_category_audit_log → cms_tag → cms_article_tag
         → cms_article → cms_article_audit_log → cms_article_version
         → cms_article_index → sys_oper_log → sys_login_log → sys_report
```

**清表倒序**（`DROP TABLE IF EXISTS` 的顺序，脚本中按此排列）

```
sys_report → sys_login_log → sys_oper_log → cms_article_index
→ cms_article_version → cms_article_audit_log → cms_article
→ cms_article_tag → cms_tag → cms_category_audit_log → cms_category
→ sys_apply_approval → sys_role_permission → sys_user_role
→ sys_permission → sys_role → sys_user
```

> 脚本仍保留 `SET FOREIGN_KEY_CHECKS = 0` 作为双保险（虽然本设计无物理外键，此举让脚本对"将来有人加了外键"也健壮）。
