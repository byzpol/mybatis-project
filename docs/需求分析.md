## 一、项目背景与目标

### 1.1 背景

本项目是《JAVA框架技术（一）》课程指定的课程项目设计，要求在实验二「SSM 框架整合 + EMP 员工管理 MIS 系统」的基础上做企业级升级，交付一个**可运行、可演示**的内容管理系统。

需要先澄清一个容易跑偏的定性：**它不是"文章发布网站"，而是带审批流转的内容运营后台。**

区别在于三点：

1. **内容不是想发就发** —— 一篇文章要走「草稿 → 编辑初审 → 主编终审 → 发布」的完整审批链，任一级驳回都要退回修改，并留下审核意见
2. **分类变更也要审批** —— 分类的新增与变更不能直接生效，需管理员审批通过后方可启用
3. **权限变更同样走审批** —— 角色申请与权限变更都要提交申请单，由管理员审批后落库

也就是说，本系统的核心复杂度不在增删改查，而在**状态流转 + 审批留痕 + 权限管控**这三件事上。

### 1.2 目标

| 维度 | 目标 |
|---|---|
| 功能目标 | 完整实现评分表要求的 7 个核心业务场景：文章发布、分类、审核、用户管理、权限管控、数据检索、日志记录 |
| 架构目标 | 完成 SSM 全注解整合，建立标准化企业级分层目录，形成可复用的公共主干 |
| 数据目标 | 用户 / 角色 / 权限 / 文章 / 分类 / 日志六表关联设计，杜绝单表开发 |
| 工程目标 | 统一接口契约、统一返回结构、统一异常与错误码，四人并行开发不互相污染 |
| 交付目标 | 可运行系统 + 建库脚本 + 接口文档 + ApiFox 测试用例集 + 架构图 + 规范自检表 + 结题报告 |

### 1.3 范围边界

**在范围内**：内容生产与多级审核、分类与标签体系、用户角色权限与授权审批、操作日志审计与数据检索统计、后台管理界面。

**不在范围内**（明确排除，避免过度设计）：前台门户网站、评论互动、第三方登录（微信/微博）、消息推送、全文检索引擎（Elasticsearch）、分布式部署与缓存中间件。

## 二、干系人角色表

系统内共 4 类业务角色，对应 4 类操作视角。

| 角色 | 角色编码 | 核心职责 | 在文章链路上的权限 | 在权限链路上的权限 |
|---|---|---|---|---|
| 投稿人 | `ROLE_AUTHOR` | 撰写与维护自己的稿件 | 创建草稿、编辑自己的草稿、提交初审、撤回自己的已发布文章 | 只能发起角色/权限申请，无审批权 |
| 编辑 | `ROLE_EDITOR` | 内容初审（第一道关） | 对「待编辑初审」的文章通过或驳回，可写审核意见 | 无 |
| 主编 | `ROLE_CHIEF` | 终审与发布决策 | 对「待主编终审」的文章通过或驳回；发布、排期、下架、归档任意文章 | 无 |
| 管理员 | `ROLE_ADMIN` | 系统与权限治理 | 拥有全部文章权限 | 审批角色申请与权限变更、分配角色、配置权限 |

**角色间的关键约束**（这里是最容易被忽略、也是最容易出漏洞的地方）：

1. **投稿人只能操作自己的文章** —— 不能靠猜 ID 编辑或撤回别人的稿件（水平越权防护）
2. **审核人不能审核自己提交的文章** —— 否则初审形同虚设（自审拦截）
3. **编辑只有初审权，主编才有终审与发布权** —— 这是两级审核能成立的前提（垂直越权防护）
4. **已归档文章对所有人只读** —— 归档是终态，任何角色都不能再改动

## 三、核心业务场景

评分表明确要求覆盖 7 个场景，本节逐条落地。

| # | 核心场景 | 一句话说明 | 归属业务域 | 负责人 |
|---|---|---|---|---|
| 1 | 文章发布 | 文章的创建、编辑、提交、审核、发布、撤回、下架、归档全生命周期 | 业务域一 | 成员A |
| 2 | 分类 | 分类的增删改查与变更审批，标签体系的维护与文章打标 | 业务域二 | 成员B |
| 3 | 审核 | 两级审核（编辑初审、主编终审），含通过/驳回、意见回填、审核流水留痕 | 业务域一 | 成员A |
| 4 | 用户管理 | 用户注册、登录、退出、信息维护、启用禁用 | 权限域（公共基础设施） | 成员C |
| 5 | 权限管控 | RBAC 模型、角色分配、细粒度权限拦截、AOP 接口权限校验、权限变更审批 | 业务域三 | 成员C |
| 6 | 数据检索 | 文章的多条件组合检索、模糊查询、分页、统计报表 | 业务域四 | 成员D |
| 7 | 日志记录 | 操作日志与登录日志的自动采集、审计查询、异常告警 | 业务域四 | 成员D |

### 3.1 四个业务域与 7 个场景的映射关系

四个业务域不是把 7 个场景简单四分，而是按**业务链路的完整性**切分，避免出现"两个人改同一张表"的情况：

| 业务域 | 负责人 | 覆盖的场景 | 主要数据表 |
|---|---|---|---|
| 业务域一 · 文章内容与多级审核发布 | 成员A | 场景 1 文章发布、场景 3 审核 | `cms_article`、`cms_article_audit_log`、`cms_article_version` |
| 业务域二 · 内容分类与标签体系 | 成员B | 场景 2 分类 | `cms_category`、`cms_category_audit_log`、`cms_tag`、`cms_article_tag` |
| 业务域三 · 用户角色权限与授权审批 | 成员C | 场景 4 用户管理、场景 5 权限管控 | `sys_user`、`sys_role`、`sys_permission`、`sys_user_role`、`sys_role_permission`、`sys_apply_approval` |
| 业务域四 · 操作日志审计与数据检索统计 | 成员D | 场景 6 数据检索、场景 7 日志记录 | `sys_oper_log`、`sys_login_log`、`cms_article_index`、`sys_report` |

**注册 / 登录 / 退出属于公共基础设施**，四人共用，不单独计入某个业务域，但归属成员C 建设（因为涉及 Session 与权限上下文）。

## 五、非功能需求

### 5.1 性能

| 编号 | 需求 | 验收标准 |
|---|---|---|
| N-P01 | 列表查询响应 | 单表数据量 1000 条以内时，分页查询接口响应时间 ≤ 500ms |
| N-P02 | 分页参数保护 | 分页 `size` 上限 100，超出按 100 截断，防止一次拉全表 |
| N-P03 | 索引有效性 | 文章列表、审核流水、排期扫描三类高频查询的执行计划 `type` 不为 `ALL` |
| N-P04 | 避免 N+1 | 列表类接口的 SQL 条数固定（不随返回行数增长） |
| N-P05 | 批量操作 | 批量提交审核等批量操作不采用逐条循环写库 |

### 5.2 安全

| 编号 | 需求 | 验收标准 |
|---|---|---|
| N-S01 | 密码存储 | 密码一律 BCrypt 加密落库，数据库中不存在明文密码 |
| N-S02 | 会话鉴权 | 未登录访问受保护接口返回 401；无权限返回 403 |
| N-S03 | 水平越权防护 | 投稿人无法通过构造 ID 编辑或撤回他人文章，命中返回业务码 11004 |
| N-S04 | SQL 注入防护 | MyBatis 一律使用 `#{}` 占位符；拼接进 order by 的字段做白名单校验 |
| N-S05 | 敏感信息不外泄 | 全局异常兜底不向前端返回堆栈或原始异常消息；日志与响应中不出现密码、Session ID |
| N-S06 | 凭据不入库 | 数据库口令写入本地配置文件并加入 `.gitignore`，严禁提交到版本库 |
| N-S07 | XSS 防护 | 富文本内容入库前做白名单过滤，输出时进行转义 |

### 5.3 可用性

| 编号 | 需求 | 验收标准 |
|---|---|---|
| N-U01 | 统一错误提示 | 所有失败响应均为统一结构，前端可统一解包与提示，无需针对单个接口特殊处理 |
| N-U02 | 参数校验友好 | 参数校验失败返回中文提示，明确指出是哪个字段不合法 |
| N-U03 | 状态冲突可辨识 | 状态不允许的操作返回 409 或对应业务码，与系统异常（500）明确区分 |
| N-U04 | 事务一致性 | 状态变更与流水记录在同一事务内，不允许出现"状态改了但流水丢了" |
| N-U05 | 逻辑删除 | 删除为逻辑删除，误删数据可恢复，且删除后列表与详情均不可见 |
| N-U06 | 日志可追溯 | 所有写操作可通过操作日志追溯到操作人、时间、IP 与结果 |
