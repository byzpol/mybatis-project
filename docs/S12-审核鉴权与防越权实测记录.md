## 二、五个关键决定

### 2.1 两类越权分开处理，判据是"在哪拦得住"

| | 垂直越权（功能级） | 水平越权（数据级） |
|---|---|---|
| 拦在哪 | Controller 上的 `@RequirePermission`（成员C 的切面） | **Service 里**（切面看不到数据归属） |
| 返回 | **403** | **11003 / 11004**（HTTP 仍 200） |
| Service 要不要重复判断 | **不要**（双重拦截会让报错信息混乱） | **必须**，这是唯一拦截点 |
| 能怎么验 | 只能真机（JUnit 直接调 Service 绕过切面） | JUnit 可测 |

**这个划分直接决定了本步的验证方式**：垂直越权写进 `target/s12-live.sh`（HTTP），
水平越权写进 `ArticleOwnershipAuthzTest`（直接调 Service）。两边的数字不能互相替代。

### 2.2 把"权限注解有没有漏"变成**反射断言**，而不是人工数一遍

手册核查项是"权限注解覆盖全部接口，没有一个写接口漏掉"。人工数一遍能得到当时的结果，
但**下次加接口时没人会再数** —— 而"新加写接口忘了加权限注解"正是最典型的越权成因：
编译通过、功能正常、只有安全检查缺失。

`ApiPermissionCoverageTest` 因此做了四件事（都是断言，不是打印）：

1. 文章模块每个接口必须有 `@RequirePermission`，且权限码**必须真实存在于 `sys_permission`**
   （拼错不报错，只会在运行时变成"谁都没权限"—— 本项目在契约 §1.3 的 `article:edit` 上踩过）；
2. 写接口必须有 `@OperLog`、读接口必须**没有**（**双向**断言，只查一边会漏掉反向错误）；
3. 全项目"没有权限注解"的接口必须**正好等于**写死的 11 项豁免清单；
4. 豁免清单里的名字必须都能反射到真实方法（防止"接口删了清单没删"）。

实测输出（`[S12] 全项目控制器接口：有权限注解 8 个，刻意豁免 11 个`）与实现完全吻合。

### 2.3 豁免清单写在**测试**里，不写在注解里

豁免的三种正当理由是：**探针**（健康检查要被监控系统匿名调用）、**认证入口**（登录时还没有身份）、
**主干自测**（S05/S06 留的验证接口）。三种理由互相不同，没法用注解表达。
写在测试里的好处是：**加一行就要改一次测试**，改动本身会出现在 code review 里。

### 2.4 ★ 权限矩阵用 `id=99999999` 跑 —— 零数据改动

切面在参数绑定之后、方法体之前执行，于是对同一个请求：

```
没权限的角色 → 403      （根本进不到方法体）
有权限的角色 → 11001    （进了方法体，但文章不存在）
```

两个结果都不会改动任何数据。于是 **16 项权限探测 + 8 项水平越权**可以在真机上跑完，
而**库表一条记录都不变**。实测核对：矩阵跑完后 `articles=20 / versions=10 / audit_logs=12`，
前 20 篇种子文章的状态码与 S11 结束时逐字相同。

> 唯一的例外是 `article:create`（四个角色都有，探测不出差异），单独建 4 篇草稿并在脚本末尾清理。

### 2.5 `checkOwnership` 坚持**没有**"超级管理员短路"

契约 §6.4 的示例片段写的是"超管直接 return"，本项目不采纳。三个理由（签名里没有角色 /
业务上不该允许 / 最小权限原则）写在 `ArticleServiceImpl#checkOwnership` 的注释里。
`testCase05`（admin 改别人草稿 → 11003）与真机第 9 项就是这个决定的守门人。

## 三、手册三个问题的回答

手册 S12 要求"特别说明这几个容易想错的地方"。逐条回答，并都已落实进 `docs/接口分类与鉴权表.md` §二。

### 3.1 谁能撤回？

**答案：只有作者本人。** 主编要撤别人的稿，用"下架"（`article:manage`）。

手册问我倾向"只有作者 + 主编"，我改了主意，理由是两条硬的：

1. **状态机已经把两个动作分开了。**
   `PUBLISHED(5) + WITHDRAW → WITHDRAWN(7)`（作者主动收回，之后还能再发）
   `PUBLISHED(5) + OFFLINE  → OFFLINE(8)`（运营强制拿下）。
   两条不同出边、不同目标状态 —— 都叫"撤回"用户分不清"我自己收的"和"我被下架的"。
2. **冻结的 Service 签名里没有角色。**
   `void withdraw(Long id, Long operatorId)` 只传 id。要表达"作者 **或** 主编"，
   Service 就得知道角色 → 要改签名 = 改契约。而"作者走 withdraw、主编走 offline"
   两句话说清了同一件事，且不动契约。

### 3.2 谁能下架 / 归档？

**答案：只有主编或管理员，作者不行。** 且这两个动作**不做归属校验**。

`article:manage` 库里只给了 `ROLE_CHIEF(12)` 与 `ROLE_ADMIN(20)` —— 权限层已经表达了"这不是你的活儿"，
再叠一层归属校验是多余的，还会把"主编下架任何人写的违规内容"这个正当场景挡住。

⚠️ 这与 §3.1 正好相反。判据是**"这个动作的主语是谁"**：撤回是作者对自己内容的动作（要归属），
下架是运营对他人的内容的动作（不要归属）。

### 3.3 编辑 / 主编能否修改别人的文章内容？

**答案：不能。** 已由 `checkOwnership` 实现并实测：编辑、主编、管理员改别人的草稿一律 **11003**。
审核人有自己的入口（`/articles/{id}/audit`），审核意见可以写、正文不能改。

## 四、本步实测抓到的发现

### 4.1 ★ 同一句「审自己的稿」，对不同角色返回不同的码

这是本步最有价值的一条发现，**做用例时极容易写错**：

```
投稿人审自己的稿      → 403    没有该操作权限，需要：article:audit
编辑  审自己创建的稿  → 11004  不能审核自己创建的文章
```

原因：投稿人**没有** `article:audit`，垂直越权层先把它拦在门外，根本走不到 `checkNotSelfAudit`。
只有"**有**这个权限、又恰好是作者"时，才能看到 11004。

**这不是 bug，是两层拦截的先后顺序可观测。** 我第一版脚本把这条例写成"期望 11004"，
得到的是一个**假的 FAIL**；改法不是改代码，而是拆成两条用例并把这个差异写进文档。

> 教训与 F02/F03/S11 一致：**断言失败先确认"我以为的判据"本身是不是错的。**

### 4.2 归属校验排在状态校验之前（顺序是可观测行为）

非作者改一篇**已归档**的文章，返回的是 **11003** 而不是 **11011**。
两个码都"拒绝"，但给用户的提示不同（"这不是你的稿" / "已归档不能改"）。
`updateDraft` 里 `checkOwnership` 在 `requireEditable` 之前，所以先答归属。
`testCase10` 与真机第 10 项把这个顺序钉住。

### 4.3 联调脚本自身的一个 bash 错误

第一版写了 `M_$who="$LAST_HTTP/$LAST_CODE"`，8 条断言全空。
根因：**bash 赋值的左侧不做变量展开**，`M_author=403/403` 被当成命令执行。
改用关联数组 `declare -A` 后正常。修正后 **PASS=37 / FAIL=0**。

### 4.4 手册的错误码错位（沿用，本步再确认一处）

手册 S12 要求：
- "用投稿人 A 的会话去编辑投稿人 B 的草稿 → **11004**" → 实测 **11003**
  （11004 是"不能审核自己创建的文章"）；
- "用已归档文章的 ID 调任何写操作 → **11010**" → 实测 **11011**
  （11010 是乐观锁冲突"文章已被他人修改"，11011 才是"已归档的文章不可修改"）。

一律以 `ErrorCode` 为准。**本步没有新增任何错误码**（主干冻结）。

> 另外手册 S12 的接口清单里"编辑初审"和"主编终审"是分开列的，实际是**同一个接口**
> （`POST /articles/{id}/audit`，环节由状态推导）—— 这是 S10 的决定，此处不重复。

## 七、下一步（S13）

手册 S13：**排期发布与立即发布** —— `publishNow()` / `publishSchedule()` / `@Scheduled` 定时任务 /
`CmsArticlePublishDTO`。

本步为 S13 留下的衔接点：

- 权限码已定：两个发布接口都是 **`article:publish`**，且**不做归属校验**（运营动作）；
  能调的角色是主编 / 管理员（库表已验证）。
- ⚠️ **"立即发布"必须清空 `scheduleTime`**（否则库里留着一个过去的排期时间，
  下次有人查"到点该发的文章"会捞到它）。
- 状态机出边：`APPROVED(3) + PUBLISH_NOW → PUBLISHED(5)`、`APPROVED(3) + PUBLISH_SCHEDULE → SCHEDULED(6)`；
  `SCHEDULED(6) + PUBLISH_SCHEDULED_TRIGGER → PUBLISHED(5)`（**只有系统定时触发这一条人工不可达**）。
  另注意 11006「只有审核通过的文章才能发布」与 11007「排期时间必须晚于当前时间」两个码已存在但尚未使用。
- 定时任务并发安全：`@Scheduled` 多实例下会重复触发，需要靠状态机 + 乐观锁保证只发布一次
  （与 S10 的"先改状态后写流水"同一思路）。
