## Q1 · 为什么用状态机而不是 if-else？状态机放在哪一层？

**一句话答**：因为状态流转是**业务规则**，不是控制流 —— 散在 `if-else` 里会漏分支、口径不一，改一处要翻遍全项目。

**展开**

1. **集中一处**：全项目 **10 个状态（0~9）、14 条迁移**全部写在一个 `ArticleStateMachine` 里，对外**只有 `transfer(status, action)` 一个入口**。Service 层**不允许**自己写 `if (status == 0)` 去判断能不能提交。
2. **三件附带好处**：① 加/改流程只改一个文件；② 非法流转统一抛 `11002`，不用每个方法各写一遍；③ 迁移定义里带 `description`（如 `SUBMIT.description` = "提交初审"），**界面按钮文案直接从状态机取**，不是前端另写一份。
3. **放在哪一层**：放在主干 `common` 包，因为它是**文章域业务规则的唯一真相**，不属于某一层。Service 只做"编排 + 事务 + 写流水"，不做"能不能流转"的判定。
4. **还能带约束**：每条迁移带"所需角色"，所以 `PENDING_EDITOR` 状态只有 `EDITOR` 能推进，`PENDING_CHIEF` 只有 `CHIEF` 能推进。
5. **可测**：状态机是纯函数（无 IO），单测直接穷举 10 状态 × 14 动作的合法性矩阵。

**可展示证据**：`src/main/java/com/lab/cms/common/ArticleStateMachine.java`（383 行，含 mermaid 注释）、`docs/状态机图.md`、单测里的状态迁移用例。

**⚠️ 追问 1**："你们用了 Spring StateMachine 吗？" → **没有**，手写 `Map<key, target>`。理由：无额外依赖、逻辑全透明、能直接带角色与文案；课程范围内 Spring StateMachine 的收益不足以抵消理解成本。
**⚠️ 追问 2**："下架之后能不能重新发布？" → **不能**。`OFFLINE(8)` 只有 `ARCHIVE` 一条出边（指导书里写"下架可重新发布"是错的，我们以状态机为准）；**撤回是可逆的**，撤回后能重新发布。

## Q2 · 为什么用逻辑删除？逻辑删除和唯一索引冲突怎么解决？

**一句话答**：因为内容运营后台必须**留痕**（删了也要能审计），但逻辑删除会让"已删除的行"继续占着唯一键的值。

**展开**

1. **为什么逻辑删除**：文章/用户这类数据被删后仍要能追溯"谁删的、什么时候删的"；并且 `cms_article_audit_log`、版本快照都要能关联到已删文章。所以 17 张表**统一**加 `deleted` 字段，全部显式写 `@TableLogic(value="0", delval="1")`。
2. **冲突是什么**：假设 `sys_user` 上有 `uk_username(username)`。用户 A 被逻辑删除后，那一行还在，`username='A'` 还占着 → **新建同名用户会报重复键**。
3. **我们的解法**：**把 `deleted` 追加为唯一键的最后一列**，即 `uk_username(username, deleted)`。删除后该行变成 `(A, 1)`，新的 `(A, 0)` 不冲突。**9 个唯一键全部按这个方式改**（S18 修订）。
4. **⚠️ 这个解法的代价（主动说）**：`deleted` 只有 0/1，**同一个 `username` 只能被逻辑删除一次** —— 删第二次还是 `(A, 1)`，仍会冲突。更严格的做法是把 `deleted` 换成"删除时间戳"或"删除流水 id"。我们选择了简单方案，**代价已登记在文档里**，不是没意识到。
5. **另一个坑**：`@TableLogic` **只管 MyBatis-Plus 自动生成的 SQL**。**手写 XML 必须自己写 `AND deleted = 0`** —— 这个坑我们踩过并写进了规范清单。

**可展示证据**：`sql/init.sql`（搜 `uk_` 看 9 个唯一键的列顺序）、`docs/S18-逻辑删除落地与代码重构.md`、`docs/数据库设计.md`。

**⚠️ 追问**："`removeById` 之后能不能看出是谁删的？" → **默认不能**。MP 的逻辑删除 SQL 里 `SET` 只有 `deleted=1`，**不填 `update_by`/`update_time`**。要看是谁删的，必须用 `LambdaUpdateWrapper.set(...)` 显式列出列。这个我们实测确认过。

## Q3 · 你们四个人怎么保证接口风格一致的？

**一句话答**：靠**三件事**：主干统一（我维护）、契约先冻结、加新域照"入户线"走固定动作。

**展开**

1. **主干由我一人维护、且冻结**：`config`/`common`/`base`/`annotation`/`aspect`/`interceptor`/`util` 七个包，规则是**只许加方法、不许改签名**，S08 冻结并打了 tag `trunk-v1.0`。别人要用新能力，只能**加**，不能改。
2. **契约先冻结（比代码更重要）**：`docs/接口契约.md` 里定了统一返回体 `Result<T>{code, message, data, timestamp}`、**双层错误码**（`100~599` 同步 HTTP 状态；`10xxx~14xxx` 保持 HTTP 200）、统一分页 `PageQuery`（`size ≤ 100`）、路径前缀 `/api/v1/`。四个人按同一份契约写。
3. **"入户线"是固定动作**：新增一个业务域，动作顺序固定 —— 建表 → entity/mapper → service 接口+实现 → controller → DTO/VO → 权限码登记 → 接口清单登记。照做就自然同构。
4. **口径以库表为准**：权限码的**唯一真相是 `sys_permission` 表的 20 条**，不是文档。如果契约和库表不一致，**改契约**。我们就是这么修掉了 `article:list/edit/offline/archive` 这四个不存在的权限码。
5. **⚠️ 如实说明**：本仓库交付的是**文章域 + 公共基础设施**；**S24 已补上分类/标签/日志/报表四域**，端点从 28 涨到 **48 个**（其中文章域 16 个）。仍未交付的是**用户权限域**（成员C）—— 它的表结构与权限体系已就绪，业务接口由该成员按同一套入户线补即可，**主干不用改一行**，这正是"集中管理"要达到的效果。

**可展示证据**：`docs/接口契约.md`、`docs/接口清单.md`（48 个端点全部同构）、`sys_permission` 表、tag `trunk-v1.0`。

**⚠️ 追问**："那如果有人非要改主干签名呢？" → 主干变更要走登记：写清"为什么必须改、影响哪些调用方"，并**同步更新契约**。我们的提交规约里有这一条。

## Q4 · 事务失效的场景你们遇到过吗？

**一句话答**：遇到过，而且是**静默失效**（不报错但不起作用），比报错难查得多。

**展开**

1. **① 同类自调用（最经典）**：`@Transactional` 靠**代理**生效，`this.method()` 走的是原始对象，**代理没进入，事务不生效**。我们在做"逐条独立事务"的登录日志时正好需要避开它 —— 做法是**经外部 Bean 调 Service 接口**，并配 `REQUIRES_NEW`。
2. **② 没配 `PlatformTransactionManager`**：纯 SSM 手写配置下，`@EnableTransactionManagement` **只是打开开关**，找不到事务管理器时它**静默跳过代理创建、不抛异常**。所以必须显式声明 `DataSourceTransactionManager` Bean。这是"不报错的失效"。
3. **③ 异常被吃掉**：`try-catch` 里把异常吞了、没重新抛，Spring 看不到异常 → **不回滚**。默认只有 `RuntimeException`/`Error` 才回滚，受检异常要加 `rollbackFor`。
4. **④ 注解加在 private 方法/接口上**：加在 `private` 或 `final` 方法上不生效。
5. **⑤ 单测里的"自动回滚"是另一回事**：`@Transactional` 加在**测试类**上，Spring Test 会在每个用例结束后回滚，让测试不污染库 —— 这跟业务事务是两套机制，别混。我们用它保证 390 个用例反复跑后数据库行数不变。

**可展示证据**：`config/JdbcConfig.java#transactionManager` 的注释、`docs/AI应用记录.md`（S19 §3.1 专章讲"为什么测试类上的 `@Transactional` 能回滚、什么时候失效"）、单测跑完的行数快照。

**⚠️ 追问**："怎么证明你们的事务真的生效了？" → 用**失败回滚**验证：故意让写流水的那一步抛异常，看主表状态是否回滚。`ArticleServiceImpl#audit` 里的注释就写明了"流水写失败时状态会被同一事务回滚"。

## Q5 · AI 在你们项目里承担了什么？哪些是你们自己判断的？

**一句话答**：AI 承担**编码与文档的生产力**，人承担**判断与验证**；凡是"AI 说项目里做了 X"，都必须回代码或库表确认 X 真的存在。

**展开**

1. **AI 具体做了什么**：写 CRUD/样板代码、生成文档初稿与 mermaid 图、写取数脚本和测试脚本、解释报错、整理规范清单。
2. **人做了什么判断**：① 技术选型的取舍（Druid vs Hikari、手写状态机 vs Spring StateMachine、分页方案 A/B）② 状态机每一条迁移的合法性 ③ 权限码口径以**库表**为准 ④ **每一条 AI 产出都用实测验证**。
3. **AI 给错、被实测纠正的例子**（这部分最能得分，我们专门记录了 796 行）：
   - AI 生成的 `updateById` 代码**不填审计列**（MP 默认 `NOT_NULL` 策略静默跳过）→ 清空字段返 200 但库里没改
   - 同类问题：`removeById` 的逻辑删除 SQL 里 `SET` 只有 `deleted=1`，**看不出是谁删的**
   - AI 写的文档注入脚本用 Python 文本模式写文件，在 Windows 上把**整份文档的 `\n` 变成 `\r\n`**，造出"整文件假 diff"
   - AI 扫权限注解时**只往上找一行**，扫出 16 个端点权限全空 —— 实际注解写在 mapping **下方**
   - AI 的自检正则没锚行首，把 Javadoc 里的 `{@code @GetMapping}` **示例代码也数成端点**（数出 18，真实 16）
   - S24 里 AI 把 `BusinessException` 的访问器写成 `getErrorCode()`（Lombok 实际生成的是 `getCode()`）→ 编译报"找不到符号"，**11 处一并改正**
   - S24 断言里 `assertEquals("...", 1, levelOf(id))` 一个基本类型、一个包装类型 → **`assertEquals` 重载歧义**编译不过，两侧统一成 `Integer.valueOf/Long.valueOf`
4. **纪律**：**"AI 写的代码我能逐行讲清楚，讲不清的不采用"**。这份答辩材料里每一条结论都能指到文件或接口。
5. **过程痕迹**：`docs/AI应用记录.md` 分六部分（S19~S24），每步记"做了什么 / AI 给错在哪 / 怎么暴露的 / 最终处置"，**累计 30+ 条**。

**可展示证据**：`docs/AI应用记录.md`（796 行）、各 `docs/Sxx-*` 与 `docs/Fxx-*` 实测记录里的"AI 给错被纠正"段。

## Q6 · 为什么用 MyBatis-Plus 3.5.5 而不是指导书写的 3.5.3.1？

**一句话答**：因为**依赖仓库里拉不到 3.5.3.1**，只有 3.5.5；而且 3.5.5 向后兼容、修了几个分页与逻辑删除的缺陷。

**展开**

1. **直接原因**：本地/企业 Maven 仓库中该版本不存在，`3.5.3.1` 解析失败；`3.5.5` 可用。**这是环境事实，不是偏好**。
2. **兼容性**：3.5.x 主线 API 稳定，`@TableLogic`、`MetaObjectHandler`、分页插件 `MybatisPlusInterceptor` 的用法都没变，迁移成本为零。
3. **收益**：3.5.5 修了分页插件在特定 JOIN 场景下 `count` 优化失效、以及逻辑删除与填充策略交互的几个问题 —— 正好是我们会踩的坑。
4. **已做验证**：**390 个单元测试全过**、真机部署 **44 项校验全过**、排期任务 **12 项验证全过**，没有出现版本相关问题。
5. **顺带一个环境坑（加分点）**：项目编译参数里有 **`<arg>-proc:full</arg>`**。原因是 JDK 23+ 的 `javac` 默认**不再自动运行注解处理器**，Lombok 会**静默失效**（编译报"找不到 getter/setter"）。我们的 Maven 跑在 JDK 25 上，必须显式打开。

**可展示证据**：`pom.xml`（版本矩阵 + `-proc:full`）、`docs/结题报告.md` §5.1、`docs/S19` 测试规模。

**⚠️ 追问**："那你们到底用哪个 JDK 编译、哪个跑？" → **编译 JDK 21 目标、Maven 运行在 JDK 25**（因 `<proc:full>` 已处理注解处理）；**Tomcat 必须用 JDK 21 启动**（实测过，用 JDK 25 起也能起，但 `system/health` 报的 `javaVersion` 与部署基线不符）。

## Q7 · 排期发布是怎么实现的？没有请求上下文时审计字段怎么填？

**一句话答**：`@Scheduled` 每分钟扫一次 `status=6 且 schedule_time <= now()` 的文章自动发布；没有登录上下文时，审计字段填**哨兵值 0**（`SYSTEM_USER_ID`）。

**展开**

1. **实现**：文章排期后状态置为 `SCHEDULED(6)`。`ArticlePublishScheduler` 用 `@Scheduled(cron)` **每分钟**跑一次，查出到期的文章 id，逐篇走状态机 `6 → 5`，写 `publish_time`、清空 `schedule_time`。
2. **没有请求上下文怎么办**：`AuditMetaObjectHandler.getCurrentUserId()` 通过 `RequestContextHolder` 拿当前请求，定时任务里拿不到 → **捕获异常，返回 `SYSTEM_USER_ID = 0`**（不返回 null，避免审计列变空）。
3. **实测验证**：自建文章走完整链路 → 排期到 `17:09:31` → **轮询到 +110 秒时自动发布**（`status 6 → 5`），`publish_time = 17:10:00`、**`publisher_id = 0`**、`schedule_time` 被清空。全程**没有任何人点按钮**。
4. **为什么填 0 而不是 null**：这样数据上能区分"**人发的**"和"**系统发的**"；如果填 null，就变成了"不知道谁发的"。
5. **幂等与局限（主动说）**：每次发布**先判状态再改**，重复扫描不会重复发布；但这是**单机内存调度**，**多实例部署会重复触发**（要上分布式调度/分布式锁才解决）。课程范围是单机 Tomcat，属合理取舍。

**可展示证据**：`task/ArticlePublishScheduler.java`、`base/AuditMetaObjectHandler.java`、`docs/部署记录.md` §七（12 项实测输出）、`docs/S13-发布与排期实测记录.md`。

## Q8 · 水平越权和垂直越权的区别？你们分别怎么防的？

**一句话答**：垂直越权是"**干了自己不该干的那类事**"（按权限码拦，出 403）；水平越权是"**动了自己不该动的那条数据**"（按数据归属拦，出 200 + 11003）。

**展开**

1. **垂直越权**：低权限角色执行高权限操作。例：`author`（无 `article:audit`）去调审核接口。
   → 由 **AOP 切面 `PermissionAspect`** 读方法上的 `@RequirePermission("article:audit")` 判断，没有权限码直接 **HTTP 403**。
2. **水平越权**：同角色下的越界。例：`author` 去撤回 `author2` 的文章。
   → 由 **Service 层的 `checkOwnership`** 比对"当前用户 id"与"文章 authorId"，不匹配返回 **HTTP 200 + code 11003**。
3. **为什么要分两层**：权限码回答"能不能做这类事"，归属校验回答"能不能对**这条**数据做"。**两层都要有**，只有权限码挡不住横向越权（同角色的人权限码完全一样）。
4. **三级失败形态（最容易被混，我们专门整理了）**：

   | 现象 | 谁拦的 | 含义 |
   |---|---|---|
   | **HTTP 401** | `LoginInterceptor` | 没登录 |
   | **HTTP 403** | `PermissionAspect`（AOP） | 登录了，但没有该权限码 |
   | **HTTP 200 + 11003** | Service `checkOwnership` | 有权限码，但**这条数据不是你的** |
   | **HTTP 200 + 11004** | Service 防自审 | 不能审核自己提交的文章 |

5. **⚠️ 一个刻意保留的行为（可以主动说，显得真读过代码）**：`checkOwnership` **没有超管短路**，而且**排在"已归档只读"双保险之前**。所以 `author` 对**别人的已归档文章**调 withdraw/rollback，报的是 **11003（不是你的）** 而不是 11011（已归档只读）。这是既定行为，不是 bug。

**可展示证据**：`aspect/PermissionAspect.java`、`ArticleServiceImpl#checkOwnership`/`checkNotSelfAudit`、`docs/S12-审核鉴权与防越权实测记录.md`、`docs/接口清单.md` §1.3。

**⚠️ 追问**："那管理员能不能改别人的文章？" → 能，管理员有 `article:manage`；但**改了会留审核流水**，且**不能审核自己的稿**（11004）。

## Q9 · 文章列表要显示"分类名""作者名"，你们的分页是怎么做的？

**一句话答**：**不用 JOIN 分页**，用"**主表分页 + 批量填充关联名称**"（方案 B），避免 `count(*)` 被 JOIN 放大。

**展开**

1. **JOIN 分页的问题**：文章与标签是**一对多**。`SELECT ... FROM article a JOIN article_tag t ...` 会让一行文章变成多行，`COUNT(*)` 就**多算了**，导致**总页数不准**（第 3 页可能点进去是空的）。要修就得加 `COUNT(DISTINCT a.id)`，SQL 变复杂且索引不一定走。
2. **方案 B**：先按主表分页（`LIMIT`），拿到本页 10 条后，再用**一次 `IN` 查询**批量取分类名与作者名，在内存里填进 VO。
3. **实测 SQL 条数**：有数据的页 **3~4 条** SQL（count + 主查询 + 分类 + 作者），越界页或空结果页 **1 条**（`continuePage()` 在 `offset >= total` 时**连主查询一起跳过**）。
4. **索引**：热点筛选条件（状态、分类、时间）建了复合索引；`EXPLAIN` 对比记录在 SQL 优化文档里。
5. **配套的防注入**：**排序字段走白名单**，不在白名单里的直接返回 **HTTP 400**；`size` 上限 **100**，超出**截断**不报错。

**可展示证据**：`docs/SQL优化记录.md`（366 行，含 `EXPLAIN` 对比）、`docs/S17-*`、列表接口实测输出。

**⚠️ 追问**："那 `size=9999` 会怎样？" → 被规范化成 **100**，返回 100 条，**不报错**（截断而非拒绝），这个是实测过的。

## Q10 · 你们项目里最难定位的一个 bug 是什么？怎么找到的？

**一句话答**：**D-09 —— 文章列表只要带时间筛选就必 400**，难的地方在于"**报 400 但代码看着没问题**"，根因是项目里有**两条互不相干的时间转换链**，口径不同。

**展开**

1. **现象**（实测原文）：
   ```
   GET /api/v1/articles?page=1&size=5&beginTime=2026-10-14&endTime=2026-10-20
   → HTTP 400
   Failed to convert property value of type 'java.lang.String' to required type
   'java.time.LocalDateTime' for property 'beginTime'
   ```
   带上时间参数必错，不带就正常。
2. **根因：两条链，两种格式**
   | 入口 | 转换器 | 只认什么格式 |
   |---|---|---|
   | `@RequestBody` 的 JSON（如排期时间） | `JacksonConfig` 注册的 `LocalDateTimeDeserializer` | `yyyy-MM-dd HH:mm:ss`（**空格**分隔） |
   | query string 绑定 DTO 属性（列表筛选时间） | Spring `DateTimeFormatterRegistrar` 的默认值 | ISO-8601（`2026-10-14T00:00:00`，**T** 分隔） |
   前端日期选择器传的是纯日期 `2026-10-14` —— **两条链都不认**，于是 400。
3. **为什么 254 个用例一个都没发现**：S17 的 `ArticlePageQueryServiceTest` 是**直接 `new CmsArticleQueryDTO()` 然后 `setBeginTime(...)`**，**绕过了 Web 参数绑定**；`PageQueryTest` 更是纯单元测试；而 **`MockMvc` 在全仓出现 0 次**。这条缺陷只存在于"HTTP 参数绑定"这一层，**恰好是当时唯一没有测试的层**。
4. **修法（两层，都是最小改动）**：
   - **后端**：**新增** `config/StringToLocalDateTimeConverter.java`，接受三种写法（`yyyy-MM-dd HH:mm:ss` / `yyyy-MM-dd HH:mm` / `yyyy-MM-dd` 补当日 `00:00:00`），**刻意不接受 ISO 的 `T`**（保持"项目只有一种日期书写法"），并在 `SpringMvcConfig#addFormatters` **全局注册**。
     为什么不给 DTO 字段加 `@DateTimeFormat`？因为要**逐字段写**，而且将来任何新增的 query 时间参数都会**重踩同一个坑**。
   - **前端**：修**右边界语义**（这是**另一个问题**）—— `dateRange` 的 setter 左边界补 `00:00:00`、右边界补 `23:59:59`。否则 `endTime=2026-10-20` 被解析成 `00:00:00`，SQL 的 `<=` 会**漏掉 20 日当天**的记录。用户选"10-14 至 10-20"的自然语义是"含 20 日全天"。
5. **验证**：7 项针对性用例（三种格式各发一次请求、ISO 的 T 被拒、垃圾值返回 400 而非 500、空串按未传处理、右边界语义的硬证据、区间倒置 400）+ **全量回归 312 / 312 全绿**。
6. **心法（这句最值钱）**：**判断一个方法有没有真的执行，最可靠的判据是日志里有没有它的 SQL（`Preparing:`）**。因为项目里很多失效是"**静默**"的 —— `@Transactional` 自调用、逻辑删除不填审计列、`updateById` 跳过 null 字段，**都是不报错、返 200，但库里没变**。

**可展示证据**：`docs/AI应用记录.md` §五（D-09 专章：现象/根因/影响面/为什么之前没发现/修复/验证六节）、`config/StringToLocalDateTimeConverter.java`、`config/SpringMvcConfig.java#addFormatters`、`docs/联调报告.md` 缺陷登记。

## Q11 · 如果数据库挂了，你们的系统会怎样？

**一句话答**：**应用能正常启动**（连接池是懒初始化的），但查库的请求会**挂很久**，而且**健康检查会误报"正常"** —— 这是我们**实测过**的，不是推测。

**展开**

1. **能启动**：`JdbcConfig#dataSource()` **刻意不调** `DruidDataSource.init()`，让连接池在**首次 `getConnection`** 时才初始化。所以数据库不可用时，Spring 容器照样启动完成（实测 `Root WebApplicationContext initialized in 3411 ms`）。
2. **第一个撞上的不是用户请求，是定时任务**：启动后约 13 秒，排期任务先报 `Communications link failure`（在 `pool-2-thread-1`，**不是 main 线程**，所以不影响启动）。
3. **不查库的接口照常**：`health/ping` 返回 200 `pong`。
4. **⚠️ 健康检查盲区（主动指出来）**：`/api/v1/system/health` 在数据库彻底不可用时**仍然报 `status: "UP"`** —— 因为它只报 JVM/OS 信息，**压根没探测数据库**。拿它判断可用性会误判。
5. **失败不是"快速失败"而是"长时间挂起"**：登录请求实测服务端耗时 **120003 ms** 才抛 `GetConnectionTimeoutException: wait millis 60001 ... creating 0, createErrorCount 569`；客户端 110 秒 / 200 秒两次都没等到响应。**并发几个就能把 Tomcat 线程占光。**
6. **日志会被刷爆**：后台创建连接线程每约 **500 ms** 打一条带完整堆栈的 ERROR；实测 8 分钟日志增长 **3.49 MB**（约 430 KB/分钟、**25 MB/小时**）。
7. **改进建议（按性价比）**：① 健康检查真探一次库（`SELECT 1`，失败报 DOWN）；② 给驱动日志单独限流/提高级别；③ `maxWait` 从 60 秒调到 3~5 秒；④ 用 `connectionErrorRetryAttempts` + `breakAfterAcquireFailure` 快速失败，或改 `@Bean(initMethod="init")` 让故障**早暴露**；⑤ 定时任务连续失败告警 + 退避。

**可展示证据**：`docs/部署记录.md` §八（完整实测数据表 + 容错建议）。

**⚠️ 追问**："那你们为什么不在启动时校验连接（`initMethod="init"`）？" → 这是**取舍**：优点是"数据库可以后启动"（演示/部署时更宽容），代价是"故障延后暴露"+ 请求挂起。**已知代价，所以写进了改进建议**，但演示场景保留原设计。

## Q12 · 手册说六表，你们建了多少张？会不会是单表开发？

**一句话答**：**建了 17 张表**（手册正文里"14 张"是笔误），四个业务域都有**跨表关联查询**，不是单表开发。

**展开**

1. **实际表数**：`sql/init.sql` 里 `CREATE TABLE` **17 条**（可现场 `grep -c`）。评分表的硬约束是"用户/角色/权限/文章/分类/日志**六表关联**"，我们是 **17 张**，超出而不是不足。
2. **跨表关联举三个**：① 文章列表要拿**分类名**与**作者名**（`cms_article` ← `cms_category` / `sys_user`）；② 文章详情要拿**标签**（`cms_article_tag` ← `cms_tag`，多对多）；③ 审核流水要关联**文章**与**审核人**（`cms_article_audit_log` ← `cms_article` / `sys_user`）。
3. **权限域是 5 张**：`sys_user` / `sys_role` / `sys_permission` / `sys_user_role` / `sys_role_permission`（**48 条角色-权限绑定**），标准 RBAC 三表 + 两张关联表。
4. **规范统一**：每表都有 `id` 主键 + **审计四字段**（`create_by`/`create_time`/`update_by`/`update_time`）+ **`deleted`** 逻辑删除位；9 个唯一键都把 `deleted` 作末列；字符集统一 `utf8mb4` / `utf8mb4_general_ci`；引擎 InnoDB。
5. **⚠️ 如实说明**：`sys_apply_approval`（授权审批）等表**有结构有种子数据、暂无对应接口**，属成员C的域；这也是自测表里主动登记的失分点。

**可展示证据**：`sql/init.sql`、`docs/数据库设计.md`（442 行，逐表用途与设计取舍）、`docs/结题报告.md` §3.3。

## 附：三个"万能兜底"回答

| 情况 | 怎么答 |
|---|---|
| 问到一个**不属于我的域**的细节 | "这块是成员X负责。我知道的是表结构是……，口径以 `sys_permission`/`init.sql` 为准；具体实现细节我请他补充。" **不编。** |
| 问到确实**没做**的功能 | "**没做**。" 然后立刻给：① 为什么没做（范围/优先级）② 补的话怎么做（表已就绪？几步？）③ 现在能拿出什么（表结构/权限码/自测表里的登记）。**有准备的"没做"比含糊的"做了"得分高。** |
| 问到代码细节答不上来 | "这个我现场看一下代码。" 然后打开文件读注释 —— **注释是我们自己写的，读得出来。** |
