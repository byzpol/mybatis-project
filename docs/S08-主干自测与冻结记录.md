### 两项的补充说明（容易被误判）

**第 7 项为什么是 HTTP 200 而不是 500？**
业务码 `11xxx`（文章域）**不会**回退成 HTTP 状态码 —— 这是 `GlobalExceptionHandler#writeStatus` 的设计：
只有 `100~599` 范围内的码才同步到 HTTP 状态码，`11xxx` 这类业务码保留在响应体 `code` 字段里。
手册要求"返回 11001 而不是 500"，正是这个意思：**客户端拿到的是明确的业务原因，不是笼统的服务器错误**。

**第 11 项为什么不能只看 `create_time` 是否非空？**
`sys_oper_log` 的 DDL 里 `create_time`/`update_time` 是 `NOT NULL DEFAULT CURRENT_TIMESTAMP`
（实测 `sql/init.sql` 第 358~360 行确认），**数据库会自己兜底填上** ——
即使 `MetaObjectHandler` 完全没生效，这两个字段照样非空。
真正能证明填充生效的硬指标是 `create_by` / `update_by`（DDL 里是 `NULL DEFAULT NULL`）。
本次实测 `createBy=4, updateBy=4`（4 = admin 的 userId），说明填充确实跑了。

## 四、本步发现并修复的两个真实缺陷

> 这两个都是"编译能过、启动不报错、平时看不出"的类型，
> 正是靠这一步的端到端自测才暴露出来 —— 这也是 S08 存在的意义。

### 缺陷 1：404 返回的是 Tomcat 错误页，不是统一 Result

- **现象**：`GET /api/v1/nonexistent-xyz` 返回 Tomcat 的 HTML 白底页
  （`HTTP状态 404 - 未找到`），前端拦截器按 JSON 解析会直接抛异常。
- **根因**：`GlobalExceptionHandler` 里明明写了 `handleNoHandlerFound` 方法，
  但 `DispatcherServlet` 的 `throwExceptionIfNoHandlerFound` **默认是 false** ——
  找不到 Handler 时不抛异常，直接让容器返回默认 404 页面。
  于是那个 handler 方法**是死代码，永远不执行**。
- **修复**：覆写 `ServletContainersInitConfig#createDispatcherServlet`，
  手动 `setThrowExceptionIfNoHandlerFound(true)`。
- **⚠️ 踩到的 API 幻觉（已实测纠正）**：
  我最初写的 `registration.setInitParameter(DispatcherServlet.THROW_EXCEPTION_IF_NO_HANDLER_FOUND, "true")` **有两处错**：
  1. Spring 5.3 **没有** `THROW_EXCEPTION_IF_NO_HANDLER_FOUND` 这个常量
     （`javap` 实测确认：常量清单里没有它）
  2. 更关键：**这个属性根本不从 Servlet init-param 读取**
     （Spring Boot 是在 `DispatcherServletRegistrationBean` 里主动调 setter 设的）
  
  若照原样写下去，会**编译失败**（常量不存在）；就算用字符串字面量绕过编译，
  开关也**不会生效** —— 又一个静默失效。正确做法只有"创建时直接调 setter"。

### 缺陷 2：JDBC 连接串与实际模板漂移，MySQL 重启后连接池起不来

- **现象**：登录接口返回 500，`logs/cms-error.log` 报
  `java.sql.SQLNonTransientConnectionException: Public Key Retrieval is not allowed`，
  Druid 初始化失败，**所有**数据库操作都挂。
- **诡异之处**：S07 那次测试（35 小时前）同样的代码、同样的配置，一切正常。
- **根因**（查证链条）：
  1. `SELECT user,host,plugin FROM mysql.user WHERE user='root'` → `caching_sha2_password`
  2. `SHOW GLOBAL STATUS LIKE 'Uptime'` → **48002 秒 ≈ 13.3 小时**，即 MySQL 在 10-09 23:15 左右重启过
  3. `caching_sha2_password` 的密码在**服务端有缓存**：缓存命中走快速认证；
     **服务重启后缓存被清空**，首次连接要走完整认证
  4. 完整认证在 `useSSL=false` 下需要向服务端索取 RSA 公钥，
     而驱动默认禁止（`allowPublicKeyRetrieval=false`）→ 直接拒连
  5. 本机 `db.properties` 的 URL 是个**简化版**，缺了 `allowPublicKeyRetrieval=true`
     等三个参数；而入库的 `db.properties.example` **本来就是对的** ——
     **实际配置与模板漂移**，平时不重启 MySQL 就一直不暴露
- **修复**：把 `db.properties` 的 URL 与 `db.properties.example` 完全对齐
  （补 `useUnicode=true&characterEncoding=utf8`、`allowPublicKeyRetrieval=true`、`rewriteBatchedStatements=true`）。
- **安全取舍说明**：`allowPublicKeyRetrieval=true` 意味着"允许客户端向服务端索取公钥"，
  理论上给了中间人替换公钥的机会。本项目是 localhost 单机 + 课程作业，
  这是业界通行做法；生产环境应改为启用 TLS（`useSSL=true&requireSSL=true`）替代。
  这条取舍写进注释，避免被当成"随手加的开关"。

> ⚠️ 顺带确认：Druid 连接池参数在 `db.properties` 里是缺失的，
> 但 `JdbcConfig` 用的是 `@Value("${druid.initialSize:5}")` 这种**带默认值**的写法，
> 所以缺了也能正常跑（走默认值 5/5/20）。**不是 bug**，但建议后续补齐以便调优。

### 6.2 冻结含义

从此刻起，主干代码（`config / common / base / annotation / aspect / interceptor / util`）
**只允许新增方法，不允许修改已有方法的签名**。

理由：B/C/D 三人的入户线都要 import 主干（`Result` / `PageQuery` / `ErrorCode` /
`BaseEntity` / `BaseService` / `@RequirePermission` / `@OperLog` …）。
改一个签名，三边同时编译失败。若确实必须改，走 §1.4 的流程：
先在群里说明 + 给出迁移方案，全员同步后再改。

**允许直接改的**：主干内部实现（不改签名）、bug 修复、新增方法/新增类。
