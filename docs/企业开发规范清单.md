### "工业全套但不必查太严"的落地说明

用户明确要求"按工业标准上全套，但是可以查的不是特别严，一些意义不大的步骤也可以省略"。因此本清单分两档：

**A 档（硬性，必须做到，能被检查发现）—— 共 40 条**
标 **【A】**。这些是"做了就是企业级、不做就是学生作业"的分水岭，且**都能被工具或人眼快速查出来**。

**B 档（软性，尽力做到，做不到要写理由）—— 共 16 条**
标 **【B】**。这些是正规企业做但课程项目收益不高的。**允许不做，但必须在 `docs/规范豁免说明.md` 里写清"为什么不做 + 替代做法"**，这本身就是企业级的做法（企业里叫"技术债登记"）。

### 被明确省略的做法（不做，且已论证）

| 省略项 | 替代做法 | 理由 |
|---|---|---|
| Flyway / Liquibase 数据库版本管理 | `init.sql` 做成**幂等可重复执行** | 课程是单库单环境，迁移工具的价值（多环境一致性）用不上；幂等脚本在演示时"随时重置"更方便 |
| 多环境 profile（dev/test/uat/prod） | 只留 `dev` + `prod` 两份配置 | 无真实测试/预发环境，多 profile 是空壳 |
| JWT 无状态鉴权 | HttpSession + `LoginInterceptor` | 单机部署不涉及分布式会话；Session 在答辩时"看得见、好演示" |
| Redis 缓存 / MQ / 分布式锁 | 数据库直查 + 事务 | 无并发压力；引入后反而增加答辩时的环境依赖风险 |
| Docker / K8s / CI-CD | 本地 Tomcat 部署 + 文档化步骤 | 课程不考察运维，投入产出比低 |
| Swagger / Knife4j | ApiFox 用例集 + `docs/接口契约.md` | 指导书指定用 ApiFox；再引一套 Swagger 会让"契约"有两个真相来源 |
| 单元测试覆盖率门槛（如 ≥70%） | 核心逻辑（状态机 + 权限）100% 覆盖，其余尽力 | 覆盖率门槛会逼人写无意义断言；聚焦核心逻辑的测试更有价值 |
| Checkstyle / SpotBugs 门禁 | IDEA 自带检查 + 人工 Review 清单 | 工具接入成本高，且本清单已覆盖其检查项 |
| 灰度发布 / 限流 / 熔断 | 无 | 单机课程项目无流量概念 |
| 国际化 i18n | 中文硬编码 | 无多语言需求 |

## 维度一 · 架构与分层纪律（10 条）

### 【A】1-1 严格遵循主干 + 入户线结构

`config / common / base / annotation / aspect / interceptor / util` 为**主干**，由成员A 一次性建好并冻结；`entity / mapper / service / service.impl / dto / vo / controller` 为**入户线**，各业务域自建。

**判定**：`com.lab.cms.common.*`、`com.lab.cms.base.*` 下的文件，Git blame 中**非成员A 的提交记录数 = 0**。

### 【A】1-2 禁止复制主干代码

任何人不得把 `Result`、`PageResult`、`ErrorCode`、`ArticleStateMachine` 等复制到自己包里改。

**判定**：搜 `class Result` 全工程只应有 1 个（`common/result/Result.java`）；搜 `class PageResult` 只应有 1 个。**若发现第 2 个，本项 0 分。**

### 【A】1-3 分层调用方向单向

`Controller → Service → Mapper`。禁止反向调用，禁止跨层（Controller 直接调 Mapper）。

**判定**：Controller 里搜 `Mapper`，只允许出现在 `@RequiredArgsConstructor` 注入的 `xxxService` 字段中；**出现 `XxxMapper` 类型的字段即违规**。

### 【A】1-4 Controller 不含业务逻辑

Controller 方法的职责只有四件事：接参、校验、调 Service、包 `Result`。

**判定**：Controller 方法体行数（不含注解与空行）**≤ 5 行**。超过即为逻辑外溢。

### 【A】1-5 Service 接口与实现分离

`service` 包放接口，`service.impl` 放实现类，实现类命名 `XxxServiceImpl implements XxxService`。

**判定**：`service` 包下无 `@Service` 注解的类（即无实现类混入）。

### 【A】1-6 Entity / DTO / VO 三类对象严格分工

| 类型 | 用途 | 位置 |
|---|---|---|
| Entity | 对应数据库表 | `entity` |
| DTO | Controller 入参 | `dto` |
| VO | Controller 出参 | `vo` |

**判定**：Controller 的方法签名中**不出现 Entity 类型**（入参和返回值都算）。

### 【A】1-7 统一 URL 前缀与命名

一律 `/api/v1/`；资源复数名词；层级 ≤3；状态变更用子资源 + POST。

**判定**：对照 `docs/接口契约.md` §1.3 逐条核对；用正则 `@(Get|Post|Put|Delete)Mapping\("(?![/{])` 搜是否有不合规 URL。

### 【A】1-8 统一返回体

所有 Controller 返回 `Result<T>` 或 `Result<PageResult<T>>`。

**判定**：搜 `public Result` 覆盖全部 Controller 方法；**搜不到裸 `public List<` / `public Map<` / `public XxxVO ` 直接返回**。

### 【B】1-9 单个类不超过 500 行

超过则考虑拆分（Service 可用「按业务动作拆子 Service」或「抽出 StateMachine / Validator / Converter」）。

**判定**：`wc -l` 统计 `src/main/java` 下所有 `.java`，超 500 行的列出并逐个说明为何不拆。

### 【B】1-10 单个方法不超过 80 行

超过则抽出私有方法。

**判定**：IDEA 的 Code → Analyze Code 或人工抽查最长的 5 个方法。

## 维度二 · 编码与命名规范（10 条）

### 【A】2-1 命名规则统一

| 元素 | 规则 | 例 |
|---|---|---|
| 包 | 全小写，点分隔，无下划线 | `com.lab.cms.common.result` |
| 类 | 大驼峰 | `ArticleServiceImpl` |
| 接口 | 大驼峰（**不加 `I` 前缀**） | `ArticleService` |
| 方法 | 小驼峰，动词开头 | `getArticleDetail`、`submitForAudit` |
| 常量 | 全大写下划线 | `MAX_SIZE`、`ROLE_ADMIN` |
| 变量 | 小驼峰，不用拼音、不用单字母（循环变量 `i/j` 除外） | `articleList` 而非 `wzList` |
| 布尔 | `is` / `has` / `can` 开头 | `isTop`、`hasPermission`、`canTransfer` |
| 数据库表 | 小写下划线，模块前缀 | `cms_article`、`sys_user` |
| 数据库字段 | 小写下划线 | `create_time`、`author_id` |

**判定**：搜全小写类名、搜带 `I` 前缀的接口、搜拼音变量（`wenzhang`、`yonghu` 等）。

### 【A】2-2 禁止魔法值

状态码、状态值、角色码、权限码、URL 路径等，一律用常量或枚举，不允许裸写字面量。

**判定**：搜 `status == 1`、`status == 5`、`"ROLE_ADMIN"`、`"200"` 等字面量。**允许的例外**：`cms_article.status` 的枚举定义处（`ArticleStatus` 里）、`init.sql`。

**反例（必须改）**

```java
if (article.getStatus() == 5) {          // ✗ 5 是什么意思？
    article.setStatus(7);                 // ✗ 7 又是什么？
}

// 正确
if (ArticleStatus.of(article.getStatus()) == ArticleStatus.PUBLISHED) {
    article.setStatus(ArticleStateMachine.transfer(
            ArticleStatus.PUBLISHED, ArticleAction.WITHDRAW).getCode());
}
```

### 【A】2-3 禁止状态判断散落

所有文章状态流转必须走 `ArticleStateMachine`，禁止在 Service/Controller 里写 `if (status == ...)` 表达状态迁移。

**判定**：搜 `getStatus() ==`，若出现在 Service 中用于"判断能否执行动作"，即为违规。允许的用途只有"展示判断"（如 `status == DRAFT` 决定是否显示删除按钮）。

### 【A】2-4 禁止在循环中查数据库

**判定**：搜 `for (` 后 10 行内是否出现 `Mapper.` 调用。

**反例**

```java
// ✗ N+1 查询
for (Article a : articleList) {
    Category c = categoryMapper.selectById(a.getCategoryId());   // 循环内查库
    a.setCategoryName(c.getName());
}

// 正确：批量查 + 内存组装
List<Long> categoryIds = articleList.stream()
        .map(Article::getCategoryId).distinct().collect(Collectors.toList());
Map<Long, String> categoryNameMap = categoryMapper.selectBatchIds(categoryIds).stream()
        .collect(Collectors.toMap(Category::getId, Category::getName));
articleList.forEach(a -> a.setCategoryName(categoryNameMap.get(a.getCategoryId())));
```

### 【A】2-5 集合返回不为 null

方法返回集合时，返回空集合而不是 `null`。

**判定**：搜 `return null;` 出现在返回类型为 `List`/`Set`/`Map` 的方法中。

### 【A】2-6 字符串比较用 `equals`，常量在前

**判定**：搜 `== "` 与 `.equals(` 的调用方向（常量写前面避免 NPE）。

### 【A】2-7 判空用工具类，不用裸 `!= null` 链

用 `Objects.isNull` / `Objects.nonNull` / `StringUtils.hasText` / `CollectionUtils.isEmpty`。

**判定**：抽查 `!= null && !.isEmpty()` 这类复合判断。

### 【A】2-8 日志用 SLF4J，不用 `System.out.println`；用占位符不用字符串拼接

```java
// ✗
log.info("审核文章 id=" + id + ", action=" + action);
// ✓
log.info("审核文章 id={}, action={}", id, action);
```

**判定**：搜 `System.out.print` **应为 0 处**；搜 `log.info("` 后的 `+` 拼接。

### 【A】2-9 注释规范：类头有 Javadoc，复杂方法有说明

| 位置 | 要求 |
|---|---|
| 类 | 必须有 Javadoc，说明这个类是干什么的、属于哪个域 |
| public 方法 | 必须有 Javadoc，说明参数、返回值、可能抛的业务异常 |
| 复杂逻辑（状态机、权限校验、SQL 优化） | 必须有行内注释解释"为什么" |
| 简单 getter/setter | 不需要注释 |

**判定**：抽查 5 个 Service 实现类的 public 方法，注释覆盖率应 100%。

### 【B】2-10 代码格式统一（缩进 4 空格、行宽 ≤120）

**判定**：IDEA 的 `Ctrl+Alt+L` 格式化后 `git diff` 应无变化。若有变化说明未格式化。

## 维度三 · 健壮性与安全（11 条）

### 【A】3-1 所有入参做校验（JSR-303）

DTO 字段必须带校验注解；Controller 参数必须带 `@Valid`。

**判定**：搜 `@RequestBody` **后紧跟的类名**，其类定义中必须有至少一个 `javax.validation` 注解（纯查询 DTO 除外）；搜 `@Valid` 数量与 `@RequestBody` 数量应匹配。

### 【A】3-2 全局异常处理器兜底

`@RestControllerAdvice` 统一处理：`BusinessException`、`MethodArgumentNotValidException`、`BindException`、`HttpRequestMethodNotSupportedException`、`HttpMediaTypeNotSupportedException`、`Exception`（兜底）。

**判定**：`GlobalExceptionHandler` 中存在这 6 个 `@ExceptionHandler` 方法。

### 【A】3-3 异常不吞不裸抛

| 反例 | 正确 |
|---|---|
| `catch (Exception e) { }` 空 catch | 至少 `log.error("...", e)` |
| `catch (Exception e) { e.printStackTrace(); }` | 用日志框架 |
| `throw new RuntimeException("文章不存在")` | `throw new BusinessException(ErrorCode.ARTICLE_NOT_FOUND)` |
| `catch (Exception e) { throw new BusinessException(...); }` 丢失堆栈 | `log.error` 记录原始异常后再抛业务异常 |

**判定**：搜 `catch (Exception e) {\n\s*}`（空 catch）；搜 `printStackTrace`；搜 `throw new RuntimeException`。

### 【A】3-4 写操作加事务，且 `rollbackFor = Exception.class`

**判定**：搜 Service 实现类中的写方法（有 `insert`/`update`/`delete` 调用的 public 方法），必须有 `@Transactional(rollbackFor = Exception.class)`。

> ⚠️ **不加 `rollbackFor = Exception.class` 是经典坑**：Spring 默认只对 `RuntimeException` 回滚，受检异常不回滚。

### 【A】3-5 垂直越权防护：`@RequirePermission`

每个需要权限的接口都必须标 `@RequirePermission("资源:动作")`。

**判定**：对照 `docs/接口契约.md` §1.3 的权限码列，逐个核对；搜 Controller 中的写方法，未标 `@RequirePermission` 的即为违规（登录、登出、`/auth/me` 除外）。

### 【A】3-6 水平越权防护：Service 层 `checkOwnership`

"只能操作自己的数据"必须在 Service 层显式校验，**不能只靠前端不显示按钮**。

**判定**：搜涉及 `authorId` / `userId` 的操作（文章提交、草稿编辑、删除），必须有 `checkOwnership` 或等价的 `authorId.equals(currentUserId)` 校验。

**这是本项目最容易失分的地方**：投稿人 A 用浏览器改一下 URL 里的 id，就能提交投稿人 B 的文章 —— 前端怎么藏按钮都没用。

### 【A】3-7 SQL 全部参数化，禁止字符串拼接

MyBatis 里用 `#{}`，**不用 `${}`**。排序字段是唯一必须用 `${}` 的地方，必须走白名单。

**判定**：搜 `${` **应只有 3 处以内**（排序字段、其他确实需要动态列名的地方），且每处都有白名单校验代码在同一文件内。

### 【A】3-8 密码不落明文、不出响应体

存储用 BCrypt；VO 中不含 `password` 字段；日志中不打印密码。

**判定**：搜 `password` 出现在 `vo` 包；搜 `log.*password`。

### 【A】3-9 逻辑删除显式声明

MP 实体上的 `@TableLogic` 必须写成 `@TableLogic(value = "0", delval = "1")`。

**判定**：搜 `@TableLogic` 不带参数的即为违规。

> **理由（实验一实测踩过的坑）**：MP 的 `@TableLogic` 默认 `value="0"` / `delval="1"`，语义是"0 = 未删 / 1 = 已删"。但它与"1 = 有效 / 0 = 无效"这类业务语义相反，不显式声明就会被默认值语义悄悄影响。显式写出，读代码的人一眼看懂。

### 【B】3-10 关键操作幂等

提交审核、发布、审核这类接口，重复调用不应产生副作用（第二次调用抛 `ARTICLE_STATUS_ILLEGAL` 而不是再插一条流水）。

**判定**：手动连续调用两次 `POST /articles/{id}/submit`，第二次应返回业务异常而非成功。

### 【B】3-11 敏感字段脱敏

用户列表里的手机号、邮箱做脱敏展示（`138****8888`）。

**判定**：`UserVO` 中手机号字段的值经过脱敏方法处理。

## 维度四 · 数据层规范（10 条）

### 【A】4-1 表名/字段名小写下划线，模块前缀区分

`sys_*` 权限与系统、`cms_*` 内容业务。

**判定**：`init.sql` 中所有表名符合 `^(sys|cms)_[a-z_]+$`。

### 【A】4-2 每表必带审计四字段 + `deleted`

`create_by` / `create_time` / `update_by` / `update_time` / `deleted`。

**判定**：查 `information_schema.COLUMNS`，每张表都应包含这 5 个列名。**已实测：17 张表全部通过**。

### 【A】4-3 主键统一 `id BIGINT UNSIGNED AUTO_INCREMENT`

**判定**：`information_schema.COLUMNS` 中每张表的 `id` 列类型为 `bigint unsigned` 且 `EXTRA='auto_increment'`。

### 【A】4-4 不使用物理外键

**判定**：`SELECT COUNT(*) FROM information_schema.TABLE_CONSTRAINTS WHERE TABLE_SCHEMA='cms_db' AND CONSTRAINT_TYPE='FOREIGN KEY'` 结果应为 **0**。**已实测：0**。

### 【A】4-5 所有关联列建索引

每个逻辑外键列（`*_id`）都必须有索引。

**判定**：遍历每张表的 `*_id` 列，在 `information_schema.STATISTICS` 中能找到以该列开头的索引（`SEQ_IN_INDEX=1` 或作为联合索引的非首位成员）。**已实测：全部通过**。

### 【A】4-6 每表每字段有 COMMENT

**判定**：查 `information_schema.COLUMNS` 中 `COLUMN_COMMENT=''` 的记录应为 0。**已实测：17 张表全部有表注释**。

### 【A】4-7 状态字段用 TINYINT + 注释枚举取值

**判定**：`cms_article.status` 的 `COLUMN_COMMENT` 中列出 0~9 的含义，且与 `ArticleStatus` 枚举严格一致。

### 【A】4-8 枚举值与代码枚举一一对应

数据库注释中的状态编号 ↔ Java 枚举的 `code` 字段，必须完全一致，不允许"数据库从 1 开始、代码从 0 开始"。

**判定**：写一个 JUnit 测试遍历 `ArticleStatus.values()`，逐个断言 `ArticleStatus.of(s.getCode()) == s`。**这个测试没写，本项不算完成**。

### 【A】4-9 脚本可重复执行

`init.sql` 连跑两遍不报错，第二遍结果与第一遍一致。

**判定**：连续执行两次，比对两次的表数量、各表行数输出。**已实测：两次一致（17 表 / 5 用户 / 20 文章 / 10 状态全覆盖）**。

### 【B】4-10 大文本与检索分离

正文用 `LONGTEXT`；需要检索的字段复制到 `cms_article_index`。

**判定**：`cms_article_index` 表存在且字段设计支持按标题/分类/热度查询。

## 维度五 · 工程化与协作（8 条）

### 【A】5-1 `.gitignore` 完整

必须包含：`target/`、`.idea/`、`*.iml`、`*.log`、`logs/`、`db.properties`、`node_modules/`、`frontend/dist/`、`.DS_Store`。

**判定**：`git status` 输出中不出现上述任何文件/目录。

### 【A】5-2 凭据不入库

数据库账号密码放 `db.properties`，该文件**永不 commit**。仓库里放 `db.properties.example`。

**判定**：`git log --all --full-history -- db.properties` 无输出；搜仓库无明文密码字符串。

> **评分标准明确写入**："硬编码真实账号口令"在维度三计 0 分。这是红线。

### 【A】5-3 Commit message 规约

格式：`<type>(<scope>): <subject>`

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 文档 |
| `style` | 格式调整（不影响逻辑） |
| `refactor` | 重构 |
| `test` | 测试 |
| `chore` | 构建/依赖/配置 |

**示例**：`feat(article): 实现文章提交初审与状态机校验`

**判定**：`git log --oneline` 抽查，反例：`update`、`修改`、`111`、`.`。

> ⚠️ **本项目实际采用的写法与上面这条不同**，以 `docs/Git提交规约.md` 第二节为准：
> 首行写成 `Sxx 这步做了什么（日期，第 N 天）`，正文像工作记录一样说清
> "新增了什么 / 为什么这么选 / 踩了什么坑"。
>
> 原因是本项目的评审方式是"拿着计划表对着提交记录一条条看，核对每天干到哪一步"，
> 语义化前缀（`feat`/`fix`/`chore`）对不上计划表里的 S01~S23 / F01~F06 编号，
> 反而要多绕一层翻译。**两者取其一即可，本清单保留上面的通用写法供参考。**
>
> 这条**不违反**本条的判定意图：判定要排除的是 `update`、`修改`、`111`、`.` 这类
> 无信息量的提交信息，而 `S06 参数校验基座、MP 插件与审计填充（10-14，第 8 天）`
> 的信息量明显更高。

### 【A】5-4 主干冻结纪律

第 2 周 D10（2026-10-16）打 tag `trunk-v1.0`；之后主干**只许加方法，不许改签名**。

**判定**：`git tag` 中存在 `trunk-v1.0`；`git diff trunk-v1.0 -- src/main/java/com/lab/cms/common/` 中**没有删除或修改既有方法签名的行**（只能是新增）。

### 【A】5-5 前端工程化

Vue 3 + Vite；目录划分 `api/`（接口层）、`views/`（页面）、`components/`（组件）、`router/`、`store/`、`utils/`。

**判定**：`frontend/src` 下存在这 6 个目录；`main.js` 中正确挂载 router 与 pinia。

### 【A】5-6 前端接口层集中管理

**所有** HTTP 调用写在 `src/api/` 下的模块文件里，页面组件不直接 `axios.get(...)`。

**判定**：搜 `src/views/` 下的 `axios` **应为 0 处**；应只有 `import { xxxApi } from '@/api/xxx'`。

> 这条与后端的"主干 + 入户线"是同一思路：**在各自的层里做集中管理**。

### 【B】5-7 依赖版本锁定

`pom.xml` 中所有依赖显式写版本号；不用 `LATEST` / `RELEASE`。

**判定**：搜 `pom.xml` 中的 `<version>LATEST</version>` 与 `<version>RELEASE</version>`。

### 【B】5-8 分支策略

主干分支 `main`；各自开发用 `feat/xxx` 分支；合并前自测通过。

**判定**：`git branch -a` 中存在各人的 feature 分支记录。

## 维度六 · 可观测性与文档（7 条）

### 【A】6-1 日志分级合理

| 级别 | 用途 |
|---|---|
| ERROR | 系统异常、需要人工介入的问题（一定是"出事了"） |
| WARN | 业务异常（如状态非法、越权拦截）—— 这是**预期内**的失败 |
| INFO | 关键业务动作（提交、审核、发布）、接口出入参摘要 |
| DEBUG | 开发期调试细节，生产关闭 |

**判定**：搜 `log.error` 是否用于业务异常（如"文章不存在"用 error 是过度报警）；搜 `log.info` 是否打印了完整大对象（如整个 `Article` 含 `LONGTEXT` 正文）。

### 【A】6-2 操作日志切面覆盖所有写操作

所有 `@OperLog` 标注的接口，正确写入 `sys_oper_log`（含操作人、模块、类型、描述、耗时、成功/失败）。

**判定**：手动调用一个写接口后，查 `SELECT * FROM sys_oper_log ORDER BY id DESC LIMIT 1` 应有对应记录且字段完整。

### 【A】6-3 登录日志记录成功与失败

登录成功写 1 条、登录失败也写 1 条（含失败原因）。

**判定**：用错误密码登录一次，查 `sys_login_log` 应有 `login_status=0` 的记录。

### 【A】6-4 全局异常有堆栈

兜底的 `Exception` 处理器中必须 `log.error("系统异常", e)`（带异常对象，不是只打 message）。

**判定**：看 `GlobalExceptionHandler` 中兜底方法的实现。

### 【A】6-5 接口清单文档

`docs/接口契约.md` 完整列出所有接口的 URL、方法、入参、出参、权限码。

**判定**：抽查 3 个实际实现的接口，与文档描述一致。

### 【A】6-6 ApiFox 用例集

所有接口在 ApiFox 中有用例，能一键运行。

**判定**：ApiFox 中的接口数量 = 实际 Controller 方法数量。

### 【B】6-7 AI 使用痕迹记录

记录 AI 在哪些环节参与了、生成了什么、人工改了什么（这是评分表"AI 合理应用"的直接依据）。

**判定**：`docs/AI使用记录.md` 存在，且记录了至少 5 条"AI 建议 → 人工判断/修改"的具体案例。

> 指导书原文要求："保留提交历史与 AI 交互痕迹"。**评委要看的是"你怎么用 AI 的"，不是"你没用 AI"**。记录"AI 生成的代码有什么问题、我怎么改的"，比单纯贴对话截图有价值得多。
