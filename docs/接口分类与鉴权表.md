# 接口分类与鉴权表（文章模块）

> S12 产出。**这张表是成员B/C/D 写前端与自查时的对照基准**，也是 S13/S14/S15 继续加接口时的模板。
> 每一条都有实测依据（JUnit `ApiPermissionCoverageTest` + `ArticleOwnershipAuthzTest` + `target/s12-live.sh`），
> 不是设计草稿。最后更新：S17（10-31）—— 第 8 行"分页检索"已实现，补 §二.12。

## 〇、先分清两类越权（这是全表的分类依据）

| | 垂直越权（功能级） | 水平越权（数据级） |
|---|---|---|
| 是什么 | 低权限角色调用了高权限接口 | 同角色用户操作了别人的数据 |
| 例子 | 投稿人调审核接口 | 投稿人 A 改投稿人 B 的草稿 |
| **在哪拦** | **Controller 方法上的 `@RequirePermission`**，由成员C 的切面统一拦截 | **Service 里**，因为切面只看得到权限标识、看不到数据归属 |
| Service 要不要重复判断 | **不要**。重复判断会造成"双重拦截、报错信息混乱" | **必须**，这是唯一的拦截点 |
| 返回 | **403** `没有该操作权限，需要：xxx` | **11003 / 11004**（HTTP 仍 200） |
| 在哪验 | 只能真机（JUnit 直接调 Service 会绕过切面） | JUnit 可测（也可真机复验） |

**⚠️ 一个反直觉的实测结论：同一句"审自己的稿"，对不同角色返回的码不同。**

```
投稿人审自己的稿   → 403   没有该操作权限，需要：article:audit   ← 垂直层先拦，根本进不到业务逻辑
编辑  审自己创建的稿 → 11004 不能审核自己创建的文章               ← 有权限、又是作者，才看到水平层
```

这不是 bug，是**两层拦截的先后顺序可观测**。做测试用例时若一律期望 11004，会得到一个假的 FAIL。

## 二、四个需要解释的分类决定

### 2.1 「撤回」只给作者本人，「下架」才给主编 —— 两个动作不要合并

手册 S12 问的是"谁能撤回？只有作者本人，还是主编也能撤？"。
**本项目的答案：撤回只有作者本人；主编要撤别人的稿，用"下架"。**

理由有两条，都是硬的：

1. **状态机已经把它们分开了。**
   `PUBLISHED(5) + WITHDRAW → WITHDRAWN(7)`（曾经发布过、作者主动收回，之后还能再发）
   `PUBLISHED(5) + OFFLINE  → OFFLINE(8)`（被强制拿下来，语义是运营处置）。
   两条不同的出边、两个不同的目标状态 —— 如果都叫"撤回"，用户分不清"我自己拿下来了"
   和"我被下架了"。
2. **冻结的 Service 签名里没有角色。**
   `void withdraw(Long id, Long operatorId)` 只传 id，不传 `LoginUser`。
   要表达"作者 或 主编"，Service 就必须知道角色，那就得改签名（改契约）。
   而"作者走 withdraw、主编走 offline"两句话说清了同一件事，且不需要动契约。
   （这与 §三 里"`checkOwnership` 没有超管短路"是同一个取舍的两面。）

> 由此，前端"撤回"按钮应只在"我把自己的已发布文章收回来"时显示（`article:withdraw` + 归属）。
> 这与 F06 遗留的 `articleActions.js` 归属按钮问题一并处理（见 §五）。

### 2.2 「下架 / 归档」是运营动作，**不做**归属校验

`article:manage` 这个权限码库里只给了 `ROLE_CHIEF(12)` 与 `ROLE_ADMIN(20)`
（编辑及以上才有）。作者没有它 —— **权限层已经表达了"不是你的活儿"**。
再叠加一层归属校验是多余的，而且会把"主编要下架任何人写的违规内容"这个正当场景挡住。

⚠️ 这与 §2.1 的"撤回"正好相反：撤回是**作者对自己内容**的动作，下架是**运营对他人的内容**的动作。
判据是"这个动作的主语是谁"，不是"这个动作听起来像什么"。

### 2.3 ⚠️ 写接口必须有 `@OperLog`，读接口必须**没有**

这条已被 `ApiPermissionCoverageTest#testWriteEndpointsLogAndReadEndpointsDoNot` 钉住，双向断言：

- 写接口少了 `@OperLog` → 谁改了数据无法追责；
- 读接口多了 `@OperLog` → 列表页一点就是几十条，`sys_oper_log` 迅速膨胀到不可用。

实测：文章模块 5 个写接口都有，2 个读接口都没有。
另外新建/修改草稿两个接口显式写了 `saveParams = false`（参数含 LONGTEXT 正文）。

### 2.4 批量提交：逐条判定，**不做整批拒绝**

`POST /articles/batch-submit` 里混进别人的文章时，**自己的成功、别人的记入失败清单**，
HTTP 仍是 200，前端必须读 `data.failList`。

为什么不做整批拒绝：用户勾了 5 篇自己的 + 1 篇别人的，整批拒绝会让他以为一篇都提交不了。
安全性由"**别人的那篇状态确实没变**"保证，而不是靠"整批拒绝"——
这条已被 `ArticleOwnershipAuthzTest#testCase14` 断言（`b1` 状态仍是 DRAFT）。

### 2.5 只读接口（详情 / 流水 / 版本列表）刻意**不设**归属限制

后台是协作场景：编辑/主编必须能打开**任何**一篇文章才能审、才能核对。
被限制的是"改"，不是"看"。写这条是为了留下"我们想过这件事"的证据 ——
否则将来有人看到"详情没做归属校验"会以为是漏洞。
（`ArticleOwnershipAuthzTest#testCase13` 断言 B 能读 A 的详情与流水。）

### 2.6 「发布 / 排期发布」是运营动作：**只给主编+管理员，不做归属校验**（S13 补记）

S13 实现这两个接口时，把这条从"计划"变成了"有实测依据的结论"：

- **为什么不给作者**：`article:publish` 在库表里只授予 `ROLE_CHIEF(12)` 与 `ROLE_ADMIN(20)`。
  作者能写、能提交，但"什么时候放出去"是主编的职能。
- **为什么不校验归属**：如果加了 `checkOwnership`，**主编就永远发布不了作者提交的稿** ——
  整条"作者写稿 → 编辑初审 → 主编终审 → 发布"的链路会断在最后一步，而那一步恰恰是主编干的。
  功能权限（能不能发布）与数据归属（这是谁的稿）是正交的两个维度。
- **与"撤回"的对照**（不要互相套用）：撤回是**作者把自己交出去的东西收回来**，
  所以 S14 的 `withdraw` **要**校验归属；发布是把**别人的**东西放出去，所以不校验。

⚠️ 真机实测：投稿人 / 编辑调发布 → **403**（`没有该操作权限，需要：article:publish`）；
主编 / 管理员 → 进得去（对不存在的 id 报 11001）。见 `docs/S13-发布与排期实测记录.md`。

### 2.7 ⚠️ 撤回的**校验顺序**：归属校验先于"已归档只读"（S14 补记）

`withdraw` 的实现是"先 `checkOwnership` → 再判 `ARCHIVED` → 再走状态机"。
这个顺序不是随手写的，它产生一个**看起来像 bug、其实是设计**的结果：

> 用**非作者**身份去撤回一篇**已归档**的文章 → 得到 **11003**（`只能操作自己创建的文章`），
> 而不是 **11011**（`已归档的文章不可修改`）。

为什么必须这样：撤回是唯一**要求归属**的生命周期动作。如果先判状态、后判归属，
那么"非作者能不能撤"这个问题会被"状态是否允许"掩盖 —— 一旦文章恰好是已归档，
攻击者就能通过错误码反推"这篇是不是归档了"，而作者身份是否匹配反而没被拒绝。
把归属放前面，"不是你的东西"永远比"这东西现在什么状态"更早被拒。

**两条都进了真机断言**（`target/s14-live.sh` 第 6 节）：
作者本人撤回已归档 → **11011**（穿过归属层，被归档双保险拦下）；
主编撤回同一篇已归档 → **11003**（在归属层就被拦下）。
这样"顺序"本身成了可回归的判据，而不是一句注释。

### 2.8 下架必须带 `reason`，且原因**只**落到 `sys_oper_log`（S14 补记）

- **为什么必须填**：下架是把一篇已发布的线上内容摘掉，属于对外的运营动作。
  没有原因的下架事后无法追责，也无法回答"为什么这篇没了"。
- **为什么用 `@NotBlank` 而不是 `@NotNull`**：`@NotNull` 挡得住 `null`，挡不住 `""` 和 `"   "`；
  空白原因和下架不填原因在业务上是同一件事。
- **为什么上限 200**：`@OperLog` 的 `oper_desc` 列是 `VARCHAR(200)`，切面里会 `truncate`；
  原因本身不写在这一列（写进 `request_param`），但把上限对齐可以保证**原因原文不会被静默截断**。
- **原因落到哪**：`WebLogAspect` 默认 `saveParams() = true`，把 `joinPoint.getArgs()`
  序列化后写进 `sys_oper_log.request_param`。**不**写进 `cms_article_audit_log`：
  那张表的 `result` 只允许 1/2，塞不下"原因"，硬塞还会污染详情页的 `rejectReason`
  （它取的是最近一次驳回意见）。**也**不新增表/列 —— 与 S13 拒绝多余 ALTER 是同一个判据。

⚠️ 代价登记在 §六：**下架原因在页面上无处回显**，只能查操作日志。

### 2.9 版本列表是**只读**接口：不做归属校验（S15 补记）

口径与详情、审核流水**完全一致**（§二.5）：后台是协作场景，编辑/主编必须能打开任何一篇文章
才能审、才能核对。而且版本列表里只有标题快照与修改说明，**没有任何正文**，
暴露面比详情接口还小 —— 详情都放开了，这里单独收紧只会自相矛盾。

它**只**校验文章是否存在（11001）。这与 `listAuditLogs` 一致：不存在的 id 要明确报错，
而不是安静返回空列表，否则前端分不清"这文章没有版本"和"这文章根本不存在"。

### 2.10 版本回滚是**写**接口：要归属校验（S15 补记）

| | 版本列表 | 版本回滚 |
|---|---|---|
| 权限码 | `article:view` | `article:update` |
| 归属校验 | ✗ | ✅ `checkOwnership` → **11003** |
| 谁能调 | 四角色全部 | **仅作者本人** |
| `@OperLog` | ✗ 查询不记 | ✅ `type=UPDATE, desc=回滚文章版本` |

**为什么不给主编**：回滚改的是**正文内容**，与"改草稿"同类，不是运营动作。
主编若想处置别人已发布的内容，用的是"下架/归档"那条线（§二.2）。
⚠️ 手册 S15 写的是"只有作者本人**或主编**可以回滚"，本项目不采纳 ——
`checkOwnership` 按 §三 的既定口径**没有超管短路**，加"主编也能回滚"就得为它开一个例外，
那会把这个接口变成全项目唯一一个能改别人正文的入口。

⚠️ 真机实测：编辑 / 主编 / 管理员回滚作者的稿 → **全部 11003**（连 admin 都不放行）。

### 2.11 ⚠️ 回滚的校验顺序：归属 → 已归档 → 状态白名单（S15 补记）

与 S14 的 `changeStatusByAction` **逐字同序**。所以用非作者身份回滚一篇**已归档**文章，
拿到的是 **11003** 而不是 **11011** —— 理由见 §二.7（归属必须比状态更早被拒）。
两个入口顺序一致的实际好处：读代码的人不必为每个动作重新推一遍"这里到底谁先谁后"。

真机两条断言同时钉住：作者回滚自己的已归档文章 → **11011**；
主编回滚同一篇 → **11003**。

### 2.12 分页检索是**只读**接口：`article:view`，不做归属校验（S17 补记）

`GET /api/v1/articles` 的权限口径与 §二.5 完全一致 —— **读接口不按归属过滤**：

- **权限码用 `article:view`，不是 `article:list`**。契约 §1.3 里写过 `article:list`，
  但库表 `sys_permission` 的 20 条里**没有**这个码（文章域只有
  `view/create/update/submit/audit/publish/withdraw/manage/delete` 九个）。
  用 `article:list` 会让**所有**角色在权限切面就被拒（fail-safe 拒绝空权限），
  而且 `@RequirePermission` 是拿注解值和库里比对，写错的后果是"全站 403"而不是报错。
- **`authorId` 是普通筛选条件，不是安全边界**。前端"我的投稿"页用它把自己筛出来，
  那是产品需求；后台需要编辑/主编能**枚举**任何人的文章才能审。
  所以 Service 的入参里**没有** `operatorId` —— 签名本身就说明"这里不做归属判断"。
  被限制的是"改"（§二.1/§二.10），不是"看"。
- **不加 `@OperLog`**：读接口一律不记操作日志（§二.3）。
  实测反向印证：`sortField=createTime` 被拒成 400 时，`sys_oper_log` **一条都没留**
  （参数校验发生在切面之前，见 §七 末段）。

真机实测（`target/s17-live.sh`，详 `docs/SQL优化记录.md` §七）：
四角色都能拿到列表；SQL 固定 **4 条**（有数据页）且不随数据量变。

## 三、`checkOwnership` 为什么**没有**"超级管理员短路"

契约 §6.4 的示例片段写的是"超管直接 return"。**本项目不采纳**，三个理由：

1. **签名里没有角色。** 冻结的 Service 签名是 `updateDraft(Long id, dto, Long operatorId)`，
   只传 id 不传 `LoginUser`（S07 的取舍：可测试、可被无 HTTP 上下文的定时任务复用）。
   要做超管短路就得改签名 = 改契约，代价大于收益。
2. **业务上也不该允许。** 手册对"编辑/主编能否修改别人的文章内容"给的答案是"不能（审核意见可以写，正文不能改）"。
   审核人有自己的入口（`/articles/{id}/audit`），不需要靠"直接改写作者的正文"来完成审核。
3. **最小权限原则。** "能管理文章"（功能权限）与"这篇文章是不是我写的"（数据归属）是**正交**的两个维度。

⚠️ 实测确认这条在真机上也成立：`admin` 改别人的草稿 → **11003**（不是放行）。
⚠️ 代价是一处**前端待办**：见 §五。

## 五、⚠️ 由此产生的**前端待办**（登记，S14 之后修）

`frontend/src/views/article/articleActions.js` 目前**只按权限码**决定按钮是否显示，**不判断归属**。
因为 `checkOwnership` 刻意没有超管短路，于是：

- 主编（有 `article:update`）会看到**别人草稿**上的"编辑"按钮，点下去被 **11003** 拒；
- 同理 admin、editor 都会看到。

按钮**可见性**与后端规则不一致属于缺陷。修法（S14 之后连同 F06 全流程 E2E 一起做）：
`articleActions.js` 的入参里已经有 `row.authorId` 与当前用户 id，
把"编辑 / 提交 / 撤回"这三个动作的显示条件从"有权限码"改成"有权限码 **且** `row.authorId === currentUserId`"。

## 七、与 S16 跨域联调的交叉引用（S16 补记）

S16 用 **50 条用例 / 63 条断言**把这 14 个接口连同三条跨域链路全量跑了一遍

1. **本章的权限矩阵在真机上再次成立**：未登录 14 个接口全 **401**；author/editor 调 publish 全 **403**；
