## 三、四个值得记的技术点

### 点 1：`PageQuery` 的排序不能拼字符串，走 `OrderItem`

**问题**：MyBatis 的 `#{}` 不能用于列名（会被当字符串字面量），
所以"排序字段"天然只能用 `${}` 拼接 —— 而那就是 SQL 注入面。

**做法**：不拼字符串，改用 MP 的 `Page.addOrder(OrderItem.asc/desc(col))`。

### 点 2：`orderItem` 的列名仍要校验 —— 且校验顺序有讲究

即使走 `OrderItem`，列名最终还是进 SQL。所以 `PageQuery` 里加了两道：

```java
// 第一道：格式白名单（正则）
private static final Pattern SAFE_IDENTIFIER =
        Pattern.compile("^[A-Za-z_][A-Za-z0-9_]{0,63}$");

// 第二道：列名白名单（各域自己传）
query.toMpPage("create_time", "publish_time", "view_count");
```

⚠️ **踩到的坑（本步最有价值的发现）**：

最初实现是 `String f = sortField.trim();` 然后校验 `f`。测试里
`sortField = "id\u0000"`（末尾带 NUL 字节）**没有**被拒绝。

原因是 **Java 的 `String.trim()` 会去掉所有码点 `<= U+0020` 的字符**，
其中包含 NUL(0x00)、TAB(0x09)。于是 `"id\0"` 被 trim 成 `"id"` 通过了校验 ——
但原始串在某些 MySQL 配置下会被当作与 `id` 不同的标识符，
这是 **NUL 字节截断绕过**的经典手法。

**修法**：只剔除两端的普通空格（0x20），控制字符原样保留给正则拒绝。

```java
// 特意不用 String.trim() —— 它会连 NUL/TAB 一起去掉，等于给注入输入"洗白"
private static String stripSpaces(String s) {
    int start = 0, end = s.length();
    while (start < end && s.charAt(start) == ' ') start++;
    while (end > start && s.charAt(end - 1) == ' ') end--;
    return s.substring(start, end);
}
```

测试里专门锁死这个行为（`testRejectsControlCharactersRegardlessOfPosition`），
覆盖 NUL 在首/中/尾、TAB、换行、回车、DEL 六种位置。
**若将来有人把 `stripSpaces` "优化"回 `trim()`，这条测试会红。**

### 点 3：报错信息里不能直接拼用户输入

非法 sortField 的报错信息如果直接拼原值，遇到含控制字符的输入
（比如 `"id\n"`）会把日志撑成两行、甚至污染终端显示。

所以加了个 `describe()` 方法：把控制字符渲染成 `\xNN` 形式、截断到 40 字符。
测试里也断言了"报错信息必须是单行"。

### 点 4：`BaseController` 故意不继承任何框架类

考虑过做成 `abstract class BaseController extends ...`，但发现没必要。
本类定位是"**静态工具方法的容器**"，无状态、无依赖注入、可自由 `new` ——
这样单测时不用起容器。提供的两个方法：

```java
protected Long currentUserId()        // 取不到返回 null（允许匿名接口用）
protected Long requireCurrentUserId() // 取不到抛 401（明确表达"必须登录"）
protected <T> PageResult<T> toPageResult(IPage<T> page)
```

分成两个方法而不是一个，是因为"允许匿名"和"必须登录"是两种不同语义。
只有一个 `currentUserId()` 的话，下游某个 null 会在 Service 深处才炸，
报错点离现场很远，排查费劲。

## 四、关于 `deleted` 填充的一处自我修正

S06 手册要求 `insertFill` 里填 `deleted = 0`，我加了。但**实测 SQL 显示这是多余的**：

```sql
INSERT INTO sys_oper_log ( module, oper_type, ..., create_by, create_time, update_by, update_time )
VALUES ( ?, ?, ..., ?, ?, ?, ? )
-- 注意：字段列表里没有 deleted
```

因为该列有 `DEFAULT 0`，MP 不会把它列进 INSERT。

**那要不要删掉这句填充？** 我选择保留，理由是防御性：

- 万一将来某张表漏写 `DEFAULT 0`
- 万一换成不允许"列不在 INSERT 列表就用默认值"的数据库方言

**多余的一道保险，好过缺一道保险。** 但我把这个判断写进代码注释和证据文档，
免得后人以为"没有它就会挂" —— 实际不会，只是多一层兜底。

## 六、与后续步骤的衔接

**S07 起写业务功能时，标准三段式**：

```java
// Controller
@GetMapping("/api/v1/articles")
public Result<PageResult<ArticleVO>> page(@Valid ArticleQueryDTO query) {
    return Result.ok(articleService.pageArticle(query));
}

// ServiceImpl（继承 BaseServiceImpl）
public PageResult<ArticleVO> pageArticle(ArticleQueryDTO query) {
    query.normalize();                                        // ① 归一化
    Page<Article> mp = query.toMpPage("create_time", "publish_time");  // ② 白名单校验
    Page<Article> result = baseMapper.selectPage(mp, buildWrapper(query));  // ③ 查询
    return PageResult.of(result.map(ArticleVO::from));
}
```

三行的职责分别是：修正非法值、拦住注入、真查询。**顺序不能反** ——
`toMpPage` 在 `normalize` 之前调的话，size 可能是 9999。

**尚未做的（后续步骤）**：
- 各业务 DTO 上的 `@NotBlank`/`@Size` 等校验注解 → S07 起随业务铺开
- `@Valid` 的校验失败处理 → `GlobalExceptionHandler` 已就绪（S05 做的）
- 乐观锁 `@Version` 的实际使用 → S13 排期发布时要用，届时必须判 `updateById` 返回值
