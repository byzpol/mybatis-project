## 二、版本快照在什么时机产生（手册要求"先确认设计"）

| 触发点 | 是否产生新版本 | 本步实测 |
|---|---|---|
| 1. 创建草稿 | ✅ 版本 1 | `[S15] 创建+改两次 → 版本 [1, 2, 3]，说明 [创建草稿, 更新草稿, 更新草稿]` |
| 2. 每次更新草稿 | ✅ +1 | 同上 |
| 3. 提交初审 | ✅ **会**（说明写"提交初审"） | 由 S09 实现，本步沿用 |
| 4. 审核驳回后作者改稿 | ✅ +1（同 2） | 同上 |
| 5. **回滚** | ✅ **也 +1**（不是删历史版本） | `[S15] 回滚到 v1：版本 [1, 2, 3]，v3 说明=回滚至版本 1` |
| 撤回 / 下架 / 归档 / 发布 | ❌ 不产生 | 内容没变，快照没意义（S13/S14 已定） |

> 第 3 项与手册的"不需要"**不一致**：手册写"提交初审时是否要快照？——不需要（内容没变）"，
> 但 S09 实现时是**要**的（`REMARK_SUBMIT = "提交初审"`）。理由：提交把文章推进到"待审"，
> 快照记录的是**谁在什么时候把哪一版内容送进了审核流程**，这是审核追溯的起点，
> 而不是"内容变了才存"。本步不改（改了会动 S09 已验证的行为），仅登记。

## 三、⚠️ 版本列表**不返回正文**（核查项 3）

### 3.1 真机实测

```
长正文文件 24000 字节（8000 个汉字）
版本列表响应 457 字节 / 详情响应 24396 字节（详情含正文）
[OK]   版本列表响应里没有 contentSnapshot 字段                 = 0
[OK]   版本列表响应里没有 content 字段                         = 0
[OK]   版本列表显著小于详情                                     列表 < 详情的 1/5
```

**列表 457 字节 vs 详情 24396 字节，差 53 倍。** 判据不是"字段大不大"，
而是**这一列在这张列表上有没有人用** —— `ArticleDetail.vue` 的版本表格只渲染
版本号 / 标题快照 / 修改人 / 说明 / 时间，正文一个字都不显示。传了不用 = 白花带宽。

### 3.2 JUnit 里的**强判据**：反射断言字段不存在

```java
for (Field f : CmsArticleVersionVO.class.getDeclaredFields()) { ... 名字含 content 就失败 ... }
try { CmsArticleVersionVO.class.getDeclaredField("contentSnapshot"); fail(); }
catch (NoSuchFieldException expected) { /* 期望路径 */ }
```

真跑输出：

```
[S15] 反射核查：VO 字段 = serialVersionUID, id, versionNo, titleSnapshot,
      modifierId, modifierName, modifyRemark, createTime, isCurrent
```

⚠️ 为什么不用"跑一次看 `contentSnapshot` 是不是 null"：正文恰好为 null 的版本会让那种断言
**假通过**。反射是**结构层面**的判据 —— 字段根本不存在，就不可能被序列化出去，
与数据内容无关，永远为真。

### 3.3 ⚠️ 一处与手册不一致：`titleSnapshot` 返回**完整**标题，不截成 50 字

手册写"只返回标题快照摘要（前 50 字）"。本项目**不采纳截断**：

1. 真正撑大响应体的是 `LONGTEXT` 正文，不是 `VARCHAR(200)` 的标题。
   把 200 字标题截到 50 字，一行只省 150 字节，却让"标题快照"这一列
   在很多中文标题上直接被砍掉后半截 —— 而这一列正是用户区分版本的主要依据。
2. 前端这一列本来就配了 `show-overflow-tooltip`，长标题由 UI 层折叠，不需要后端提前截断。
3. 截断是**不可逆的信息损失**：后端截了，前端就算想显示全文也拿不到。

## 四、回滚的规则与关键设计决定

### 4.1 ⚠️ URL 以**契约**为准，不是手册

| | 手册 S15 | 契约 §1.3 第 16 行（**采用**） |
|---|---|---|
| 回滚 | `POST /articles/{id}/versions/{versionNo}/rollback` | `POST /articles/{id}/rollback`，`{versionNo}` 放请求体 |
| 版本详情 | `GET /articles/{id}/versions/{versionNo}` | **无此接口** |

三个理由：① 契约已冻结（tag `trunk-v1.0`，10-16 评审通过），手册是任务书、契约是交付物；
② **前端已按契约实现好了**（`article.js` 的 `rollbackVersion` 注释里明确写"手册的已废弃"），
按手册实现会让前端立刻 404；③ 项目约定 URL 资源层级 ≤3，
`/articles/{id}/versions/{n}/rollback` 在 `/api/v1` 之后有 4 段。

⚠️ 手册的 `GET /{id}/versions/{versionNo}`（取某一版的正文）**本步不实现**：
契约里没有、前端不调用、且同样超层级。它对应的是"回滚前先看看要变成什么样"这个需求，
当前用不上（前端确认弹窗只提示"将以 vN 的内容新建一个版本"）。已登记为挂起项。

### 4.2 ⚠️ 权限码 `article:update`（契约写的是 `article:edit`）

契约 §1.3 写 `article:edit`，但**库里没有这个码**（`sys_permission` 的 9 个是
`view/create/update/submit/audit/publish/withdraw/manage/delete`）。照契约写会让
`PermissionAspect` 认为所有角色都缺权限，**连 admin 都被 403**。
以 `docs/接口分类与鉴权表.md` 为准（那张表是核对过库表的）。

### 4.3 状态白名单：只有 DRAFT / REJECTED / WITHDRAWN 可回滚

**为什么"已发布(5)"不能直接回滚**：已发布的内容是**线上**内容。允许一步回滚意味着
"任何有权限的人可以在不经过审核的情况下改变读者看到的东西" —— 那正是审核流程存在的意义。
正确路径是 **先撤回 → 再回滚 → 重新提交审核 → 重新发布**，每一步都在状态机里有据可查。

更硬的一条理由：`PUBLISHED(5)` 与 `PENDING_*`/`SCHEDULED(6)` 一样属于"在流转中"的状态，
它们的出边都被状态机管着；**回滚不改变状态、只改内容，它绕过了状态机** ——
越是这样，越要靠一条显式白名单把"能让它绕过状态机的场景"限制到最小。

**⚠️ 用白名单而不是黑名单**：将来状态机加第 11 个状态时，黑名单会**默认放行**
（写回滚的人根本不知道有新状态存在），白名单会默认拒绝。
安全相关的判断一律用白名单 —— 这是本项目的一条通则。

实现用 `EnumSet` + `Collections.unmodifiableSet`：`contains` 是位运算；
且 `EnumSet.contains(null)` 返回 `false` 而不抛异常，状态为 null 的脏数据自然落进"拒绝"分支。

真跑输出：

```
[S15 白名单] PENDING_EDITOR(1) → 11002
[S15 白名单] PENDING_CHIEF(2) → 11002
[S15 白名单] APPROVED(3) → 11002
[S15 白名单] PUBLISHED(5) → 11002
[S15 白名单] SCHEDULED(6) → 11002
[S15 白名单] OFFLINE(8) → 11002
[S15 白名单] ARCHIVED(9) → 11011（归档只读比状态非法更具体）
```

### 4.4 ⚠️ 校验顺序沿用 S14：归属 → 已归档 → 状态白名单

与 `changeStatusByAction` **逐字同序**。所以用非作者身份回滚一篇**已归档**文章，
拿到的是 **11003** 而不是 **11011** —— 理由见
`docs/S14-撤回下架归档实测记录.md` §4.2：归属必须比状态更早被拒，
否则"这不是你的稿"会被"状态允不允许"掩盖。

真机两条断言同时钉住（第 8 节）：

```
作者回滚自己的已归档文章 → 期望 11011   HTTP=200 code=11011  {"code":11011,"message":"已归档的文章不可修改"}
非作者(主编)回滚已归档文章 → 期望 11003  HTTP=200 code=11003  {"code":11003,"message":"只能操作自己创建的文章"}
```

### 4.5 ⚠️ 回滚**只**恢复 `title` 与 `content`

因为 `cms_article_version` **只快照了这两列**。`summary` / `cover_url` /
`category_id` / `is_top` 不在快照里，因此回滚不会、也无法恢复它们。

这一点必须说清楚，否则用户会以为"回滚 = 回到那一版的样子"，而实际上分类、封面、摘要
都还是现在的值。前端确认弹窗的文案已经按"以 vN 的内容**新建一个版本**"来表达，
不敢写"恢复到 vN"。

**真机判据**（第 5 节）：先把摘要改成"改后摘要"、分类改成 2，再回滚到 v1：

```
[OK]   ⚠️ 摘要不在快照里 → 回滚后仍是「改后摘要」 = 改后摘要
[OK]   ⚠️ 分类不在快照里 → 回滚后仍是 2                 = 2
[OK]   标题确实被恢复了                                     = 【S15联调】只回滚正文
```

### 4.6 ⚠️ 为什么回滚要"再生成一个新版本"，而不是删掉后面的版本

回滚的语义是**"以旧内容新建一版"**，不是"撤销"。删掉后面的版本会有三个后果：

1. **历史不可信**：版本表本来是只增不改的审计性数据（`CmsArticleVersion` 连
   `update_by`/`update_time` 都没有），删除等于允许改写历史。
2. **版本号会重复**：删掉 N+1 之后下一个新版本又会取到 N+1，而"第 N+1 版"
   在别人眼里已经出现过一次，含义完全不同。
3. **回滚本身无法追溯**：谁也说不清"文章现在为什么是这个内容"。

所以回滚 = 覆盖正文 + 追加一条 `version_no = max + 1`、
`modify_remark = "回滚至版本 N"` 的快照。**版本号只增不减。**

真机判据：回滚到 v1 后版本号是 `[1,2,3,4]`（不是 `[1]`），且
`v2` 仍在（`[OK] v2 还在（回滚不是删历史） = 更新草稿`）。

⚠️ `modify_remark` 记的是**目标版本**而不是新版本号（"回滚至版本 1"），
否则文案会变成"回滚至版本 4"而实际上是回到 v1，语义完全反了。

### 4.7 版本号生成的三方案对比（手册第四节要求）

| 方案 | 能否保证不重复 | 代价 | 结论 |
|---|---|---|---|
| ① **唯一索引 `uk_article_version(article_id, version_no)` + 捕获 `DuplicateKeyException` 重试** | ✅ **数据库层面**保证 | 只在真正冲突的那一次重试，代价≈0 | ✅ **采用** |
| ② `SELECT MAX(version_no) ... FOR UPDATE` 悲观锁 | ✅ | 要求 `FOR UPDATE` 与后续 INSERT 在同一事务 → **持锁到事务提交**；且"下一篇的版本号"这一行**还不存在**，要锁只能锁"当前最大号那一行"，语义绕一层 | ❌ 不采用 |
| ③ 乐观锁 `@Version` | ❌ | 乐观锁保护的是**文章主表**那一行，它保证"两个请求不会同时改同一篇文章"，但**不保证版本号不重复** —— 版本号是另一张表的事 | ❌ 不采用（但主表更新仍在用它，见 §4.10） |

**为什么 ① 是"最后一道防线"而不是"唯一防线"**：取号本身仍是
`SELECT MAX(version_no) + 1`（并发下两个请求会拿到同一个号），
真正的兜底是**数据库的唯一索引** —— 即使代码有并发漏洞，数据也不会脏。

⚠️ 冲突后必须**重新查一次 MAX**（`for (attempt = 1..3)` 循环体第一行就在做），
直接 +1 会拿到下一个同样可能被占用的号 —— 那叫瞎猜，不叫重试。

**实测判据**（`testUniqueIndexRejectsDuplicateVersionNo`）—— 直接问数据库，不查代码：

```
[S15] 唯一索引 uk_article_version 存在且真的拒绝重复 (articleId=967, versionNo=1)
```

它做两件事：① 读 `information_schema.statistics` 断言索引存在、`non_unique = 0`、复合 2 列；
② **真的插一条重复记录**看它被拒绝。项目里"唯一索引兜底"这句话出现在多处注释里，
但注释不是证据 —— 索引被人删掉、建错成非唯一索引，代码看起来一模一样。

### 4.8 并发实测：5 个请求同时改同一篇文章

```
[S15] 并发更新 5 次 | 成功=1 11010(乐观锁)=4 其它=[] | 版本号=[1, 2, 3]（无重复、无空洞）
```

⚠️ 断言的是**"版本号无重复、无空洞"**这个不变式，不是"5 个请求全部成功"。
同一篇文章被同时改，除第一个之外都会拿到 **11010** —— 那是**乐观锁在工作**，是设计如此。
用例同时打印"成功 / 乐观锁冲突 / 其它"的分布，把"到底发生了什么"留在测试输出里。

⚠️ 顺带说明：`insertVersionSnapshot` 的"冲突后重新取号重试"分支（`attempt > 1`）
在本用例里**不一定**会被走到 —— 要让两个线程恰好拿到同一个号，必须让它们的
`SELECT MAX` 严格交错，这是无法在单进程测试里稳定复现的（S09 已把同一条登记为未覆盖）。
本用例覆盖的是"最终数据不脏"这个**可断言**的结果。

### 4.9 ⚠️ 覆盖正文必须显式列列（`content` 允许为 NULL）

```java
LambdaUpdateWrapper<CmsArticle> wrapper = Wrappers.<CmsArticle>lambdaUpdate()
        .eq(CmsArticle::getId, article.getId())
        .set(CmsArticle::getTitle, target.getTitleSnapshot())
        .set(CmsArticle::getContent, target.getContentSnapshot());
```

**不能用 `updateById(entity)`**：`content_snapshot` 允许为 NULL（"确实没正文"），
而 `updateById` 的 NOT_NULL 默认策略会把 null 字段**整段跳过** —— 于是
"回滚到一个没有正文的版本"会返回 200，但库里的正文一个字都没被清掉。
这是 S09 就踩过的同一个坑。

**真机判据**（`testRollbackRestoresNullContent`）：把 v1 的 `content_snapshot` 改成 NULL，
改一次稿（v2 有正文），再回滚到 v1 →

```
[S15] 回滚到空正文版本 → 库里 content 已置 NULL（显式列列生效）
```

### 4.10 ⚠️ 内存里的 `article` 必须同步改成"回滚后"的内容

`insertVersionSnapshot(article, ...)` 从**入参对象**取标题与正文。
如果覆盖完库里就忘了改内存对象，新快照记的会是回滚**前**的旧内容 ——
而它的 `modify_remark` 却写着"回滚至版本 N"，等于生产一条**自相矛盾**的记录，
并且这条记录会被 `isCurrent` 指认为"当前版本"，内容却是旧的。

所以覆盖写库之后立刻：

```java
article.setTitle(target.getTitleSnapshot());
article.setContent(target.getContentSnapshot());
insertVersionSnapshot(article, operatorId, REMARK_ROLLBACK_PREFIX + versionNo);
```

### 4.11 N+1 治理与"不额外查 MAX"

- **修改人昵称**：先收集去重（`LinkedHashSet`），再**一次 `IN` 查询**拼装，绝不在循环里 `selectById`。
- **最大版本号**：**刻意不额外查一次 `SELECT MAX(version_no)`**。版本列表已按
  `version_no` 升序取出，**最后一个元素的 versionNo 就是最大值**。
  再发一条 SQL 不但多一次往返，还多一个"两条查询结果不一致"的可能
  （两条查询之间有人插入了新版本）。用列表自身推导，"取列表"与"算 isCurrent"必然一致。

**真机判据**（第 10 节，读 `cms.log` 的 `Preparing:` 行数）：

```
1 个版本 → 3 条 SQL；21 个版本 → 3 条 SQL（增量 0）
[OK]   SQL 条数不随版本数增长    增量 0 ≤ 2（逐条查的话增量会是 20）
```

3 条 = 文章存在性 + 版本列表 + `sys_user` 批查。
**判据是"增量"而不是绝对值**（绝对值里含权限切面等自身可能发出的查询）。
一个逐条查修改人的实现，增量会等于版本数（20）。

### 4.12 ⚠️ `isCurrent` 不能用 `Integer ==` 比较

```java
vo.setIsCurrent(row.getVersionNo() != null && row.getVersionNo().intValue() == maxVersionNo);
```

两个 `Integer` 用 `==` 比的是**引用**，只在 -128~127 的缓存范围内"恰好"相等 ——
版本号超过 127 之后这个判断会**静默变成永远 false**。
项目里已经为同一个坑踩过一次（S13 的 `statusCode != SCHEDULED.getCode()`）。

另有一条容易忽略的：`isCurrent` 必须是显式的 `Boolean` 而不是 null。
用例里专门反向断言 `isCurrent 不能是 null（必须显式赋 false）` ——
null 会让前端 `v-if="row.isCurrent"` 恒假，**看着"没标错"其实是字段没赋值**。

### 4.13 版本接口**不写审核流水**

版本快照与审核流水是两条线：快照记"内容在什么时候长什么样"（`cms_article_version`），
流水记"谁在哪一环节对内容给出了什么结论"（`cms_article_audit_log`，`result` 只允许 1/2）。
回滚是内容操作，不是审核结论。

**真机判据**（第 11 节）：回滚前后该文章的审核流水条数 **0 → 0**。

## 五、手册 5 条核查项逐条判定

### ⚠️ 第一次跑踩的两个坑（都是脚本自身的问题，不是代码缺陷）

1. **长正文被后续更新整篇覆盖**：第 9 节先造了一篇长正文草稿，又用
   `update_draft` 改了一次 —— 而 `update_draft` 会用新正文**整篇覆盖**，
   于是"当前内容"变短了，体积比较得出"详情 409 字节 < 列表 457 字节"。
   修法：新增"可传正文文件"的参数，第二次更新仍然带长正文。
   （**也算一个真发现**：说明"改草稿"确实是整体替换语义，不是增量 patch。）
2. **脚本跑了 2m31s 超过默认超时被 SIGTERM**：脚本里大量调用 Python 解析 JSON，
   每次都要起一个新进程（Windows 上约 1s），累积超过 120s。
   修法：放后台跑。**没有**为了提速把 JSON 解析换成 `grep` ——
   grep 在"字段顺序变了""多了一层嵌套"时会静默给错答案。
