## 三、手册 vs 实际：三处必须纠正的差异

> 按"一切以实测/实读文件为准"的原则，这里逐条列出**手册描述与实际不符**之处。
> 这些正是"AI 幻觉"最容易出没的地方。

### 差异 1：手册漏了 `version` 字段（乐观锁）

- **手册说**：`CmsArticle` 字段为 `title、summary、coverUrl、content(LONGTEXT)、categoryId、status、authorId、publisherId、publishTime、scheduleTime、isTop、viewCount` —— **共 12 个**。
- **实际库表**：`cms_article` 还有一列 `version INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号（MyBatis-Plus @Version）'`。
- **处理**：实体**必须**加该字段并标 `@Version`。漏掉的后果是"乐观锁静默失效"——
  并发编辑时后提交的覆盖先提交的，**不报错、不留痕**，是最难查的一类 bug。
- **验证**：`ArticleEntityMappingTest#testVersionIsOptimisticLock` 断言 MP 确实识别到了该列。

### 差异 2：手册要求新建 `ArticleStatusEnum`，但项目已有 `ArticleStatus`

- **手册说**：新建 `common/enums/ArticleStatusEnum.java`，10 态，
  `APPROVED(3,"已通过待发布")`、`SCHEDULED(6,"定时待发")`。
- **实际**：S04 已建 `common/enums/ArticleStatus.java`（10 态，code 0~9 完全一致），
  且描述略有不同（`APPROVED(3,"审核通过")`、`SCHEDULED(6,"定时发布中")`），
  另有 `of()` / `ofNullable()` / `getDesc` 等能力，以及 **15 个已有测试**在断言它。
- **决策**：**不新建**。新建一个 code 完全相同的枚举会导致：
  ① 两处 code 定义，改一处漏一处；
  ② `CmsArticle.status` 到底该用哪个类型说不清；
  ③ 15 个现有测试白写。
- **说明**：手册里的 `getDesc(Integer)` 要求，现有枚举用 `ofNullable(code).getDescription()`
  等价实现（VO 组装时用）。差异只在"描述文案"上，非功能差异。

### 差异 3：手册要求状态机放 `util/` 包，且只提三个方法

- **手册说**：`util/ArticleStateMachine.java`，方法 `canTransfer` / `nextStatus` / `assertTransfer`。
- **实际**：S04 已建 `common/ArticleStateMachine.java`（不在 `util/`），
  已有 `canTransfer` / `transfer`（抛异常版）/ `outDegree` / `transitionCount`，且有大段设计注释。
- **决策**：**保留原位置与原有方法**（移动包会破坏 S05 可能已有的引用与测试），
  **在其上补齐** `nextStatus`（非法返 null）与 `assertTransfer`（固定抛 11002）。
- **两个易混方法的语义分工**（已写进类注释）：

  | | 合法迁移 | 非法迁移 | 入参 null / 脏码 |
  |---|---|---|---|
  | `transfer` | 返回目标 | 抛异常（三种错误码分情况） | 抛异常 |
  | `nextStatus` | 返回目标码 | 返回 null | 返回 null |
  | `assertTransfer` | 不抛异常 | 抛 `ARTICLE_STATUS_ILLEGAL` | 抛 `ARTICLE_STATUS_ILLEGAL` |

## 四、四个技术决策及理由

### 4.1 `CmsArticleVersion` 为什么不继承 `BaseEntity`

判据是**库表有没有那几列**，不是"这张表重不重要"：

```
BaseEntity 提供的列：id, create_by, create_time, update_by, update_time, deleted
                                        ^^^^^^^^^^  ^^^^^^^^^^  ^^^^^^^^^^^
cms_article_version 实际列：id, article_id, version_no, title_snapshot,
                       content_snapshot, modifier_id, modify_remark,
                       create_time, deleted
                       —— 没有 create_by / update_by / update_time
```

若强行继承，`AuditMetaObjectHandler` 会给 `updateBy/updateTime` 填值
（`FieldFill.INSERT_UPDATE` 插入时也填），MP 把这些列拼进 INSERT →
数据库报 `Unknown column 'update_by' in 'field list'`。

**用测试把"不该有"也钉死**：`ArticleEntityMappingTest#testCmsArticleVersionDoesNotInheritBaseEntity`
断言该类不继承 `BaseEntity`，且不含那三个列。将来有人"好心"改成继承，测试会立刻拦下。

### 4.2 `isTop` 为什么要显式 `@TableField("is_top")`

MP 的列名推导**看 getter/setter 名，不直接看字段名**。Lombok 对 `is` 前缀有特殊规则，
`boolean isXxx` 与 `Integer isXxx` 生成的方法名不同，推导结果存在不确定性。
这是一类"编译通过、运行报 `Unknown column 'top'`"的典型故障。

实测确认（`ArticleEntityMappingTest#testIsTopColumnMapping`）：
MP 解析出的列名是 `is_top`，且不含 `top` / `isTop`。

### 4.3 两个新枚举为什么实现"查不到不抛异常"（而 `ArticleStatus.of` 抛）

两者用途不同：

- `ArticleStatus.of(code)`：用于**入参校验**（前端提交的状态值必须合法）→ 抛异常合理。
- `AuditStageEnum.ofNullable` / `AuditResultEnum.getDesc`：用于**把库里的历史值翻成中文展示**
  → 库里若有手工改坏的脏值，抛异常会让整个审核历史列表 500。
  返回 `"未知环节"` 兜底，页面能开、问题也能一眼看见。

同理 `CmsArticleVO.statusDesc` 用 `ofNullable` 兜底。

### 4.4 `ArticleServiceImpl` 为什么全抛 `UnsupportedOperationException` 而不是留空

留空（方法体为空 / `return null`）的症状：`saveDraft` 返回 null，
调用方以为是新 id，带着 null 往下走，错误在很远的地方才爆。

抛异常则"忘实现"立刻暴露，且异常信息点名了方法与在哪一步实现。
**宁可立刻炸，不要静默地错** —— 这些异常本身就是"待实现清单"。

## 五、本步踩到的坑（实测发现，非推测）

### 坑 1：Javadoc 里嵌套 `/* */` 导致注释块提前闭合

**现象**：编译报 `非法字符: '\u3002'`、`需要 class、interface、enum 或 record`，
且行号指向注释内容以后的位置，看起来像"文件整体坏掉了"。

**根因**：Javadoc 注释里写了一句示例代码
`{@code ... if (t == null) { /* 忘了处理 */ }}`，
其中 `/* 忘了处理 */` 的 **`*/` 提前闭合了外层注释块**，后面的代码全变成裸文本。

**修复**：改成不带 `/* */` 的表述。

**教训**：**Javadoc 里永远不要出现 `/*`**（哪怕在 `{@code }` 里）。
`{@code}` 只处理 HTML 转义，不处理注释嵌套。
这是写文档时"顺手举个代码例子"极易踩的坑 —— 已记入长期约定。

### 坑 2：MP `TableInfoHelper` 没有 `getTableInfo(Configuration, Class)` 重载

**我先写的代码**（凭记忆）：`TableInfoHelper.getTableInfo(configuration, entityClass)`。

**实际**（用 `javap` 查 MP 3.5.5 的 jar 确认）只有：
```
public static TableInfo getTableInfo(java.lang.Class<?>);
public static TableInfo getTableInfo(java.lang.String);
public static synchronized TableInfo initTableInfo(MapperBuilderAssistant, java.lang.Class<?>);
```
**没有** `(Configuration, Class)` 两参数版本。

**修复**：改用单参数 `getTableInfo(Class)`（容器已启动、实体已注册，缓存里能取到）。

### 坑 3：MP 的 `TableInfo` 里 `deleted` 列被返回两遍

**现象**：测试断言"列数应为 19"失败，实际 20，多出一个 `deleted`。

**根因**：`deleted` 列**既在 `info.getFieldList()` 里，又被
`info.getLogicDeleteFieldInfo()` 单独返回一次**。我把两者都往 List 里加，重复计数了。

**关键**：这是**测试代码的 bug，不是实体的问题** —— 实体列名本身完全正确。
修法是收集时用 `LinkedHashSet` 去重。

**教训**：写"对账类"测试时，先打印实际值再写断言。
若我一开始就断言 `actual.size() == 20`，就把这个坑"固化"成正确了。
