### ⚠️ 为什么 vue-router 锁 4.x 而不是用最新的 5.x

`npm view vue-router version` 当前最新是 **5.4.0**，但它的 peer 依赖是这样的：

```
vue-router@5  peer: vue ^3.5.34 || ^4.0.0, vite ^7.3.0 || ^8.0.0,
                   pinia ^3.0.4 || ^4.0.2, @pinia/colada >=0.21.2, @vue/compiler-sfc
```

它把 **pinia、@pinia/colada、vite 都变成了硬 peer** —— 这已经不是"路由库"的语义了，
是换代级别的重构。手册与组内基线写的都是 **vue-router 4**，组里另外三个人也按 4 的写法在写，
为了不让四个人的页面出现"你按 4 写的 `router.push` 在我这不好使"的问题，锁 4.x 尾版 **4.6.4**。

同理，pinia 没锁大版本（手册没写），取当前稳定版 4.0.3；
它的 `@vue/devtools-api` 是**非可选** peer，npm 7+ 会自动装上，属预期行为。

### Node 版本下限

`vite@8.3.4` 与 `@vitejs/plugin-vue@6.0.9` 的 engines 都是 `^20.19.0 || >=22.12.0`。
本机 Node **v22.22.2** 满足，所以在 `package.json` 里同样写了 `engines.node`，
避免组里有人用 Node 18 跑出莫名其妙的错。

## 三、关键配置项与"为什么这么设"

### 3.1 `vite.config.js` 用函数式配置而不是对象式

```js
export default defineConfig(({ command }) => ({
  base: command === 'build' ? '/cms-mis/' : '/',
  ...
}))
```

**开发与构建要两套 base**：

| 场景 | `base` | 原因 |
|---|---|---|
| `vite`（dev） | `/` | 浏览器直接访问 `http://localhost:5173/`，资源也在根下，正常 |
| `vite build` | `/cms-mis/` | war 部署在 Tomcat 的 `/cms-mis` 上下文下，产物必须去 `/cms-mis/assets/...` 找 |

如果构建也用 `/`，打出来的 `index.html` 会写 `<script src="/assets/index-xxx.js">`，
浏览器会去 `http://host:8080/assets/index-xxx.js` 请求 —— 而 war 在 `/cms-mis` 下，**必然 404**。
这是纯 SSM（非 Spring Boot）项目最典型的踩坑点，实测已确认必须设。

### 3.2 路由 base 与 vite base 自动对齐

`src/router/index.js`：

```js
history: createWebHistory(import.meta.env.BASE_URL)
```

`import.meta.env.BASE_URL` 由 `vite.config.js` 的 `base` 决定：dev 时是 `/`，构建时是 `/cms-mis/`。
**两边不需要手工同步**，也就不会出现"改了 vite 忘了改 router"的漂移。

### 3.3 `build.outDir` 指向 `../src/main/webapp`

```js
build: { outDir: '../src/main/webapp', emptyOutDir: true }
```

这样 `npm run build` 的产物直接落进 war 的源码目录，`mvn package` 时由 maven-war-plugin 一起打包。
`mvn package` 日志里的 `Copying webapp resources [D:\mybatis-demo\project1\src\main\webapp]`
就是这一步生效的证据。

⚠️ **`emptyOutDir: true` 的副作用**：每次构建会**清空** `src/main/webapp/` 整个目录。
所以这个目录里**只能放构建产物**，绝不能手工塞文件。
本项目用 Java 配置类代替 `web.xml`（pom 里已配 `failOnMissingWebXml=false`），
webapp 下没有需要保留的东西，因此是安全的。

### 3.4 `src/main/webapp/` 不入库（新增到 `.gitignore`）

`.gitignore` 开头就写了核心原则："构建产物、IDE 配置、凭据、日志、依赖目录，一律不入库"。
`src/main/webapp/` 和 `target/` 是同一个性质 —— 完全由 `npm run build` 生成，所以排除掉。

**代价（必须写清楚）**：克隆仓库后**必须先在 `frontend/` 下执行 `npm install && npm run build`，
再执行 `mvn package`**，打出来的 war 才带前端页面。
（已验证：没有 `src/main/webapp` 时 war 仍能构建成功，只是不含前端 —— 因为 `failOnMissingWebXml=false`。）

### 3.5 `resolve.alias`：`'@'` → `frontend/src`

用 `fileURLToPath(new URL('./src', import.meta.url))` 而不是 `path.resolve(__dirname, 'src')`：
`package.json` 里设了 `"type": "module"`，`vite.config.js` 是 ESM，`__dirname` 不存在，会直接报错。

`jsconfig.json` 是配套的 —— 它不参与构建，只让编辑器的 Ctrl+点击跳转和自动补全能认出 `@`。

### 3.6 `server.port = 5173` 但不设 `strictPort`

端口被占用时 Vite 会自动顺延到 5174 / 5175。
后端 `CorsConfig` 已按 `http://localhost:[*]` 放开，顺延也能联调；设了 `strictPort` 反而会在
"5173 被占"时报错退出，平白多一个故障点。

### 3.7 浏览器要访问 `localhost:5173` 而不是 `127.0.0.1:5173`（本机实测）

实测 `netstat` 结果：

```
TCP    [::1]:5173    [::]:0    LISTENING    32936
```

Vite 把服务**只绑在 IPv6 的 `[::1]`** 上（Node 的 `localhost` 在本机优先解析到 `::1`）。
所以 `curl http://127.0.0.1:5173/` 是 `Failed to connect`，而 `http://localhost:5173/` 正常。
浏览器用 `localhost` 访问不受影响，但用 Postman / curl 手工测的时候要注意这一点。

### 3.8 开发期代理与生产期跨域是"两道防线"

`server.proxy` 的 `'/api' → 'http://localhost:8080'` **不做 rewrite**：
后端 URL 本身就是 `/api/v1` 前缀，原样转发即可。
用 proxy 的好处是浏览器看到的是同源请求，`JSESSIONID` 这个 Cookie 能正常带上；
跨域 + 第三方 Cookie 会被现代浏览器直接拦掉。

## 四、⚠️ 三处本次踩到/发现的真问题

### 4.1 【最重要】war 部署后静态资源全 404 —— `addResourceLocations` 的路径语义

**现象**：war 部署后，`/cms-mis/index.html` 能打开，但页面上 **所有 js / css 一律 404**，
且返回的是 **649 字节的 Tomcat HTML 错误页**（不是我们的统一 JSON 404）。

**根因**：`ResourceHttpRequestHandler` 解析资源的算法是
「先按 URL pattern 切掉匹配部分，再把剩余相对路径拼到 location 上」。实测：

| 请求 | pattern | 剩余路径 | location | `applyRelativePath` 结果 | 对不对 |
|---|---|---|---|---|---|
| `/assets/index-x.js` | `/assets/**` | `index-x.js` | `"/"` | **`/index-x.js`** | ❌ 丢了 `assets/` |
| `/assets/index-x.js` | `/assets/**` | `index-x.js` | `"/assets/"` | `/assets/index-x.js` | ✅ |
| `/index.html` | `/index.html` | `""`（空串） | `"/"` | `/`（web 根） | ⚠️ 靠 Tomcat 欢迎页兜住 |

注意第三行：`/index.html` 之所以"看起来能用"，是因为 pattern 把整个路径吃光了、
剩余为空、拼出来是 web 根目录，而 Tomcat 对 web 根目录会按欢迎页规则返回 `index.html`。
**这是顺带成立，不是正确写法**，所以最终配置里把每一处的原因都写进注释，避免后人误以为
`location "/"` 是通用写法又去套到子目录上。

**修法**：location 的目录层级必须与 URL 前缀对齐 ——

```java
registry.addResourceHandler("/index.html").addResourceLocations("/").setCachePeriod(0);
registry.addResourceHandler("/assets/**").addResourceLocations("/assets/").setCachePeriod(60*60*24*30);
```

### 4.2 【为什么必须补 `addResourceHandlers`】三个配置叠出来的死角

三个已有配置叠在一起，导致 DispatcherServlet 谁都不认识的请求全落到统一 404：

1. `ServletContainersInitConfig#getServletMappings()` 返回 `{"/"}` —— DispatcherServlet **顶替了 Tomcat 的 DefaultServlet**；
2. `SpringMvcConfig` 上有 `@EnableWebMvc` —— 会**关闭**"未匹配请求转交默认 Servlet"的机制
   （Spring Boot 里靠自动配置补上，纯 SSM 必须自己写）；
3. 于是 `/cms-mis/index.html`、`/cms-mis/assets/*.js` 这些**真实存在**的文件在 DispatcherServlet 里找不到映射。

又因为 S08 打开了 `throwExceptionIfNoHandlerFound`，最后落到 `GlobalExceptionHandler` 返回 404 的 JSON ——
浏览器拿到的不是网页而是 `{"code":404,...}`，**页面彻底白屏**。

**为什么不用 `configureDefaultServletHandling().enable()`**（XML 时代 `<mvc:default-servlet-handler/>` 的等价物）：
它会把**所有**未匹配请求都转给默认 Servlet，而默认 Servlet 对不存在的路径返回 Tomcat 的 HTML 错误页 ——
正好把 S08 刚修好的"统一 404 结果"打回原形（转发后 SpringMVC 认为"handler 找到了"，
`throwExceptionIfNoHandlerFound` 不再触发）。
所以这里**只精确放行确实存在的三类静态资源**，其余路径照旧走统一 404，两个目标不冲突。

> **主干冻结纪律核对**：本次是在 `SpringMvcConfig` 上**新增一个 `addResourceHandlers` 方法**，
> 未改动、未删除任何既有方法签名，符合 `docs/企业开发规范清单.md` 5-4
> "冻结后只许加方法，不许改签名"。冻结通知（B/C/D 可以拉入户线）依然有效。

### 4.3 【施工事故】`CATALINA_HOME` 指向 Tomcat 11，起错了容器

第一次跑部署脚本时 `/cms-mis/*` 一律 404、`tomcat9/logs` 一直是空的。查了才发现：

```
CATALINA_HOME=D:\develop\jdk\apache-tomcat-11.0.18-windows-x64\apache-tomcat-11.0.18
```

本机环境变量里 `CATALINA_HOME` 指向 **Tomcat 11**。`catalina.bat` 的逻辑是
"`CATALINA_HOME` 非空就直接用，否则才从脚本位置推断"，
所以哪怕执行的是 tomcat9 目录下的 `catalina.bat`，它照样去起 Tomcat 11 —— 而 Tomcat 11 的 webapps 里
根本没有 `cms-mis`，于是全是 404。日志自然也写进了 Tomcat 11 的 logs。

**修法**：启动前显式覆盖两个变量（S08 的脚本里本来就有这一行，本次重写脚本时漏了）：

```bash
export CATALINA_HOME="D:/develop/jdk/tomcat9/apache-tomcat-9.0.122"
export CATALINA_BASE="$CATALINA_HOME"
```

**教训**：本机同时装了 Tomcat 11（jakarta）和 Tomcat 9（javax），
唯一可信的判据是启动日志里的 `开始初始化 Servlet 引擎:[Apache Tomcat/x.y.z]` 和设备目录，
不能只看"我 cd 到哪个目录"。

## 六、`npm run build` 产物如何与 Tomcat 部署衔接（手册要求说明的部分）

完整链路，每一步都有实测支撑：

```
frontend/src/*.vue,*.js
   │  npm run build（vite）
   ▼
frontend/../src/main/webapp/{index.html, assets/*}
   │  mvn package（maven-war-plugin 的 Copying webapp resources）
   ▼
target/cms-mis.war
   │  拷到 $CATALINA_HOME/webapps/
   ▼
$CATALINA_HOME/webapps/cms-mis/（Tomcat 自动解包）
   │  请求 /cms-mis/**
   ▼
DispatcherServlet（映射 "/"）
   ├─ /api/**            → @Controller（或统一 Result 404）
   └─ /index.html, /assets/** → ResourceHttpRequestHandler → war 根目录下的真实文件
```

**三个必须同时成立的条件**（缺一个就是白屏）：

1. `vite.config.js` 的 `base` 在构建时必须是 `/cms-mis/`（否则资源 URL 少了前缀）；
2. `SpringMvcConfig#addResourceHandlers` 必须放行 `/index.html` 与 `/assets/**`，
   **且 location 的目录层级与 URL 前缀对齐**（否则文件明明在 war 里也 404）；
3. 部署前 `npm run build` 的产物必须已经落在 `src/main/webapp/`（否则 war 里根本没有这些文件）。

**已知限制（写清楚，别到答辩才发现）**：路由用的是 `createWebHistory`（URL 干净，没有 `#`），
代价是**刷新深层路径**（如直接按 F5 打开 `http://localhost:8080/cms-mis/articles`）
会走 DispatcherServlet 的"无 handler"分支返回统一 404 JSON —— 因为服务器并不知道
`/articles` 是个前端路由。
本项目**开发期一律用 Vite dev server**（它内置了 history fallback，刷新正常），
部署后演示时走"点菜单跳转"（客户端路由，不经过服务器），因此不受影响。
若将来必须支持深层刷新，有两个选择：改造 `router` 用 `createWebHashHistory`（URL 变 `/#/articles`，
改动最小），或加一条"非 `/api/**` 且无后缀则 forward 到 `/index.html`"的规则（要小心别把
统一 404 冲掉）。**这两条都不在本步做**，留给 S21~S23 的部署章节按需决定。
