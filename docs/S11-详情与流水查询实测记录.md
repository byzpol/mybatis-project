## 二、关键设计决策

### 2.1 详情 VO **继承** `CmsArticleVO`，不重写 17 个字段

详情 = 列表项的全部字段 + 正文 + 驳回意见 + 审核流水。
若另起一个类把字段抄一遍，就出现两个"文章展示字段"的定义，
以后加字段要改两处、漏一处就**静默不一致**。
契约 §5.3 也是 `ArticleDetailVO extends ArticleVO`。

⚠️ 继承时必须写 `@EqualsAndHashCode(callSuper = true)`：
否则 Lombok 生成的 `equals` 会忽略父类字段，两个 id 相同但标题不同的 VO 会被判"相等"。

### 2.2 ⚠️ 详情 VO **不带** `versions` 字段（契约 §5.3 里有）

理由是**先去看前端到底怎么用**：`frontend/src/views/article/ArticleDetail.vue` 第 146 行
import 了 `getArticleDetail, listAuditLogs, listVersions, rollbackVersion`，
第 180 / 191 / 208 行**分别**调了详情、流水、版本三个接口 ——
它并不读 `detail.versions`。

> **没有消费者的字段不填。** 为它多查一张表是把响应时间花在没人看的地方。
> 版本功能要到 S15 才做，届时若确实需要"详情一并带版本"再加字段不迟。

### 2.3 ⚠️ 出参字段名跟 **F05 的组件**走，不跟契约

契约 §5.3 把流水字段叫 `auditAction` / `auditOpinion`，
但 `frontend/src/components/AuditTimeline.vue` 第 11~16 行声明的数据形状是：

```
auditStage:     1 | 2,
auditorName:    '李编辑',      // 审核人昵称（后端拼好，前端不做二次查询）
result:         1 | 2,
opinion:        '内容结构清晰',
auditTime:      '2026-10-01 09:30:00',
articleVersion: 2
```

**F05 已经按这套写完了**（并且它的注释明确写着"后端拼好，前端不做二次查询"）。
本步按 `result` / `opinion` 出参，与组件**逐字对齐**。
改契约比改已经验过的组件更划算，但**契约文档本身需要同步**（见 §四）。
另外该组件**不需要** `auditorRole`，所以本 VO 不提供。

### 2.4 `auditLogs` 按 `auditTime` **正序**（手册说倒序，不采纳）

- 契约 §5.3 的字段注释是"审核流水（按时间正序）"；
- `frontend/src/api/modules/article.js` 的 `listAuditLogs` 注释也写"按时间正序"；
- **展示用的倒序前端已经自己做了**：`AuditTimeline.vue` 第 166 行的 `sortedRecords`
  明确写着"按时间倒序排（最新在上）"并自己 `sort` 了一遍。

所以后端返正序时，界面仍然是"最新在上"——
手册那个核查项（"顺序与时间倒序正确"）**在界面层面满足，在接口层面按契约返正序**。

### 2.5 ⚠️ `ORDER BY audit_time ASC, id ASC` —— 第二排序键不能省

库表 `audit_time` 是 `DATETIME`（**秒精度，没有小数位**）。
主链路自测里"提交 → 初审 → 终审"往往发生在**同一秒内**
（真机实测：270 号文章 5 条流水全部落在 `22:35:43` ~ `22:35:45`），
只按 `audit_time` 排序时这几条时间完全相同，MySQL 返回顺序**不确定**，
"第一条是不是初审"这类断言会**偶发失败** —— 最难查的一类问题。
加 `id`（自增，天然等于插入顺序）作第二键后顺序就确定了。

真机 SQL 末尾可见：`... ORDER BY audit_time ASC,id ASC`。

### 2.6 四条 SQL 的构成，以及"为什么不是 N+1"到底该看什么

| # | SQL | 条件 |
|---|---|---|
| ① | `cms_article` selectById | 总是 |
| ② | `cms_article_audit_log` selectList | 总是 |
| ③ | `sys_user` **selectBatchIds**（作者 ∪ 审核人，去重） | 集合非空 |
| ④ | `cms_category` selectById | `categoryId` 非空 |

真机实测：**流水 0 条和 5 条时都是 4 条 SQL**。
"这次跑了 4 条"本身证明不了什么，**"条数不随审核次数增长"才是判据**。
最硬的一条证据是日志里的 `sys_user WHERE id IN ( ? , ? , ? )` ——
5 条流水、2 个审核人 + 1 个作者，**一条 IN 查回来**；
若逐条查审核人，这里会出现 5 条 `sys_user`。

### 2.7 `listAuditLogs` **保留** `requireArticle` 检查

不加的话，对不存在的 id 会返回"空流水"，
前端会显示"文章不存在但审核历史为空"这种**自相矛盾**的页面。
代价是多一条 SQL（该接口实测 3 条）。真机实测 `/articles/99999999/audit-logs` → **11001**。

### 2.8 `rejectReason` 取"最近一次**驳回**意见"，不是"最后一条流水的意见"

终审通过之后最后一条流水的意见是"终审通过，同意发布"，
直接取最后一条会把"同意发布"当成驳回原因展示。
实现是**从后往前找第一条 `result = 2`**。

也**不**判断"这条驳回是否已被后续提交覆盖"：前端只在 `status = REJECTED` 时展示它，
而已驳回状态下最后一条驳回意见必然就是当前要改的原因 ——
多写一层判断只会多一个出错的地方。
真机实测（271 号，已驳回）：`rejectReason = 结构混乱，请重写` ✔

### 2.9 `selectNicknames` 空集合必须**提前返回**

`selectBatchIds(空集合)` 生成的是 `WHERE id IN ()`，
这在 MySQL 里是**语法错误**（不是"查不到"）。
草稿文章没有任何审核流水时正好会走到这个分支 —— 很容易漏。

### 2.10 脏状态码兜底，不让一条脏数据把详情 500

`ArticleStatus.ofNullable(99)` 返回 null → `statusDesc` 给"未知状态"、`statusColor` 给 `info`，
`status` 原样返回（前端可能需要看到实际值以便排查）。
测试 `testDetailWithDirtyStatusDoesNotThrow` 直接 UPDATE 一个 99 进库验证。

### 2.11 查询接口**不记操作日志**

`GET /{id}` 与 `GET /{id}/audit-logs` 都不加 `@OperLog`。
真机查库验证：`sys_oper_log` 里 `oper_desc` 含"详情/流水"的记录 **0 条**，
本轮只有写操作（新建草稿/提交/登录/审核/修改草稿）。

### 2.12 新建的 `CmsCategory` 是**最小实体**，不是分类模块

只为了承接"详情要显示分类名"这一件事（`selectById`）。
分类的完整 CRUD 属其他成员主责，本步**不越界**。
实体里特别标注了列名是 `category_name` 而不是 `name`。

## 三、本步实测抓到的问题

### 3.1 ⚠️ 我第一版注释里的 SQL 条数结论是**错的**

`getDetail` 的第一版 Javadoc 写着：

> ⚠️ 流水查不到时（草稿还没提交过）③④ 会相应减少，所以实测可能只有 3 条

**真机实测：空流水草稿也是 4 条。** 原因是 ③ 的集合里**永远至少有"作者"**
（`authorId` 非空），所以 `sys_user` 那条查询省不掉 ——
而作者名正是详情页要显示的东西，省掉反而是错的。
真正会出现 3 条的唯一情形是 ④ 也省掉，即 `categoryId = null`。

**已改正**注释，并写明"把 4 条当常数来断言"。
这个错误如果不做真机 SQL 计数就发现不了 —— 它只在文档里，不影响运行，
但会把后面接手的人带偏。

### 3.2 联调脚本自己的两处判据错误（不是产品问题）

第一轮脚本 PASS=12 / FAIL=2，两条 FAIL 全是脚本写错：

| 现象 | 根因 | 修正 |
|---|---|---|
| "无流水草稿详情 = 3 条" 期望不成立 | 沿用了我那条错误注释的预期 | 改成预期 4 条 |
| "独立接口流水条数 = 5" 实际 10 | `grep -o '"auditStage":\|"result":'` 把两个字段都数了（5×2=10） | 只数 `"auditStage":` |

修正后重跑 **PASS=14 / FAIL=0**。
> 教训与 F02/F03 一致：**断言失败先确认"我以为的判据"是不是本身就错的。**

### 3.3 一个只能靠真机发现的差异：`create_by` 是 0 还是真实用户

JUnit 里 `cms_article_audit_log.create_by` 是 **0**，
真机上是 **2（编辑）/ 3（主编）**。
原因是审计字段靠 `MetaObjectHandler` 从**登录态**取当前用户，
JUnit 直接调 Service 没有 HTTP 请求上下文。
**"审计填充"这件事只有真机才验得准。**
