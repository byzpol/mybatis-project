| 跑法 | `node docs/evidence/F03-cdp-verify.mjs`（脚本里 OUT_DIR / Chrome 路径是当时的绝对路径，换机器要改） |

> **为什么不是 vite dev server**：本环境下 vite dev server 的依赖预构建要批量删除
> `node_modules/.vite/deps_temp_*`（80 个文件），被 CLI 的批量删除保护
> （`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，阈值 50）打断进程，服务几十秒后猝死。
> `vite build` 不走依赖预构建所以一直正常。改用真实 war 反而更好：这是交付物的真实形态。
>
> **已知限制（S22 才修）**：SPA 用 `createWebHistory`，Tomcat 没有"未匹配路径回退 index.html"
> 的配置，所以**直开/刷新子路由会 404**。因此脚本里所有路由切换都靠"加载 `/cms-mis/`
> → 页面内程序化导航"完成，不做深层路径的整页加载；最后专门断言一次这个 404，
> 作为交给 S22 的证据。

## 三、bug 1：`baseURL` 少上下文路径 —— CDP 抓包铁证

**症状**：war 部署后，登录页输入正确账号口令点登录，**完全静默**（不报错、无提示、
表单无校验错误、按钮 loading 正常收回、无遮罩残留）。

脚本里的诊断分支（登录失败时自动打开 `Network.enable` 抓包并打印）输出：

```
诊断(网络): ["→ POST http://localhost:8080/api/v1/auth/login",
            "← 404 http://localhost:8080/api/v1/auth/login"]
```

**URL 里没有 `/cms-mis`** —— 后端 context path 是 `/cms-mis`，前端却打到了 `/api/v1/...`。

同一时刻的页面诊断显示"什么都没有"，正是这种"全静默"最容易把人引向错误方向：

```json
{
  "path": "/cms-mis/login",
  "messages": [],
  "formErrors": [],
  "inputs": ["chief", "123456"],
  "btnDisabled": false,
  "overlay": false
}
```

**修复**：`baseURL: ${import.meta.env.BASE_URL}api/v1`。修后登录成功，52 项断言全过。

> 为什么 F02 没抓到：F02 在 vite dev 环境验的，`BASE_URL='/'`，拼出来仍是 `/api/v1`，
> dev 下永远正确。**只有真机部署才暴露。**

## 四、bug 2：`Set-Cookie` 的 Path 不匹配 —— 修复前后响应头对比

**修复前**（dev 经 proxy）：

```
Set-Cookie: JSESSIONID=xxxxxxxx; Path=/cms-mis; HttpOnly
```

页面在 `localhost:5173`，发出去的请求路径是 `/api/v1/auth/login`，匹配不上 `Path=/cms-mis`
→ 浏览器丢弃该 Cookie。症状：**登录接口 200 且有 `Set-Cookie`，下一个请求就是 401。**

**修复后**（proxy 把 Path 改写为 `/`）：

```
set-cookie: JSESSIONID=xxxxxxxx; Path=/; HttpOnly
```

登录后能正常携带会话，`/auth/me` 恢复登录态断言通过：

```
PASS  带 Session 整页加载 /cms-mis/ 后仍是登录态（/auth/me 恢复成功）
```

## 五、4.5 节的 DOM 诊断：为什么两条断言"看起来失败了"

折叠态下侧边栏的真实 DOM（最小诊断脚本原样输出，节选）：

```json
{
  "asideW": 64,
  "menuCollapsed": true,
  "icons": [
    { "cls": "el-icon", "centerX": 32, "display": "flex", "offsetW": 18 },
    { "cls": "el-icon el-sub-menu__icon-arrow", "centerX": 0, "display": "none", "offsetW": 0 },
    { "cls": "el-icon", "centerX": 32, "display": "flex", "offsetW": 18 },
    { "cls": "el-icon el-sub-menu__icon-arrow", "centerX": 0, "display": "none", "offsetW": 0 },
    { "cls": "el-icon", "centerX": 32, "display": "flex", "offsetW": 18 },
    { "cls": "el-icon el-sub-menu__icon-arrow", "centerX": 0, "display": "none", "offsetW": 0 }
  ],
  "bars": [
    { "cls": "el-scrollbar__bar is-horizontal", "display": "none", "offsetW": 0, "offsetH": 0 },
    { "cls": "el-scrollbar__bar is-vertical",   "display": "none", "offsetW": 0, "offsetH": 0 }
  ],
  "wrap": { "scrollW": 64, "clientW": 64, "overflowX": "hidden" },
  "wrapScrollbarH": "none"
}
```

**读法**：

1. 真图标 `centerX` 全是 **32**（64px 侧栏正中）→ 图标**本来就是居中的**；
   那个 `0` 来自 `.el-sub-menu__icon-arrow`（子菜单箭头），折叠态被 EP 设成
   `display:none`，而 `getBoundingClientRect()` 对隐藏元素返回**全 0 矩形**。
2. 横向 bar **本来就是隐藏的**（`display:none`、`offsetW=0`）。它一直存在于 DOM 里
   （EP 的 Scrollbar 用 `v-show` 控制显隐），所以"`querySelector` 能查到"根本不能当判据。
3. `wrap.scrollW === clientW === 64`，`overflow-x: hidden` → 无横向溢出。

**结论**：功能没问题，是**断言判据写错了**。修正为"看 computed display + 滤掉零尺寸元素"后：

```
PASS  折叠态菜单图标水平居中（中心 ≈ 32px）  [32,32,32]
PASS  侧边栏内无横向溢出内容  overflowX=0 hbar=false
```

> 排查用的最小诊断脚本（`diag-narrow.mjs`）与验证脚本同为一次性的，
> 已在验证结束后随 `target/f03-check/` 一起删除；本文保留了它的关键输出。
