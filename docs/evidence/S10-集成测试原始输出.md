## 3. 四条最关键的原始证据（逐条说明证明了什么）

### 3.1 `[S10] 事务验证通过：流水写入失败 → 状态回滚，流水 0 条`

证明"改状态"与"写流水"处在**同一个事务**里，而且**这条不变式是被真正验证过的**，不是"看起来应该没问题"：

| 细节 | 说明 |
|---|---|
| 触发方式 | 传 600 字 `auditOpinion`；库表 `opinion VARCHAR(500)`，本机 `sql_mode` 含 `STRICT_TRANS_TABLES` → MySQL 报错误 1406 |
| 实际异常 | `org.springframework.dao.DataIntegrityViolationException` |
| 断言一 | 状态仍为 `PENDING_EDITOR(1)` —— 说明**前一步已经执行成功的状态更新被回滚了** |
| 断言二 | 流水 0 条 —— 失败的那次没有留下半条记录 |

**为什么这条证据成立与否，取决于实现里"先改状态、后写流水"的顺序**：
若按手册顺序（先流水后状态），这个失败点发生在任何写操作之前，"状态有没有被回滚"就无从检验。

### 3.2 `[S10] 初审通过：…（stage=1,result=1,auditor=2,articleVersion=2）` 与 `[S10] 终审通过：… 累计流水 2 条（stage 序列 = [1, 2]）`

这两条一起证明**"环节由状态反推"是真的**：两次调用的是**同一个方法** `audit(...)`，
唯一的差别是文章当前状态不同；写出来的 `audit_stage` 分别是 1 和 2。
若环节判断写错（比如恒为 1），这两条必有一条失败。

顺带证明 `articleVersion` 的口径：值是 **2**（业务快照号 = 创建草稿 1 + 提交初审 2），
**不是** `cms_article.version`（乐观锁号，此时是 1）。见 §3.3。

### 3.3 `[S10] article_version 口径正确：流水记 2（业务快照号），而非乐观锁号 1`

写这条测试是因为这两个字段极易混：

- `cms_article.version`：MP 乐观锁号，每次 UPDATE +1；
- `cms_article_version.version_no`：业务快照号，创建草稿=1、改一次+1、提交再审+1。

`cms_article_audit_log.article_version` 的库表注释写明对应后者。
测试先断言"提交后最大快照号=2 且乐观锁号=1"，再断言流水里记的是 **2** ——
如果实现里误取了乐观锁号，这条会失败。

### 3.4 `[S10] 驳回→改稿→再提交→再初审 走通；同一环节累计 2 条流水（result 序列 = [2, 1]）`

这是本步**最重要的一条证据**，它证明的是一个**"不做某事"的决定**：

- `CmsArticleAuditLog` 的类注释把"防重复审核"描述为"查 `(article_id, audit_stage)` 是否存在，有则拒绝"。
- **按字面实现会打断主链路**：走完"驳回 → 改稿 → 再提交"之后，该文章在 `audit_stage=1` 上
  已经有了一条历史流水，存在性检查会把合法的第二次初审误判成重复审核。
- 实现里**没有**加这个检查（理由：状态机已经足够，且流水是"历史"、状态是"现在"）。
- 这条测试把 result 序列 `[2, 1]`（先驳回后通过）与"同一环节 2 条流水"都钉住 ——
  将来若有人照类注释补上存在性检查，这里立刻红。
