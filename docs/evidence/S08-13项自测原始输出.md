## 7. 业务异常 → 11001（不是 500）

```
POST /cms-mis/api/v1/system/selftest/exception?mode=1     （带登录 Cookie）

HTTP 200
{"code":11001,"message":"文章不存在","timestamp":1791607272668}
```

**结论**：HTTP 状态码为 200 是正确的 —— 业务码 `11xxx` 属于"请求合法但业务被拒"，
`GlobalExceptionHandler#writeStatus` 只把 `100~599` 范围内的码同步到 HTTP 状态码，
`11xxx` 保留在响应体 `code` 中。客户端据此能给出精确提示，而不是笼统的"服务器错误"。

## 8. 系统异常 → 500 且不泄漏堆栈

```
GET /cms-mis/api/v1/health/boom      （故意触发 NullPointerException，带登录 Cookie）

HTTP 500
{"code":500,"message":"系统内部错误，请联系管理员","timestamp":1791607273404}
```

**结论（本项最关键）**：响应体中
- **没有** `java.lang.NullPointerException`
- **没有** 类名、方法名、行号
- **没有** 文件路径、SQL 语句
- **没有** `data` 字段（null 未被序列化，说明 Jackson 配了 `NON_NULL`）

真实堆栈只写在 `logs/cms-error.log`。对照如下（本轮 `logs/cms.log` 中的 ERROR 记录）：

```
2026-10-10 12:41:13.402 [http-nio-8080-exec-2] ERROR c.l.c.c.exception.GlobalExceptionHandler - 系统异常 | GET /cms-mis/api/v1/health/boom
```

以及 `logs/cms-error.log` 中含完整堆栈（`at org.apache.tomcat.websocket.server.WsFilter.doFilter(...)`
一路到 `at java.base/java.lang.Thread.run(...)`）。

> **本轮 cms.log 的 ERROR 计数 = 1，恰好就是这条故意异常** ——
> 说明除它之外没有任何其它系统异常发生。

## 10. 排序字段注入防护

```
GET /cms-mis/api/v1/health/page-echo?sortField=create_time; DROP TABLE cms_article
（实际请求经 --data-urlencode 编码，带登录 Cookie）

HTTP 400
{"code":400,"message":"排序字段非法：create_time; DROP TABLE cms_article（只允许字母、数字、下划线，且不能以数字开头）","timestamp":1791607274745}
```

**结论**：注入样本被正则白名单挡下，返回 400 并**在消息里回显了非法输入**（便于排查），
没有走到 SQL 层，因此**不存在 SQL 语法错误**，更不存在注入。

## 11. 数据层往返自测（覆盖手册第 11、12、13 项）

```
POST /cms-mis/api/v1/health/db-roundtrip      （带登录 Cookie）

HTTP 200
{"code":200,"message":"数据层往返验证完成","data":{
  "insert":{
    "rows":1,
    "id":40,
    "createBy":4,
    "createTime":"2026-10-10 12:41:15",
    "updateBy":4,
    "updateTime":"2026-10-10 12:41:15",
    "handlerWorked":true,
    "caveat":"createTime/updateTime 有数据库 DEFAULT 兜底，非空不代表填充生效；以 createBy/updateBy 是否非空为准"
  },
  "updateNoWhere":{
    "blocked":true,
    "exceptionType":"org.mybatis.spring.MyBatisSystemException",
    "message":"nested exception is org.apache.ibatis.exceptions.PersistenceException: \r\n### Error updating database.  Cause: com.baomidou.mybatisplus.core.exceptions.MybatisPlusException: Prohibition of table update operation\r\n### The error may exist in com/lab/cms/mapper/SysOperLogMapper.java (best guess)\r\n### The error may involve com.lab.cms.mapper.SysOperLogMapper.update\r\n### The error occurred while executing an update\r\n### Cause: com.baomidou.mybatisplus.core.exceptions.MybatisPlusException: Prohibition of table update operation"
  },
  "logicDelete":{
    "deleteRows":1,
    "hiddenFromQuery":true,
    "note":"行仍在库中，deleted 已置 1；验证用：SELECT id,deleted FROM sys_oper_log WHERE id = 40"
  },
  "testTag":"[S08-TRUNK-TEST]",
  "testRecordId":40
},"timestamp":1791607275451}
```

### 11.1 审计字段自动填充（手册第 11 项）

`createBy=4`、`updateBy=4`（4 = admin 的 userId），`handlerWorked=true`。

⚠️ 注意这里只把 `createBy/updateBy` 当作硬指标：库表里
`create_time`/`update_time` 是 `NOT NULL DEFAULT CURRENT_TIMESTAMP`，
数据库会兜底填充，**即使 `MetaObjectHandler` 失效它们也非空**。

### 11.2 防全表更新（手册第 13 项）

`blocked=true`，异常链最终原因为：

```
com.baomidou.mybatisplus.core.exceptions.MybatisPlusException: Prohibition of table update operation
```

即 `BlockAttackInnerInterceptor` 生效，不含 WHERE 的 UPDATE 在执行前被拦下。

### 11.3 逻辑删除（手册第 12 项）

`deleteRows=1`（删除语句生效）、`hiddenFromQuery=true`（`selectById` 返回 null）。

**行还在库里的证据**：自测结束后执行物理删除

```sql
DELETE FROM sys_oper_log WHERE oper_desc LIKE '[S08-TRUNK-TEST]%';
-- 返回：deleted_rows = 1     ← 物理删除能删到它，说明逻辑删除没有真的删掉行
SELECT COUNT(*) FROM sys_oper_log WHERE oper_desc LIKE '[S08-TRUNK-TEST]%';
-- 返回：0                    ← 测试数据已清理干净
```
