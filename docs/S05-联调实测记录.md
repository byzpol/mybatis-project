## 三、⚠️⚠️ 四个真实踩坑（本阶段最有价值的产出）

### 坑 1：演示数据的 BCrypt 哈希是"编"出来的 —— 登录永远失败

**现象**：`POST /auth/login` 返回 `{"code":13003,"message":"用户名或密码错误"}`，
但库里 `sys_user.password` 明明是 60 位、`$2a$10$` 开头的合法 BCrypt 格式。

**根因**：`init.sql` 里的演示哈希是**凭自然语言手感写出来的字符串**，
格式像 BCrypt，但**不是任何密码的哈希**。用 `BCryptPasswordEncoder.matches()` 实测：

```
123456          -> false
admin           -> false
12345678        -> false
<本机 MySQL root 口令>  -> false
```

全部 false —— 这个哈希根本无法匹配任何明文。

> 注：这里原本还顺手把本机 MySQL 的口令也丢进去试了一遍，
> 写文档时那个明文已经抹掉。数据库口令属于凭据，
> 不能出现在任何入库文件里（包括文档），这条自己也要守。

**排查手法**（值得记住）：单独写一个 main 方法，用项目同版本的
`BCryptPasswordEncoder` 直接 `matches()` 测试，一眼定性。

**修复**：用 BCrypt **真实生成**哈希，再 UPDATE 回库：

```java
// 用 BCryptPasswordEncoder.encode() 生成，每次随机盐 → 五个账号哈希互不相同
BCryptPasswordEncoder e = new BCryptPasswordEncoder();
e.encode("123456");   // → $2a$10$LiulYA8oOJl5li1xTRJfauzp5uaE79d8FtPVCruuqhBQgDwnt51KW
```

**教训（写进规范）**：
> **演示数据的密码哈希绝不能手写。** 必须用目标框架的编码器真实生成后粘贴。
> 否则"格式对、语义错"，登录永远失败的这种 bug 会消耗大量排查时间，
> 且因为是"看起来对的数据"，所有人都会先怀疑代码而不是数据。

**已同步修复**：`sql/init.sql` 的演示账号段落需替换为真实哈希（见该文件"演示账号"注释）。

### 坑 2：`strictUpdateFill` 在 MP 3.5.5 下对 `updateById` 不生效

**现象**：登录成功但接口返回 500：

```
Column 'update_time' cannot be null
SQL: UPDATE sys_user SET last_login_time=?, update_by=?, update_time=? WHERE id=? AND deleted=0
参数: 2026-10-08T17:41:53(non-null), null, null, 4
```

**根因**：`AuditMetaObjectHandler.updateFill()` 里用了 `strictUpdateFill`。
MP 3.5.5 在 `updateById` 组装 SET 子句时，会把带 `FieldFill.INSERT_UPDATE` 策略的列
**提前纳入更新列表**，导致 `strictFill` 的"仅当为 null 才填"判定被绕过。

**修复**：UPDATE 分支改用 **无条件覆盖** 的 `setFieldValByName`：

```java
// ❌ 失效
strictUpdateFill(metaObject, FIELD_UPDATE_TIME, LocalDateTime.class, LocalDateTime.now());
// ✅ 有效
setFieldValByName(FIELD_UPDATE_TIME, LocalDateTime.now(), metaObject);
```

**为什么覆盖是正确语义**：`update_time` 本就表示"本次操作的时间"，
不存在"尊重调用方传入的值"这个诉求。而 INSERT 侧仍用 `strictInsertFill`，
以保留"数据初始化时显式指定 createTime"的能力（如灌入"过去 3 天的文章"用于演示排序）。

### 坑 3：`MetaObjectHandler` 在纯 SSM 下不会自动生效（**最隐蔽**）

**现象**：所有 `insert` 都抛 `Column 'create_time' cannot be null`，
四个审计字段（`create_by`/`create_time`/`update_by`/`update_time`）在 SQL 参数里**全是 null**。

**错误认知**（我最初写进 `MybatisConfig` 注释的）：
> "MP 的自动填充依赖 MetaObjectHandler 实现类（加 @Component 被扫描到即可），此处无需额外开关。"

**这是 Spring Boot 下的错觉。** `mybatis-plus-boot-starter` 的自动配置
会帮你把容器里的 `MetaObjectHandler` Bean 塞进 `GlobalConfig`；
但本项目是**纯 SSM**（手动 new `MybatisSqlSessionFactoryBean`，无 starter），
MP **不会**主动去 Spring 容器里找，不显式 `set` 就等于没写这个填充器。

**修复**：显式注入并设置：

```java
@Bean
public SqlSessionFactory sqlSessionFactory(DataSource dataSource,
                                           MybatisPlusInterceptor interceptor,
                                           AuditMetaObjectHandler auditHandler) throws Exception {
    ...
    factoryBean.setGlobalConfig(globalConfig(auditHandler));   // ← 必须传进去
}

private GlobalConfig globalConfig(AuditMetaObjectHandler handler) {
    GlobalConfig gc = new GlobalConfig();
    ...
    gc.setMetaObjectHandler(handler);   // ← 这一行就是修复点
    return gc;
}
```

**排查难点**：这个 bug 的日志表现极具误导性——
`WebLogAspect` 的 catch 里打印的是 `e.getMessage()`，
而 `DataIntegrityViolationException` 经 MyBatis-Spring 翻译后 **`getMessage()` 是空串**，
日志只显示 `操作日志写库失败（已保留文件日志） | 原因=`，原因字段是空的。
很容易误判成"表结构问题"或"字段长度问题"。

**连带修复**：所有 `catch` 块改为传异常对象（`log.warn(msg, e)`）而不是只拼 `e.getMessage()`，
让堆栈进日志。

### 坑 4：双容器下，加在 Controller 上的切面**静默失效**

**现象**：`@OperLog` 注解写对了、编译打包都正常，
但接口调用后 `sys_oper_log` **没有新记录**，Tomcat 日志里**连切面的一行输出都没有**。

**根因**：本项目是**双容器**结构：

| 容器 | 配置类 | 扫描范围 | 存放 |
|---|---|---|---|
| 根容器 | `SpringConfig` | `com.lab.cms`，**排除** `@Controller` / `@EnableWebMvc` / `@Aspect` | Service、Mapper、基础设施 |
| 子容器 | `SpringMvcConfig` | 只扫 `@Controller` | 全部 Controller |

`@EnableAspectJAutoProxy` 写在**根容器**，它注册的 `AnnotationAwareAspectJAutoProxyCreator`
是**容器级**后置处理器 —— **只代理本容器内的 Bean**。
Controller 是子容器的 Bean，根容器的后置处理器**根本管不到**，
于是 Controller 方法上的 `@OperLog` / `@RequirePermission` 全部形同虚设。

**最坑的地方**：这个 bug **不报错、不警告**，只是功能静默失效。
而且如果只用 admin（他有全部权限）测试，连 `@RequirePermission` 失效都发现不了 ——
**必须用 author 测越权才能暴露**。这也是"要有多角色测试账号"的实战理由。

**修复**（两处，缺一不可）：

```java
// SpringMvcConfig.java（子容器）
@EnableAspectJAutoProxy                                    // ← 子容器也要开 AOP
@Import({WebLogAspect.class, PermissionAspect.class})     // ← 切面显式引入子容器
public class SpringMvcConfig implements WebMvcConfigurer { ... }

// SpringConfig.java（根容器）
excludeFilters = {
    ...,
    // 切面统一由 SpringMvcConfig 导入子容器，避免同一份切面在两容器各注册一次
    @ComponentScan.Filter(type = FilterType.ANNOTATION,
                          classes = org.aspectj.lang.annotation.Aspect.class)
}
```

> 根容器的 `@EnableAspectJAutoProxy` **保留** —— 服务于未来可能加在 Service 方法上的
> `@OperLog`（如 S13 的定时发布任务）。两处都开是刻意设计，不是重复。

## 四、附带修正：HTTP 状态码需与业务码一致

**原设计缺陷**：`GlobalExceptionHandler` 所有 handler 都返回 `Result`，
导致 **HTTP 状态码恒为 200**，错误只写在响应体的 `code` 字段。这是常见反模式，有三个硬伤：

1. **前端拦截器无法工作** —— axios 的 `validateStatus` 默认只认 2xx，业务错误走 200
   会导致"成功"与"业务失败"混在同一个分支里判断。
2. **网关/监控失明** —— Nginx、SLB、APM 的错误率统计基于 HTTP 状态码，
   一个 401 横飞的系统在监控里显示"100% 成功率"。
3. **缓存与重试语义错乱** —— 中间层无法区分"请求成功但业务失败"与"请求本身失败"。

**修复**：新增 `writeStatus(HttpServletResponse, int)` 工具方法，每个 handler 显式调用：

```java
private void writeStatus(HttpServletResponse response, int code) {
    if (code >= 100 && code <= 599) {   // 业务码 10xxx~14xxx 不映射（会回退为 200）
        response.setStatus(code);
    }
}
```

**映射规则**（实测确认）：

| 异常类型 | HTTP 状态 | 响应体 code |
|---|---|---|
| 未登录（`LoginInterceptor` / `UNAUTHORIZED`） | **401** | 401 |
| 越权（`PermissionAspect`） | **403** | 403 |
| 参数校验失败 | **400** | 10001 |
| 方法不支持 | **405** | 405 |
| 媒体类型不支持 | **415** | 415 |
| 系统异常（兜底） | **500** | 500 |
| 业务异常（状态机非法流转等） | **200** | 11001 / 11002 / … |

> 最后一行的设计意图：业务码 11xxx/12xxx 这类**本身就是业务语义**，
> 不是 HTTP 协议层错误。用 200 + 业务码表达"请求合法但业务被拒"是准确的。
> `writeStatus` 对超出 100~599 的值自动回退，不会把 11001 当状态码写出去。

## 八、可直接复用的排障口诀（写给三个月后的自己）

1. **"看起来对的哈希"最危险** —— 密码类数据必须用真实编码器生成并实测 `matches()`。
2. **MP 在纯 SSM 下不会自动发现 `MetaObjectHandler`** —— 必须 `globalConfig.setMetaObjectHandler(...)`。
3. **UPDATE 侧用 `setFieldValByName`，别用 `strictUpdateFill`** —— 后者在 `updateById` 下会被绕过。
4. **双容器里，Controller 上的切面必须在子容器开 AOP** —— 否则静默失效，且只有多角色测试才能发现。
5. **`DataAccessException.getMessage()` 可能是空串** —— 打日志一律传异常对象，别只拼 message。
6. **异常处理要让 HTTP 状态码跟随语义** —— 别做"HTTP 恒 200"的系统。
