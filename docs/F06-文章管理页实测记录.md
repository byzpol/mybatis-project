## 二、为什么把「状态 + 权限 → 动作」抽成独立文件

这是本步唯一一个"看起来多此一举"的决定，理由必须写清楚。

### 2.1 不抽出来就没法验证

F06 阶段后端 `ArticleController` 还没建（S09 才写），
`GET /api/v1/articles` 是 404 —— **列表页一行数据都没有**（F03 建的占位页也无从谈起）。
而 F06 的头号核查项恰恰是「操作列按钮随状态与权限正确变化」。

如果这段逻辑写在 `ArticleList.vue` 的模板里（`v-if="row.status===0 && hasPermission(...)"`），
在这个阶段**唯一能验证的方式就是用肉眼看代码** —— 而"用肉眼看代码"正是这一轮要避免的。

抽成纯函数之后：
- 它不 import Vue、不 import pinia、不碰 axios，**脱离浏览器就能逐条断言**；
- `getRowActions(article, hasPermission)` 把权限判断做成**传入的函数**而不是直接读 store，
  于是可以伪造任意角色的权限集合（10 状态 × 4 角色 = 40 组合）。

结果：`F06-actions-matrix.mjs` **118 项断言全过**（明细见 §6.1）。

### 2.2 规则只写一张表

动作集合完全由 `RULES`（状态 → 动作 key 顺序）与 `ACTION_META`（动作 → 权限码 / 文案 / 是否危险）两张表决定。
要加一个动作只改这两张表，不需要在模板里找散落的 `v-if`。

### 2.3 `SCHEDULED(6)` 与 `ARCHIVED(9)` 的特殊性

`RULES[6] = ['view']`、`RULES[9] = ['view']` 看着像漏写了，其实是从状态机推出来的：

- `SCHEDULED(6)` 只有一条出边 `PUBLISH_SCHEDULED_TRIGGER`，而它是**定时任务触发的**，
  不是人点的按钮 → "定时发布中"的文章没有人工动作（不能撤回、不能下架）。
  要支持"取消排期"，得先给状态机加迁移，而不是只在前端加个按钮。
- `ARCHIVED(9)` 是终态，没有任何出边 → 只读。

## 三、⚠️ 本步查出的一处真实错误：**已下架不能「重新发布」**

这是本轮最值得记的一条 —— 它同时出现在**手册**和**我先前写的实现**里。

### 3.1 事实

逐行读了 `common/ArticleStateMachine.java` 的静态迁移表（第 112~159 行），
14 条合法迁移的**最后两条**是：

```java
// ---------- 13~14. 归档（两条路径，都到终态）----------
map.put(key(ArticleStatus.WITHDRAWN, ArticleAction.ARCHIVE), ArticleStatus.ARCHIVED);
map.put(key(ArticleStatus.OFFLINE,   ArticleAction.ARCHIVE), ArticleStatus.ARCHIVED);
```

也就是说 **`OFFLINE(8)` 只有 `ARCHIVE` 一条出边，没有 `PUBLISH_NOW`**。
（`PUBLISH_NOW` 在已撤回态有：`WITHDRAWN(7) + PUBLISH_NOW → PUBLISHED(5)`。）

而手册 F06 写的是：

> · 已撤回/已下架 → 查看、重新发布、归档

**「已下架 → 重新发布」在状态机里不存在。**

### 3.2 为什么必须改前端而不是"先加上去"

如果前端照手册下发一个「重新发布」按钮，用户点下去会命中：
`ArticleStateMachine.assertTransfer(OFFLINE, PUBLISH_NOW)` → 抛 `11003（文章状态非法）`。
**界面给了一个必然失败的按钮**，比少一个按钮糟糕得多 ——
用户会以为是系统坏了，而不是"这个操作不允许"。

### 3.3 处理

- `RULES[8]` 从 `['view','republish','archive']` 改成 `['view','archive']`；
- `PRIMARY[8]` 从 `'republish'` 改成 `'view'`；
- 留了一条**专门的回归断言**（防止以后有人"顺手补回来"）：
  ```
  ok('已下架(8) 不出现 republish（主编）', ...)
  ok('已撤回(7) 主编能看到 republish（对照，说明 7 与 8 确实不同）', ...)
  ```
  以及浏览器里的一条：
  ```
  PASS  ★ 主编在「已下架」行**看不到**「重新发布」（状态机没有 OFFLINE→PUBLISH_NOW）
  PASS  ★ 主编在「已撤回」行**能**看到「重新发布」（对照）
  ```

### 3.4 如果产品上确实要"下架后重新上架"

正确做法是**先给状态机加第 15 条迁移**，并同步三处：

1. `ArticleStateMachine.TRANSITIONS`（以及静态块末尾 `assert TRANSITIONS.size() == 14` 的自检数字）；
2. `ArticleStateMachineTest` 的「合法迁移 14 条」断言；
3. `docs/接口契约.md` 与 `docs/状态机图.md`。

而不是只在前端把按钮加上。**这条已登记为需要组内确认的事项。**

## 四、四个页面的设计取舍

### 4.1 新建与编辑共用一个页面（`ArticleEdit.vue`）

两条路由指向同一个组件：

| 路由 | 名称 | 场景 |
|---|---|---|
| `articles/create` | `ArticleCreate` | 新建，无 id |
| `articles/edit/:id` | `ArticleEdit` | 编辑，带 id，先拉详情回填 |

两者表单字段、校验规则、布局完全一样，唯一差别是提交到哪个接口。
拆成两个文件后每次改字段都要改两处 —— 而漏掉的那一处表现为
"编辑页能存、新建页存进去字段丢了"，很难在自测时发现。

**新建成功后 `router.replace` 到编辑路由**：否则用户再点一次「保存」会走 `saveDraft`，
因为它不是幂等的（后端没做重复提交保护），手快点两下就会建出两篇草稿。

### 4.2 「提交初审时正文必填」不写成表单 `rules`

`CmsArticleSaveDTO` 的注释已经把取舍写清楚了：草稿允许只填标题。
所以"正文必填"只属于**提交流程**，不属于字段本身。

写成 `rules` 会让「保存草稿」也拦住用户；写成 `onSubmitAudit` 里的一次显式判断才对：

```js
if (!form.content || !form.content.trim()) {
  ElMessage.warning('提交初审前请填写正文')
  return
}
```

### 4.3 审核页「环节」不进请求体

手册 F06 写的是 `audit(id, {stage, result, opinion})`，
但契约与 `api/modules/article.js` 都是 `{auditAction, auditOpinion}` 且**不传 stage**。

理由：前端选择的 stage 与库里真实状态可能不一致（比如两个人同时打开页面，一个已经审完了），
后端还得写"以谁为准"的规则。**状态是唯一真相，阶段从状态推出来就不会打架。**

所以「环节」只用于：① 筛选待审队列（`status=1` 或 `status=2`）② 显示标题文案。

环节的默认值不是拍脑袋：库表里 `article:publish` 只授予了主编与管理员，
所以**有 publish 权限的人默认落在终审，编辑默认落在初审**；
同时具备两者（管理员）时顶部才出现切换按钮。

### 4.4 「驳回必须填意见」用置灰按钮，不用"点了再报错"

沿用 F05 的结论：**浏览器不会给 `disabled` 的按钮派发 `click` 事件**，
所以"按钮置灰"和"点击后报错"是两种互斥的校验设计，同时做必然得到死代码。

本页选置灰 + 旁边写明原因，判据也很直白（按钮上的 `disabled` 属性），
自动化脚本可以直接断言 —— 实测四条（§6.2）。

### 4.5 「我的投稿」为什么单独建一个 5 行的文件

`articles/list` 与 `articles/mine` 的差别只有"是否固定按当前用户过滤"。
最省事的做法是两条路由指向同一个组件，但 **Vue Router 在同一个组件用于两个路由时会复用组件实例** ——
从「文章列表」切到「我的投稿」，`onMounted` 不会重新执行，表格里还是原来那批数据，
看起来就像"点了没反应"。

绕开它的常见两招都有副作用：`watch(route)` 会让逻辑分散，给 `router-view` 加 `:key` 会让**所有**页面切路由都重建。
用一层薄封装（`ArticleMine.vue` = `<ArticleList preset-author />`）成本最低，也不打扰任何现有代码。

## 五、踩坑

### 5.1 【视觉缺陷，靠截图发现】状态标签被折成两行

第一轮 95 项断言里有 92 项通过（3 条 FAIL 都是断言写错，见 §6.3），**但截图里有一处问题断言没覆盖**：

`待编辑初审` / `定时发布中` 两个 5 字状态标签，在 110px 宽的状态列里被折成两行，
于是 10 行里有 3 行比其它行高一截，整张表看着毛糙。

修正：
- `StatusTag.vue` 加 `white-space: nowrap`（标签文案是后端定的，前端只能不让它换行）；
- 状态列 `minWidth` 110 → 120。

**并补了 3 条断言把它变成可自动发现的**：

```
PASS  ★ 会话一 状态标签都是单行（高度 ≤ 26px，没有折成两行）
PASS  ★ 会话一 10 个状态标签高度完全一致  [20]
PASS  ★ 会话一 10 行行高完全一致（没有因为某个标签折行而高出一截）
```

> 教训：**"断言全绿"不等于"页面没问题"**。渲染类的问题里，
> 有一类（间距、折行、对齐、颜色搭配）用断言描述起来很别扭，
> 但对人眼来说一秒钟就能看出来 —— 所以截图这一步不能省。

### 5.2 【判据坑】`clientWidth` 不含 border

断言"表格宽度不超过卡片内容宽度"时，我沿用了 F04 时期算出的 `card.clientWidth - 42`
（`padding 20×2 + border 1×2`），实测 FAIL：`1138 / 1136`。

真正的原因是：**`clientWidth` 本身就不包含 border**（只含 padding + 内容），
所以内容宽 = `clientWidth - 40`。改对之后是 `1138 / 1138`，正好铺满。

> 与 F03「元素存在 ≠ 元素可见」、F04「量错了滚动容器」是同一类错误：
> **先确认自己量的是哪个盒子，再比大小。**

### 5.3 【判据坑】下拉选项在 DOM 里全都存在

断言"状态下拉有 10 个选项"时拿到了 **28** 条。
原因是页面上同时存在 4 个下拉的**全部选项**：

| 下拉 | 选项数 |
|---|---|
| 分类 | 9 |
| 状态 | 10 |
| 作者 | 5 |
| 每页条数 | 4 |
| 合计 | **28** |

el-select 的选项随组件一起渲染进 DOM，只是被外层 popper 藏起来。
所以"取 `.el-select-dropdown__item`"拿的是全部。

修法：判据加 `offsetParent !== null`（`display:none` 的祖先会让 `offsetParent` 变 `null`），
也就是"这个选项真的可见"。

> 顺带：那 28 条里状态那一段**完全正确**（草稿…已归档 10 条，顺序与 `STATUS_OPTIONS` 一致），
> 说明组件没问题，只是断言选错了范围。

### 5.4 【模板真错误】双引号套双引号会把 HTML 属性截断

`ArticleList.vue` 里给 `ConfirmAction` 传正文时一度写成：

```html
:content="`...可归档但**不能再重新发布**...`"
```

好在这次是反引号里的模板串，没有截断属性；但**同时犯了一个更隐蔽的错**：
把 Markdown 的 `**加粗**` 写进了会原样显示的确认框文案里 —— 用户会看到字面的两颗星号。

改成纯中文表述：`下架后不能再重新发布，只能归档。`

> 与 F05 的结论合并成一条通用规矩：
> **会原样渲染给人看的字符串（确认框、提示、标题）里，不要写 Markdown 标记。**

### 5.5 【容易漏的模板坑】危险动作的触发点在 `@confirm` 而不是 `@click`

操作列是 `v-for` 出来的，所以模板统一写 `@click="runAction(act.key, row)"`。
但危险动作（删除/下架/归档）包在 `ConfirmAction` 里，
而 `ConfirmAction` **完全接管了点击**（先弹确认，确认后才 `emit('confirm')`）。

第一版 `runAction` 的 `switch` 里只写了 `view/edit/audit/submit/publish*`，
把 `remove/offline/archive` 留给了"默认分支什么都不做" ——
**点确认后什么都不会发生，且不报错**，属于最难查的一类遗漏。

现在三个分支都显式列出来了，并且 `default` 分支会 `console.error`，
将来 `articleActions.js` 加了新动作而这里忘了接，控制台会明确报出来。

### 5.6 【架构性风险，与 F04/F05 同源】4 个组件在本步才第一次被真正用上

F04/F05 交付的 `PageTable` / `StatusTag` / `AuditTimeline` / `ConfirmAction`，
在 F06 之前**没有任何调用方** → `vite build` 会把它们 tree-shaking 掉，产物里根本不含它们
（F04 记过："构建成功 ≠ 文件正确"）。

本步把 `ArticleList` 接上之后，构建产物里出现了：

```
assets/PageTable-CZAwMf5H.js        16.11 kB
assets/ConfirmAction-CAHebiSy.js    11.33 kB
assets/AuditTimeline-DsUtzEhB.js     4.69 kB
```
（`StatusTag` 的代码在共享 chunk `article-*.js` 里，因为多个文章页都用它。）

并且用"在产物里 grep 每个组件的特征字符串"的方式证了一遍：

| 组件 | 特征字符串 | 命中文件 |
|---|---|---|
| PageTable | `PageTable 使用错误` | `PageTable-CZAwMf5H.js` |
| StatusTag | `未知状态` / `定时发布中` | `article-CYmiHRe0.js` 等 |
| AuditTimeline | `暂无审核记录` | `AuditTimeline-DsUtzEhB.js` |
| ConfirmAction | `原因会记录到审核流水` | `ConfirmAction-CAHebiSy.js` |

### 5.7 【判据坑】用 `pre-wrap` 才能让正文不顶破容器

正文容器如果直接用 `<pre>`，默认 `white-space: pre` **不折行** ——
正文里只要有一任意长的行，就会把容器顶破，进而让整个页面出现横向滚动条
（而"1440 宽无横向滚动条"正是本步的核查项之一）。

所以两处正文容器都显式写了 `white-space: pre-wrap; word-break: break-word`，
并且**加了断言**：

```
PASS  会话二 正文容器是 pre-wrap（长行会折行，不会顶破页面）  pre-wrap
PASS  会话三 详情页正文用 pre-wrap（长行折行）  pre-wrap
```

### 5.8 【安全】正文一律不 `v-html`

正文是用户提交进来的内容。本项目没有富文本编辑器，正文按纯文本存，
用 `v-html` 只会把"恰好长得像 HTML 的文本"当代码执行 —— 典型的 XSS 入口。
现在没有危险只是"恰好没人这么填"，不是安全。

要支持富文本时，正确顺序是：**后端做白名单净化（如 OWASP Java HTML Sanitizer）→ 再决定前端能否渲染**，
而不是前端先 `v-html` 再说。

## 七、F06 期间查出的 `article.js` 与后端不一致（已修正）

| 位置 | 原写法 | 实际（依据） | 后果 |
|---|---|---|---|
| `pageArticles` 入参 | `keyword / tagId / createTimeFrom / createTimeTo / onlyTop` | `CmsArticleQueryDTO` = `title / categoryId / status / authorId / beginTime / endTime` | 传过去**不报错、被静默忽略** → "筛选看起来生效了其实没生效" |
| `pageArticles` 排序白名单 | `createTime / updateTime / ...`（驼峰） | 白名单比的是**数据库列名**（`PageQuery` 第 229 行注释明确："白名单里写的是数据库列名"） | 传 `createTime` 会被判"不支持排序"直接 400 |
| `saveDraft` / `updateDraft` 字段 | `coverImage / tagIds` | `coverUrl`，且 `CmsArticleSaveDTO` **没有** `tagIds` | 同上，静默丢失 |
| 权限码 | `article:list / article:edit / article:offline / article:archive` | 库里只有 `article:view / article:update / article:manage`（**前四个码库表一条都没有**） | 若按旧码写，`@RequirePermission` 会把所有人挡在 403 |

这 4 处全部按后端真实定义改掉了。**"文档与代码不一致"里最危险的就是第 1 和第 3 类：
它不报错。** 只有把字段名逐个对过 DTO 才能发现。
