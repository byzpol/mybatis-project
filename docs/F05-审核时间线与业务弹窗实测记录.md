## 二、`AuditTimeline.vue` 的设计取舍

### 2.1 环节名与结论的口径都取自后端枚举

| 展示项 | 取值来源 | 兜底 |
|---|---|---|
| 环节名 | `com.lab.cms.common.enums.AuditStageEnum`（1 编辑初审 / 2 主编终审） | 「未知环节」——与后端 `getDesc()` 的兜底文案**完全一致** |
| 结论标签 | **复用 `StatusTag` 的 `approval` 映射表**（1 通过 / 2 驳回） | 「未知状态」 |
| 圆点颜色 | 从 `approval` 映射表的 `type` 派生（success→绿 / danger→红） | info 灰 |

**为什么不在这里再写一份"结论 → 颜色"的表**：审核结论只有两个值，没有任何理由分家。
共用之后有一个直接好处：**标签色和圆点色永远一致**——写了两次就一定会出现
"标签是红的、圆点是灰的"这种只在特定数据下才暴露的不一致。

### 2.2 倒序是自己排的，没用 `el-timeline` 的 `reverse`

因为"默认只显示最近 3 条"这件事本身就要求**先按时间排好再截取**。
既然要排，就别让排序一会儿在组件计算里、一会儿在 CSS 方向上。

排序实现上有个刻意的选择：**用归一化后的字符串比较，不用 `new Date()`**。

```js
function normalizeTime(t) { return String(t).replace('T', ' ').trim().slice(0, 16) }
// ...
return tb.localeCompare(ta)   // 倒序
```

理由：后端给的是 `2026-10-01 09:30:00`（**空格分隔**）。这种格式在 `new Date()` 里
属于"实现相关的宽容解析"，不同引擎行为不同（有的直接 `Invalid Date`）。
字符串比较只要格式一致就是稳定且正确的，而且完全绕开了时区问题。
顺带这个归一化还让 `YYYY-MM-DDTHH:mm:ss`（ISO）也能正常排 —— 一行代码兼容两种输入。

### 2.3 意见块的三条显示规则

| 情况 | 是否显示意见块 | 样式 |
|---|---|---|
| 驳回，写了意见 | 显示 | 浅红底 + 红色左竖线 + 引号 |
| 驳回，**没写**意见 | **也显示** | 同上，文案兜底为「（未填写审核意见）」 |
| 通过，写了意见 | 显示 | 浅灰底 + 灰色左竖线，**不加引号** |
| 通过，没写意见 | **不显示** | —— |

第二条是刻意的：驳回却不写原因是个值得被看见的事实，静默地什么都不显示反而会让人
以为"没审核过"。第三条的引号只给驳回 —— 引号是"引述一段理由"的语义，
通过时的意见通常只是备注，加引号反而像在强调。

**引号用 CSS 伪元素 `::before/::after` 加，不写进文本里**：这样从页面上复制这段意见时
不会把引号一起带走。

### 2.4 折叠只隐藏"渲染"，不隐藏"数据"

`visibleRecords` 是计算属性，`props.records` 本身不动。
使用方拿到的永远是完整数组，不会被组件改掉 —— 否则父组件再传一次同样的数组进来，
`v-for` 的 key 全变了，会白白重建一遍 DOM。

## 三、`ConfirmAction.vue` 的设计取舍

### 3.1 两种形态，为什么必填原因要用 dialog 而不是 MessageBox

`requireReason = true` 走 `el-dialog` + `textarea`，**不是** MessageBox。原因很具体：

> **MessageBox 没有"禁用确认按钮"的能力。**
> 用它就得等用户点了确认、再弹一句"请填写原因"、再把框关掉 —— 用户要被打断两次。
> 换成 dialog 才做得到"原因没填时确认键直接是灰的、旁边写着为什么"。

### 3.2 ⚠️ 一个真实的设计缺陷：`touched` 是死代码

第一版的逻辑是"点了确认却没填 → 才把提示转成红色"（想避免"一上来就红字指责用户"）：

```js
function onDialogConfirm() {
  touched.value = true          // ← 永远执行不到
  if (reasonInvalid.value) return
  ...
}
```
```html
<p class="confirm-action__hint" :class="{ 'is-error': reasonInvalid && touched }">
```

实测时那条断言**一直 FAIL**，才反应过来为什么：

> **浏览器不会给 `disabled` 的按钮派发 `click` 事件。**
> 确认键是 `:disabled="reasonInvalid"`，原因没填时它根本不可点，
> `onDialogConfirm` 压根不会被调用，`touched` 永远是 `false`。

也就是说 **"按钮置灰"和"点击后报错"是两种互斥的校验设计**，想同时做就会得到一段死代码。
（"点击后报错"对应的是"按钮**不**置灰、点了才校验"那一套做法。）

**修正**：去掉 `touched`，未填写时提示就固定是「请填写原因」+ 危险色，
与旁边置灰的确认键配对。用户的动作只剩两个 —— 填原因让按钮亮起来，或者点取消。

> 这条是本步**唯一一处改了组件而不是改断言**的地方。
> 其余 FAIL 全是判据写错（见第五节），这条是真的设计问题。

### 3.3 两个 Element Plus 的细节

**① `ElMessageBox.confirm` 的 `type` 不接受 `'danger'`**

它只认 `'warning' | 'info' | 'success' | 'error'`。所以 `type: 'danger'` 要映射成
`'warning'`（拿那个橙色感叹号图标），再用 `confirmButtonClass: 'el-button--danger'`
把按钮刷红。**只传 `type:'danger'` 的话图标会静默消失** —— 不报错、不警告。

实测拿到的按钮 class 列表是 `["el-button","el-button--primary","el-button--danger"]`：
`el-button--primary` 是 MessageBox 自己的默认值，和 `el-button--danger` 同时存在。
最终底色是红的（`rgb(214,69,69)`），因为 EP 的 CSS 里 `.el-button--danger` 排在
`.el-button--primary` 之后，同优先级后者胜出。这算"能用但依赖加载顺序"，
所以专门留了一条断言盯着它的实际背景色，将来 EP 升级改了顺序能第一时间发现。

**② `ElMessageBox` 的样式要手工 import**

它是**函数式调用**，`unplugin-vue-components` 管不到它的样式，必须在使用处
`import 'element-plus/es/components/message-box/style/css'`。
漏了的症状非常像"自己写坏了"：弹框**没有背景遮罩**、按钮是原生样式。
本步专门用一条断言把它钉死：**量遮罩的背景色**（`rgba(0,0,0,0.5)`），
再补一条"弹框圆角不是 0px"作为旁证。

同时把 JS 的 import 也从"依赖自动导入"改成**显式** `import { ElMessageBox } from 'element-plus'`：
这是"点下去就要弹框"的关键路径，依赖自动导入的话，解析不到只会是运行时 `ReferenceError`，
属于最难查的一类。

## 五、踩坑

### 5.1 【判据坑】模板换行会被算进 `textContent`

`StatusTag` 的模板是

```html
<el-tag ...>
  <el-icon v-if="showIcon">...</el-icon>
  {{ label }}
</el-tag>
```

`{{ label }}` 前面的换行与缩进变成了文本节点，于是 `textContent` 是 `" 通过"` 而不是
`"通过"`，版本号徽标同理（`" v2"`）。
F04 的脚本里我写了 `.trim()` 所以没事，**F05 第一轮忘了 trim，两条断言直接 FAIL**。

> 教训：只要断言比对的是 `textContent`，就先 `trim()`。这不是"顺手加一下"，
> 而是模板里的空白**本来就是内容的一部分**（Vue 默认保留 `<pre>` 之外的空格合并结果）。

### 5.2 【判据坑】不要在任何断言里写死 Element Plus 的默认色值

断言"驳回意见块左侧竖线是红的"时，我写成了
`borderLeft.includes('245') || borderLeft.includes('108')`
—— 那是 EP 默认危险色 `#F56C6C` = `rgb(245,108,108)`。
实测拿到的是 **`rgb(214, 69, 69)`**：本项目主题把 `--el-color-danger` 换成了自己的红。

**断言写死框架默认值，会把"主题生效"误判成"样式没起效"** —— 正好反了。
改成解析 RGB 后判"R 明显大于 G"，只认"红"这个事实本身。

（顺带这也成了"主题变量确实生效"的一条证据：`--el-color-danger` 被换掉了。）

### 5.3 【判据坑】`disabled` 的按钮点了等于没点

见 3.2。它既是"我的断言写错了时机"，更是"组件里有一段到不了的代码"。
两者的区别在于：改断言之后如果它能过，说明只是判据问题；如果**怎么改都过不了**，
那就要回头看看被测对象是不是真的做不到。

### 5.4 【判据坑】`ElMessageBox` 的确定位

页面上可能同时存在多个 `.el-dialog`（每个 `ConfirmAction` 都渲染一个，只是没 `v-model` 打开），
所以不能按 `.el-dialog` 取第一个。做法是按**标题文本 + 遮罩可见**双重定位：

```js
Array.from(document.querySelectorAll('.el-dialog')).find(d =>
  d.querySelector('.el-dialog__title').textContent.includes(titlePart) &&
  getComputedStyle(d.closest('.el-overlay')).display !== 'none')
```

顺带复习 F03 的教训：判断可见性只能看 `display`，不能靠"元素在不在 DOM 里"。

### 5.5 【模板真错误】双引号套双引号会把属性截断

临时页第一版写的：

```html
content="驳回后文章会回到作者的"已驳回"列表，作者需要修改后重新提交。"
```

`"` 在 HTML 属性值里就是结束符，`content` 会在「作者的」之后被截断，后面的内容变成
一堆乱七八糟的属性。改用中文直角引号「已驳回」，语义一样、还更好看。

### 5.6 【架构性风险，与 F04 同源】F05 的两个组件交付时也没有调用方

删掉临时页后，`AuditTimeline.vue` / `ConfirmAction.vue` 同样**没有任何模块 import 它们**，
会被 tree-shaking 跳过（构建产物 24 个，与 F03 完全一致，搜不到任何组件代码）。
加上 F04 的两个，现在**累计 4 个组件处于"构建覆盖不到"的状态**。

F06 会把 `PageTable` / `StatusTag` / `AuditTimeline` / `ConfirmAction` 全部接进页面，
届时构建保护一次性恢复。这期间它们能保持正确，靠的是 F04/F05 两轮的 56 + 58 项真机断言。
