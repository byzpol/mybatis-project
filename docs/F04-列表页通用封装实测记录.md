## 二、`PageTable.vue` 的设计取舍

### 2.1 它凭什么叫"通用"：一条判据

> **如果某段逻辑只有文章列表用得上，它就不该出现在这个文件里。**

按这条判据自查：文件里搜不到 `article` / `cms_article` / `status` / `title` 任何一个业务词。
所有列、所有查询条件、所有按钮都由使用方通过 props 和插槽注入。

### 2.2 六个需要解释的取舍

**① 排序字段用列上的 `sortField`，不是列的 `prop`**

这是本组件最容易踩的一个坑，所以写在文件头部注释里：

```js
{ prop: 'createTime', label: '创建时间', sortable: true, sortField: 'create_time' }
```

原因：后端 `PageQuery.checkSortFieldIn()` 比对的是**数据库列名（下划线）白名单**，
而前端列的 `prop` 通常是 Java 属性名（驼峰）。两者恰好在 `title` 这类单词列上同名，
在 `createTime` 上就不同名 —— 不显式指定就会拼出一个后端白名单里没有的字段，直接 400。
（后端**只认白名单**是刻意的，这是防 SQL 注入的那道墙，不能为了前端方便去放宽。）

**② 空值条件一律不传**

```js
if (v === null || v === undefined || v === '') return
if (Array.isArray(v) && v.length === 0) return
```

不这么做的话，`title = ''` 会被序列化成 `title=`，后端拼出 `title LIKE '%%'` ——
语义从"不按标题过滤"变成了"必须有标题"。分页给 0 条、用户以为没数据，
是这类问题的典型表现。

**③ 排序状态放在组件内部的 `ref`，不放进 `queryModel`**

`queryModel` 是"业务查询条件"，它归使用方所有（重置时要清空它）。
排序是组件的交互状态。混在一起，"重置到底该不该清排序"这个问题就没有答案了。
现在答案很明确：**清**（见 `onReset`），而且清了也不影响使用方的对象。

**④ `refresh()` / `reload()` 分开暴露**

- 编辑完某一行回来 → `refresh()`，停在当前页（用户希望"我怎么出来的就怎么回去"）
- 新增了一条 → `reload()`，回第 1 页（新数据排在最后，停在第 5 页会让人以为没成功）

**⑤ 查询/改条数都要 `current = 1`**

- 查询：不重置页码的话，用户在第 5 页收紧条件会看到"查不到数据"（其实只是没有第 5 页）
- 改条数：第 5 页 × 每页 100 条会请求一个根本不存在的页

⚠️ 实现上有个细节：**`onPageChange` 里不能再赋值 `current`**。
`v-model:current-page` 已经把值改好了，再赋一次会造成"点一次翻两页"。

**⑥ 请求异常不弹提示，但一定结束 loading**

```js
} catch (e) {
  rows.value = []; total.value = 0
} finally { loading.value = false }
```

不弹提示是因为 `request.js` 的响应拦截器**已经统一弹过一次**了，这里再弹就是两条一样的报错。
还留着 `catch` 是为了保证 `loading` 一定收回 —— 否则一次失败就永久转圈。

### 2.3 分页条数为什么固定 `[10, 20, 50, 100]`

与后端 `PageQuery.MAX_SIZE = 100` 对齐。不放开更大的值，是因为后端会把超过 100 的
`size` 归一化成 100；用户选了"每页 200"却只拿到 100 条，会以为系统丢数据。
（组件里还额外用服务端返回的 `current/size` 回写分页器，万一后端做了归一，界面显示的也是真实生效值。）

### 2.4 序号连续

```js
function indexMethod(index) { return (current.value - 1) * size.value + index + 1 }
```

不写这行的话，第 2 页的序号会从 1 重新开始 —— 讨论"第几行"时就会歧义。

## 三、`StatusTag.vue` 的映射表与两处必须说清的事

### 3.1 映射表的来源

`article` 映射（10 条）与后端 `com.lab.cms.common.enums.ArticleStatus` 的
`description` + `color` **逐条一致**。另有两张表：

| 表名 | 来源 | 内容 |
|---|---|---|
| `category` | `sql/init.sql` 第 186 行的列注释 | 0 待审批 / 1 已生效 / 2 已驳回 |
| `approval` | 后端审核结论枚举 | 1 通过 / 2 驳回 |

### 3.2 ⚠️ 与手册 F04 的 1 处差异：状态 3 的颜色

| | 手册 F04 | 后端 `ArticleStatus` + `docs/接口契约.md`（第 1118 行） |
|---|---|---|
| `3 已通过待发布` | `primary`（蓝） | `APPROVED(3, "审核通过", "success")` |

按项目既定口径（**库表 / 契约 / 代码 > 手册**）取 `success`。
副作用要提前说清：**状态 3（审核通过）与状态 5（已发布）标签同为绿色**，靠文案区分。
如果确实想让两者在视觉上分开，正确做法是改**后端枚举的 `color`**（一处生效），
而不是只在前端偷偷改一份 —— 那会变成两份真相。

### 3.3 ⚠️ 为什么前端要存一份映射，而不是直接用接口返回的 `statusDesc/statusColor`

`CmsArticleVO` 同时给了 `statusDesc` 和 `statusColor`，理论上前端不用自己维护映射。
但 `StatusTag` 要能**脱离接口单独使用**（审核页里只拿到状态码，不想为了一个标签再去取详情），
而且列表页一次 20 行，按码直接渲染比每行去读 VO 字段干净。
代价是两边要同步 —— 所以文件注释里写明了"**改映射时以后端枚举为准，两边一起改**"。

### 3.4 双 `<script>` 结构，以及**不要自引用 import**

组件里同时有 `<script>` 和 `<script setup>`：

- `<script>` 只负责 `export` 静态映射表与 `getStatusMeta/getStatusOptions`
- `<script setup>` 负责组件本身的逻辑

这样既能让使用方按需具名导入（`import { getStatusOptions } from ...`），
也能满足手册要求的 `StatusTag.getStatusOptions()` 调用方式（把函数挂到组件 options 上）。

⚠️ **这里踩过一个坑**：第一版在 `<script setup>` 里写了

```js
import { getStatusMeta } from './StatusTag.vue'   // ← 自己 import 自己
```

正确的写法是**直接引用**：`<script>` 与 `<script setup>` 编译后同处一个模块作用域，
上面 `<script>` 里 `export` 的函数在下面**直接可见**，不需要再 import 一次
（再 import 会构成自引用循环模块）。

**这个坑最阴的地方是：`vite build` 完全不会报错。**
JS 里未声明的标识符只有运行时求值才炸。所以"构建成功"在这里毫无说服力 ——
必须真机跑一次（本步就是这么发现并纠正的，见第五节踩坑 1）。

### 3.5 两个小约定

- **未知状态码显示「未知状态」**，不留空白 —— 空白会让人以为是"没查到数据"
- **`String()` 归一**：后端 JSON 里状态是数字，但 URL query 或手写测试里可能是 `"3"`，
  对象取值时数字 3 与字符串 `'3'` 不相等；统一转成字符串再查，少一类诡异问题
  （实测已验证：传 `"3"` 正确显示「审核通过」）

## 五、踩坑

### 5.1 【真坑，最值得记】`vite build` 成功不能证明 `<script setup>` 里的引用是对的

见 3.4 节。判据：**只会在运行时炸**，而且是"整个组件渲染不出来"这种级别。
本步的处置：把「StatusTag 正常渲染出 10 个标签」作为一条**独立断言**留下 ——
如果那个引用解析失败，断言值会是 0，一眼可辨。

### 5.2 【判据坑】`el-input` 是 `inheritAttrs: false`，`id` 落在内部原生 `input` 上

排查脚本里写 `document.querySelector('#f-title').querySelector('input')`，
拿到的却是 `null`（报 `Cannot set properties of null`）。
原因：Element Plus 的 `el-input` 把 `$attrs` 透传给了内部的**原生 `<input>`**，
所以 `#f-title` 指向的就是那个 `<input>` 本身。
**教训**：写断言时不要假设"组件根元素是外层 div"，要么查真实 DOM，要么写成两种落点都能处理的形式。

### 5.3 【判据坑】`el-table` 的横向滚动容器不是 `.el-table__body-wrapper`

第一版量 `body-wrapper.scrollWidth - clientWidth`，恒为 0，于是误判"表格内部没有横向滚动"。
真实结构是 `body-wrapper`（`overflow: hidden`）里再套一层 `.el-scrollbar__wrap`，
**在滚的是后者**。改用它之后，800px 视口下量到 `wrapOverflow = 100px`，与"内层表格 850 / 容器 750"完全吻合。

### 5.4 【判据坑】"渲染行数"不能用来证明筛选生效

第 1 轮断言"筛选后应渲染 11 行"失败了。原因很朴素：**分页在客户端只渲染当前页**，
每页 10 条时第 1 页恒为 10 行。要看总数得读分页器上的 `.el-pagination__total`（"共 11 条"）。

### 5.5 【判据坑】表格宽度 ≠ 视口宽度

`.app-card` 有左右各 20px 内边距 + 1px 边框，1440 视口下表格只有 **1390**（少 42px）。
断言必须对齐"容器内容宽度"这个基准，否则会得出"表格没撑满"的错误结论。

### 5.6 【判据坑】Element Plus 的 `<el-button>` 会给两个汉字中间自动加空格

「登录」在 DOM 里是「登 录」（`autoInsertSpace` 默认开启）。
比对按钮文案必须先 `replace(/\s/g, '')`。

> **5.2~5.6 这五条都是同一个病**：把"我以为的判据"当成了事实。
> 与 F03 记下的那条教训（"元素存在" ≠ "元素可见"）是同一种错误。
> 处置办法一样：**断言失败先打真实 DOM，别先改代码**。

### 5.7 ⚠️ 交付即"失去构建保护"：两个组件目前没有调用方

删掉临时示例页之后，`PageTable.vue` / `StatusTag.vue` **没有任何模块 import 它们**，
于是会被 tree-shaking 跳过、压根不进构建产物（`assets/` 里搜不到 `F04Demo` 或组件代码）。
这正是 F02 记录过的那条：**没有调用方的模块，`vite build` 根本不校验**。

所以必须如实说明：**本步的编译事件发生在"临时示例页存在的那次构建"里**；
从提交这一刻到 F06 把它们接进页面之前，这两个文件是"构建覆盖不到"的状态。
F06 的第一个动作就是把它俩接进 `ArticleList.vue`，届时构建保护自动恢复。

### 6.1 四条核查项（全部通过）

手册 F04 的四条核查项，逐条给判定依据：

| # | 核查项 | 判定依据（实测值） | 结论 |
|---|---|---|---|
| ① | 没有 `request` 时给出友好警告而不是白屏报错 | 渲染出 `el-alert`，标题「PageTable 使用错误：未传入 request」，描述里含 `(params) => Promise<PageResult>`；同区块**不渲染**表格与分页器；控制台有 `[PageTable] request 是必填的…`；页面无未捕获异常；正文 `innerText=1498` 非空 | ✅ 8 条断言 |
| ② | 查询、重置、翻页、改每页条数四个动作都重新请求**且参数正确** | 每个动作都用「调用次数 +1」证明真的发了新请求；参数实测见下表 | ✅ 24 条断言 |
| ③ | `StatusTag` 传 99 显示「未知状态」 | `#tag-unknown` 的 `textContent === '未知状态'`；另验证传 `"3"` → 「审核通过」、传 `null` → 「未知状态」 | ✅ 10 条断言 |
| ④ | 示例页在窄屏下表格不横向溢出 | 1440 / 1024 / 800 / 600 四档，`documentElement.scrollWidth - clientWidth` 全部 = **0px** | ✅ 13 条断言 |

**② 的参数明细**（`window.__f04calls` 全程记录，脚本原样输出）：

```
#1 {"page":1,"size":10}                                   ← 挂载自动请求第 1 页
#2 {"page":1,"size":10,"title":"标题 1"}                   ← 点查询：带条件、回第 1 页
#3 {"page":2,"size":10,"title":"标题 1"}                   ← 翻页：page=2，条件保留
#4 {"page":1,"size":20,"title":"标题 1"}                   ← 改条数：size=20，回第 1 页
#5 {"page":1,"size":20,...,"sortField":"create_time","sortOrder":"asc"}  ← 排序：传数据库列名
#6 {"page":1,"size":10}                                   ← 重置：条件与排序都清空、条数复位
#7 {"page":1,"size":20}                                   ← 再次改条数（无筛选，用于验证渲染满 20 行）
```

顺带验到的两个细节：
- 未选状态时参数里**不出现** `status` 键（空值不传的约定生效）
- 第 2 页首行序号是 **11**（不是从 1 重新开始）

**④ 的四个视口实测值**：

| 视口 | 页面溢出 | 表格宽 | 内层表格宽 | 容器内滚动量 | 标题列实际宽 |
|---|---|---|---|---|---|
| 1440 | 0px | 1390 | 1390 | 0 | **384** |
| 1024 | 0px | 974 | 974 | 0 | **258** |
| 800 | 0px | 750 | **850** | **100px** | **220** |
| 600 | 0px | 550 | **850** | **300px** | **220** |

**"列用的是 minWidth 而不是固定 width"这件事是怎么被证出来的**：
看标题列（`minWidth: 220`）的**实际渲染宽度** ——

- 1440 时是 **384**、1024 时是 **258**（都被拉伸到明显大于 220）→ 说明列在按比例吃掉剩余宽度
- 800 / 600 时回落到 **220**（守住最小宽，不再压缩）

固定 `width` 的列在四种视口下都会是同一个值，不会出现这种"拉伸 → 回落"的行为。
