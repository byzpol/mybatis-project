## 一、逻辑删除的完整性检查

### 1.1 四问逐一回答（手册【一】）

#### （1）所有业务表是否都有 `deleted`，且实体都标了 `@TableLogic(value="0", delval="1")`

- **库表侧：17/17 全有。** 实测 `grep -n "\`deleted\`" sql/init.sql` 命中 **17 条**列定义，
  类型统一 `TINYINT NOT NULL DEFAULT 0 COMMENT '逻辑删除：0=未删除 1=已删除'`。
  另外用一个 UNION ALL 查询在**业务库**上逐表统计，17 张表里 `SUM(deleted=1)` **全部为 0**
  （即当前没有任何软删数据，基线 `articles=20 / versions=10 / audit_logs=12` 与种子一致）。
- **实体侧：7/7 全覆盖**，但覆盖方式是"6 + 1"：

  | 覆盖方式 | 实体 | 说明 |
  |---|---|---|
  | 继承 `BaseEntity`（基类统一声明 `@TableLogic`） | `CmsArticle`、`CmsArticleAuditLog`、`CmsCategory`、`SysLoginLog`、`SysOperLog`、`SysUser` | 6 个 |
  | **自己声明** `@TableLogic(value="0", delval="1")` | `CmsArticleVersion` | 1 个 |

  ⚠️ **为什么 `CmsArticleVersion` 是唯一的例外**：库表里它**没有** `create_by / update_by /
  update_time` 三列（只有 `create_time`），所以不能继承 `BaseEntity`（继承会凭空多出 3 个
  不存在的列，MP 生成 SQL 时会报 1054 Unknown column）。**判据是"库表有没有那几列"，
  不是"这张表重不重要"** —— 这条判据在 S08 定过一次，S18 重新核对仍然成立。
- 另有 10 张表（`sys_role`、`sys_permission`、`sys_user_role`、`sys_role_permission`、
  `sys_apply_approval`、`cms_tag`、`cms_article_tag`、`cms_article_index`、`sys_report`、
  `cms_category_audit_log`）**还没有 entity/mapper**（属成员B/C/D 的域，尚在开发中），
  所以"实体是否标了 `@TableLogic`"对它们不适用；但它们的建表脚本里 `deleted` 列已经齐了。

#### （2）唯一索引与逻辑删除的冲突

手册举的例子是 `cms_tag.tag_name`。**实测：这不是个例，全库 9 个唯一键全部有这个问题。**
完整分析与处置见 §1.2。**结论：统一把 `deleted` 追加为唯一键的最后一列，已落地到
`sql/init.sql` 并同步业务库。**

#### （3）逻辑删除后关联数据怎么处理

- **机制事实（先纠正一个常见误解）**：MP 的 `deleteById`（含 `deleteByIds`）
  **只会 `UPDATE 自己那一行 SET deleted = 1`，不做任何级联**。也就是说
  "文章删了，它的流水和版本会怎样"这个问题的答案是：
  **什么都不会发生 —— 流水/版本行自己的 `deleted` 仍是 0，仍然查得出来。**
- **本项目的现状**：**文章域当前根本没有删除入口**。实测：
  `ArticleController` 共 15 个端点（`GET /`、`POST /draft`、`PUT /{id}/draft`、
  `POST /{id}/submit`、`POST /batch-submit`、`POST /{id}/audit`、`GET /{id}`、
  `GET /{id}/audit-logs`、`POST /{id}/publish`、`POST /{id}/schedule`、
  `POST /{id}/withdraw`、`POST /{id}/offline`、`POST /{id}/archive`、
  `GET /{id}/versions`、`POST /{id}/rollback`），**没有 `DELETE`**；
  `ARTICLE_DRAFT_ONLY(11013)`「仅草稿或已驳回状态的文章可删除」这个错误码
  **全仓零引用、从未被抛出**。
  → 所以"文章删了关联数据怎么办"在本项目**是设计问题，不是运行时问题**。
- **给出结论（供组内决定）**：若将来补 `DELETE /articles/{id}`（仅草稿/已驳回），推荐：

  | 关联表 | 推荐处置 | 理由 |
  |---|---|---|
  | `cms_article_audit_log`（审核流水） | **保留，不级联删** | 审计凭证。草稿态通常没有流水，真有也不该抹掉 |
  | `cms_article_version`（版本快照） | **保留，不级联删** | 与流水同理；草稿态只有 1~2 条，留着不占空间 |
  | `cms_article_tag`（标签关联） | **随文章一起标记删除** | 纯派生数据，留着会在"按标签检索"里产生指向已删文章的悬挂关联 |
  | `cms_article_index`（检索索引） | **随文章一起标记删除**（并置 `index_status=0`） | 派生数据；不处理会让检索结果出现打不开的文章 |
  | `sys_oper_log`（操作日志） | 保留 | 日志域归属成员D，且日志本就不该随业务数据消失 |

  ⚠️ **本轮不实现**：新增删除接口属于**行为变更**，必须有独立用例与回归（本轮手册的定位是
  "重构与规约自检"）。已登记进 §三 的重构优先级表，并同步到 `docs/联调报告.md` 的挂起清单。

#### （4）统计类查询（count）是否都会自动带上 `deleted = 0`

**分两类，判据是"SQL 谁生成的"：**

| SQL 来源 | 是否自动带 `deleted = 0` | 依据 |
|---|---|---|
| MP 自动生成（`selectCount` / `selectList` / `selectPage` / `selectBatchIds` / `updateById` …） | **自动带** | `@TableLogic` 会改写 MP 生成的 SQL |
| **手写 XML** | **必须自己写**，MP 不管 | MySQL 层面没有"逻辑删除"这个概念 |

- 实测（S18 从真实运行日志 `logs/cms.log` 里取，不是推测）：

  ```
  DEBUG c.l.c.m.C.selectCount - ==>  Preparing: SELECT COUNT( * ) AS total FROM cms_article_audit_log WHERE deleted=0
  DEBUG c.l.c.m.CmsArticleAuditLogMapper.selectList - ==>  Preparing:
    SELECT id,article_id,audit_stage,auditor_id,result,opinion,audit_time,article_version,
           create_by,create_time,update_by,update_time,deleted
      FROM cms_article_audit_log
     WHERE deleted=0 AND (article_id = ?)
     ORDER BY audit_time ASC,id ASC
  ```

- **手写 XML 只有 3 个语句**，S18 逐个核对，**全部自己写了 `AND deleted = 0`**：

  | XML 文件 | 语句 | 逻辑删除处理 |
  |---|---|---|
  | `CmsArticleMapper.xml` | `selectIdTitleByKeyword` | `AND deleted = 0` |
  | `CmsArticleVersionMapper.xml` | `selectMaxVersionNo` | `AND IFNULL(MAX(...)) ... AND deleted = 0` |
  | `SysUserMapper.xml` | `selectByUsername` / `selectRoleCodesByUserId` / `selectPermissionCodesByUserId` | 主表 `AND deleted = 0`，**JOIN 条件也各自带了** `r.deleted=0` / `rp.deleted=0` / `p.deleted=0` |

  JOIN 那 3 处是**最容易漏的**：主表带了、关联表没带，权限校验时就会把"已逻辑删除的角色"
  也算成用户拥有的角色。这条已写进 S18 的复现方式（§八）。

### 1.2 唯一索引与逻辑删除的冲突：分析与落地方案

#### 1.2.1 问题是什么

逻辑删除把"删除"变成了 UPDATE，行还在表里。于是 **唯一索引看不见"删除"这件事**：

```
1. INSERT cms_tag(tag_name='Spring')          → 成功，deleted=0
2. UPDATE cms_tag SET deleted=1 WHERE ...     → 逻辑删除，行还在
3. INSERT cms_tag(tag_name='Spring')          → ERROR 1062 Duplicate entry 'Spring'
                                                 （业务上"删了再建同名"完全合法，但数据库不让）
```

#### 1.2.2 本库的实际冲突面（实测，不是推演）

`information_schema.STATISTICS` 实查：全库 **9 个唯一键**，**9 个全部中招**：

| # | 表 | 唯一键 | 列 | 归属 | 触发场景 |
|---|---|---|---|---|---|
| 1 | `sys_user` | `uk_username` | `username` | 成员C | 删除账号后重建同名账号 |
| 2 | `sys_role` | `uk_role_code` | `role_code` | 成员C | 删除角色后重建同编码角色 |
| 3 | `sys_permission` | `uk_permission_code` | `permission_code` | 成员C | 删除权限后重建同编码权限 |
| 4 | `sys_user_role` | `uk_user_role` | `user_id, role_id` | 成员C | 取消授权后重新授权同一角色 |
| 5 | `sys_role_permission` | `uk_role_permission` | `role_id, permission_id` | 成员C | 取消角色权限后重新勾选 |
| 6 | `cms_tag` | `uk_tag_name` | `tag_name` | 成员B | **手册点名的就是这条**：删标签后建同名标签 |
| 7 | `cms_article_tag` | `uk_article_tag` | `article_id, tag_id` | 成员B | 取消文章标签后重新打同一标签 |
| 8 | `cms_article_version` | `uk_article_version` | `article_id, version_no` | **成员A（我）** | 删版本后重建同号版本 |
| 9 | `cms_article_index` | `uk_article_id` | `article_id` | 成员D | 删除索引行后为同一文章重建 |

⚠️ **必须说清"当前可达性"**：上述 9 条里，**目前没有任何一条是可达的**，原因有两个 ——
① `cms_article_version` 是本项目唯一的"有唯一键且属我已实现"的表，而**文章域没有任何删除
版本的入口**（回滚是"新建一版"，不是删旧版）；② 其余 8 张表**都还没有 entity/mapper**。
→ 也就是说这 9 条现在都是**潜在缺陷**。**但正因为现在还没人写它们的删除代码，才是改地基
成本最低的时刻** —— 等成员B/C/D 各自实现完删除入口再回头改，代价是全组返工。

#### 1.2.3 候选方案对比与推荐

| 方案 | 做法 | 能否根治 | 改动面 | 评价 |
|---|---|---|---|---|
| **A. 唯一键追加 `deleted`** | `uk_tag_name(tag_name)` → `uk_tag_name(tag_name, deleted)` | 「删→再建同名」根治；「同一名称被删两次」仍冲突 | **每表 1 行 DDL，零代码改动** | ✅ **本轮采纳** |
| B. 删除时改写业务列 | `SET tag_name = CONCAT(tag_name,'#',id), deleted=1` | 根治 | 每个域的删除入口都要改；且 4 个列都是 `VARCHAR(50)`，拼 `#` + 最多 20 位 id 会**超长**，还要连带改列宽 | 登记为根治清单，需 B/C/D 一起做 |
| D. `deleted` 存自己的 id | `deleted` 改 `BIGINT`，删除时 `SET deleted = id` | 彻底根治（id 唯一 ⇒ 永不冲突） | **要改全组共用的 `BaseEntity` 语义**；且 MP 的 `@TableLogic(delval=...)` **不支持写 "id" 表达式**，得绕开 MP 自己写删除方法 → 动到所有人的删除路径 | ❌ 不推荐（风险最大、收益最小） |
| C. 去掉唯一键，应用层保证唯一 | 查询时带 `AND deleted=0` 判重 | 不根治 | 少 | ❌ 不推荐（并发下必然漏，属于**倒退**：把数据库能给的保证换成了有竞态的应用检查） |

**推荐 A，理由三条（可验证）：**

1. **它是零语义变更，且这个结论可证明、也已实测。**
   - 可证明："老唯一键 `(col)` 成立" ⇒ "新唯一键 `(col, deleted)` 必然成立"。
     因为老键已经保证了 `col` 不重复，追加一个恒定等值的列不会再产生冲突。
   - 已实测：改前在业务库上逐表统计，**17 张表 `SUM(deleted=1)` 全为 0**（不存在不同
     `deleted` 值的同值行），所以追加列**不影响任何一行现存的唯一性判断**。
2. **它把 9 个键一次改完，而另外 3 个方案都做不到。**
   `sql/init.sql` 是成员A（公共基础设施）的产出，9 个键散落在 4 个人的域里；
   一次 DDL 改完，不需要任何人的代码配合 —— 这是组长该做的地基工作。
3. **它把冲突从"必然"降为"罕见"，且把"降级路径"留清楚了。**
   方案 B 需要在 4 张表上各写一段自定义删除 SQL，且要改列宽；**残留的
   "两条墓碑"场景（见 §1.3）在 B 做完之前不会消失，A 做完之后也不会变差** ——
   即 A 是 B 的**前置步骤**，不是替代品。

#### 1.2.4 落地内容

`sql/init.sql`（9 处，`git diff --numstat` = `24 insertions(+), 9 deletions(-)`，
**非整文件替换**，行尾保持 LF）：

```sql
-- 改前
UNIQUE KEY `uk_tag_name` (`tag_name`),
-- 改后（9 个键一律把 deleted 追加为**最后一列**）
-- S18：追加 deleted 为末列 —— 逻辑删除后重建同名不再撞 1062（见 docs/重构记录.md 第一节）
UNIQUE KEY `uk_tag_name` (`tag_name`, `deleted`),
```

同时把 9 条 `ALTER TABLE ... DROP INDEX ... , ADD UNIQUE KEY ...` 跑在**业务库 `cms_db`** 上，
使运行库与脚本一致（与 S17 的处理方式相同）。改完 `information_schema` 实查：

```
TABLE_NAME             INDEX_NAME            cols
cms_article_index      uk_article_id         article_id,deleted
cms_article_tag        uk_article_tag        article_id,tag_id,deleted
cms_article_version    uk_article_version    article_id,version_no,deleted
cms_tag                uk_tag_name           tag_name,deleted
sys_permission         uk_permission_code    permission_code,deleted
sys_role               uk_role_code          role_code,deleted
sys_role_permission    uk_role_permission    role_id,permission_id,deleted
sys_user               uk_username           username,deleted
sys_user_role          uk_user_role          user_id,role_id,deleted
```

**为什么 `deleted` 放最后一列，不放第一列？**
① 放末列**完整保留原索引的最左前缀能力**（`(tag_name, deleted)` 仍支持只用 `tag_name` 的
等值/范围查询，而 `(deleted, tag_name)` 只在"所有查询都带 `deleted = 0`"时才等价）；
② 唯一键的判重语义与列顺序无关，放哪儿都行，那就选对查询更友好的那个。
（对照：S17 新增的 `idx_deleted_create_time` 是**普通索引**且**每一处查询都带 `deleted = 0`**，
把 `deleted` 放前导列是为了让后面的 `create_time` 仍然有序 —— 两种选择不矛盾，
判据是"这个索引要服务什么形状的查询"。）

### 1.3 残留风险登记（已登记，需 B/C/D 一起做）

| 项 | 内容 |
|---|---|
| 残留场景 | 同一业务值被**逻辑删除两次**（`新增 → 删除 → 新增 → 删除`）→ 第二次删除撞 1062 |
| 为什么方案 A 不解决 | `deleted` 只有 0/1 两个值，两条墓碑必然相等 |

| 触发时间点 | 成员B/C/D 实现"标签管理 / 用户与授权管理 / 检索索引维护"的**删除**功能之后 |

### 1.4 自动填充（本题标题里的"与自动填充落地"）

- `AuditMetaObjectHandler` 已在 S08 落地并冻结，S18 复核三项事实：
  1. **硬指标是 `create_by / update_by` 被填上**（不是 `create_time` —— 后者有
     `DEFAULT CURRENT_TIMESTAMP`，漏填看不出来）；
  2. 无 HTTP 上下文时把 `create_by / update_by` 填 **0（不是 null）** —— `MpPluginIntegrationTest`
     有针对性的断言；
  3. INSERT 时**必须显式把 `deleted` 填成 0**：MP 会把 `deleted` 列写进 INSERT 的列清单，
     此时若填充器不管它，会走到 `DEFAULT` 之外的空值路径并报
     `Column 'deleted' cannot be null` —— 这条在 `AuditMetaObjectHandler` 的类注释里有记录。
- 唯一与 S18 相交的点：**本次 9 个唯一键都追加了 `deleted`，而 `deleted` 是由填充器/默认值
  统一写 0 的**，所以新键的"恒定等值列"前提成立（§1.2.3 第 1 条）。两者是相互支撑的。

## 四、IDEA 静态检查操作指引

> ⚠️ **先行说明**：手册要求产出"IDEA 检查结果截图"。**本机无法生成** ——
> 只有配置目录 `C:\Users\admin\AppData\Local\JetBrains\IntelliJIdea2025.3`，
> 全盘找不到 `idea64.exe` / `inspect.bat`（未装 Toolbox）。**如实登记**，
> 并用**可复现的替代证据**顶替（见 §五）。下面这份指引仍然完整给出，
> 供组员在自己装了 IDEA 的机器上执行，并作为答辩时的"我们确实做了静态检查"的说明。

### 4.1 启用 IDEA 自带 Inspections（中文菜单路径）

1. `文件` → `设置`（快捷键 `Ctrl+Alt+S`）→ `编辑器` → `检查`。
2. 顶部"配置文件"选 `项目默认` 或 `Default`；右侧 `严重性` 列可排序。
3. **建议重点打开的检查项**（按本项目的失分点挑的，不必全开）：

   | 类别 | 检查项 | 为什么本项目要看 |
   |---|---|---|
   | Java / 代码风格 | `未使用的声明`、`冗余的 if`、`不必要的局部变量` | 清掉演进留下的死代码 |
   | Java / 数据流 | `条件始终为真/假`、`可能为 null 的解引用` | 本项目的 `Integer status` 用 `!=` 比引用是真实踩过的坑 |
   | Java / 并发 | `同步块中的方法调用`、`非 final 字段的懒初始化` | 定时任务 + 并发取号 |
   | Java / 性能 | `循环中的字符串拼接`、`可以用 Arrays.asList` | N+1 与日志拼接 |
   | Java / 错误处理 | `catch 块为空`、`吞掉异常` | 反例：`WebLogAspect` 故意吞异常（不能影响主流程），要能解释 |
   | Javadoc / 拼写 | `Javadoc 中的非法引用`、`未解析的符号` | 本项目有 `{@code}` 引用具体类名的大量注释，改类名后能立刻发现 |
   | Spring | `Spring Bean 注入`、`@Transactional 用法` | **`@Transactional` 同类自调用不生效**是本项目的头号坑，IDEA 能报出来 |

4. 跑一遍：`代码` → `检查代码`（`Ctrl+Alt+Shift+I`），范围选整个 `src`，
   输出的 `ERROR` 级即为"必须处理"。
5. ⚠️ **对 `ERROR` 的处理口径**：本项目自定义的 `BusinessException`（继承 `RuntimeException`）
   在 IDEA 里通常不会报 `ERROR`；若报了"未处理的异常"，应检查是不是漏了 `throws`
   或在切面外抛出的检查型异常。

### 4.2 阿里 Java 编码规约插件（Alibaba Java Coding Guidelines）

1. `文件` → `设置` → `插件` → `市场`，搜索 `Alibaba Java Coding Guidelines`，
   安装后重启。
2. 扫描：右键 `src`（或单个模块）→ `编码规约扫描`。结果面板按 **Blocker / Critical / Major**
   分级。也可用顶部菜单 `工具` → `阿里编码规约` → `编码规约扫描`。
3. **本项目重点关注的三类**（手册点名的"改名、常量、日志"）：
   - **命名**：拼音、缩写、单字母变量名 → 本项目实查**无拼音**；
   - **常量**：魔法数字 → 本项目已把 `100 / 3 / 1062 / 200` 等常量化；
   - **日志**：`System.out`／`printStackTrace`／`{}` 占位符 → 生产代码 **0 处违规**，
     测试里的 165 处 `System.out` **预期会被报**，需在报告里说明用途（§2.5 第 9 条）。
4. **对 `Blocker` 的处置口径**：要求清零；本项目实测**无 Blocker 级问题**
   （依据见 §五 的等价扫描）。

### 4.3 为什么**不**在 Maven 里接 Checkstyle / SpotBugs 门禁

1. **课程项目没有 CI**：接了门禁就必须有人执行。没有流水线时它只是一个"本地可选插件"，
   而"可选"等于"没人跑"。
2. **会制造**假安全感**：门禁不是为了让人放心，是为了让**没人能跳过**。
   一个"配置了但从不触发失败"的插件，比不配置更糟 —— 评审看到 build 绿了，
   会以为规范检查过了。
3. **误报会挤掉真问题**：SpotBugs 在本项目会大量报 `EI_EXPOSE_REP`（返回可变集合）、
   `SE_BAD_FIELD`（序列化字段）等与 Spring/MP 使用方式无关的项，噪声淹没真信号。
4. **单人提交、无代码评审流程**：门禁的价值来自"别人不能合入坏代码"，
   本项目是四人各写各的域、按天提交，没有合入评审环节，门禁没有作用点。
5. **替代方案已经在用**：`-Xlint` 全量编译告警（§五）+ `information_schema` 断言测试
   （唯一索引真的存在且真的拒绝重复）+ 真机 SQL 条数判据（`Preparing:` 计数）——
   **都是可复现、能进 git、不依赖 IDE 的证据**。这比"一张截图"更适合答辩。

### 5.2 替代证据一：`-Xlint` 全量编译告警（可复现的构建输出）

**落地方式**：`pom.xml` 的 `maven-compiler-plugin` 增加

```xml
<arg>-Xlint:all,-serial,-processing,-classfile</arg>
```

并**刻意不加 `-Werror`** —— 课程项目没有 CI 门禁，把告警变成编译失败只会让协作变脆。

**为什么这样能替代 IDE 截图**：任何人 clone 后 `mvn compile` 都会看到同一份告警清单，
不依赖 IDE、不需要截图、可进 git。这才是"可复现证据"。

**实测结论（删 `target/classes` 后全量重编）**：

| 告警 | 处数 | 处置 | 理由 |
|---|---|---|---|
| `rawtypes`（裸类型 `new Class[]{}`） | **2** | **✅ 已修** | 真问题。`ServletContainersInitConfig` 的 `getRootConfigClasses()` / `getServletConfigClasses()` 返回裸 `Class[]`，改成 `Class<?>[]`（**只加泛型，不改签名**） |
| `serial`（`Set`/`List` 接口字段未声明 `Serializable`） | 19 | ❌ 刻意不修 | 字段声明用接口（`Set`/`List`）是**正确的 API 设计**；实际实现 `HashSet`/`ArrayList` 都可序列化。改成具体类会掩盖注入点、加大改动面 |
| `processing`（"没有处理程序要使用以下任何批注"） | 若干 | ❌ 刻意关闭 | `-proc:full` + Lombok 组合下的提示，与代码质量无关 |
| `classfile`（依赖 jar 的 `kotlin.Metadata` 缺类文件） | 若干 | ❌ 刻意关闭 | 来自第三方 jar，不是本项目代码 |

**处置后的判据**：`rm -rf target/classes && mvn -o compile` → **`BUILD SUCCESS`，零源码告警**。
（⚠️ 踩坑记录：`-Xlint` 在**增量编译**下不报告警 —— 第一次只改文件重编，会以为"项目很干净"。
**必须删 `target/classes` 强制全量重编**，这条也写进了 `pom.xml` 的注释。）

### 5.3 替代证据二：机械扫描（对应阿里规约"改名 / 常量 / 日志"三类）

```bash
# 1) 日志与异常
grep -rn "printStackTrace" src/main/java                      # → 0
grep -rn "System\.out" src/main/java                           # → 0（test 里 165 处，见 §2.5#9）
grep -rnE "log\.(info|debug|warn|error)\([^)]*\+" src/main/java # → 0（全部 {} 占位符）

# 2) 常量
grep -c "static final" src/main/java/com/lab/cms/service/impl/ArticleServiceImpl.java  # → 14

# 3) 命名（拼音嫌疑；命中的都是英文词）
grep -rnoE "\b[a-z]+(zhe|de|le|ma|ne|ba)[A-Za-z]*\b" src/main/java --include=*.java      # → 无拼音

# 4) 事务内 HTTP 调用
grep -rn "HttpClient\|RestTemplate\|HttpURLConnection" src/main/java                     # → 0
```

**结论**：对应阿里规约的"改名 / 常量 / 日志"三类，**无阻断级问题**。
