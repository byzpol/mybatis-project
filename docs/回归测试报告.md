### 2.6 R6 · 事务回滚（确定性失败点）

用 **600 字审核意见**触发 `cms_article_audit_log.opinion VARCHAR(500)` 的 1406 ——
这条路径之所以是"确定性失败点"，是因为审核逻辑是**先改状态、后写流水**：

```
[PASS] ① 失败确实发生（HTTP 5xx）                 http=500
[PASS] ② 状态被回滚：仍为 1（待编辑初审）          实际=1
[PASS] ③ 流水条数不变：仍为 0（没留半条）          实际=0
[PASS] ④ 失败后文章仍可用：改传正常长度 → 200      实际=200 / 状态=2 / 流水=1
```

> ⚠️ 这个失败点能成立，恰恰依赖"**先改状态、后写流水**"这个顺序
> （手册写的是先写流水）。如果顺序反过来，状态还没改就已失败，就验不到回滚。
> 这条顺序当初是刻意的，S20 用它做回归判据，等于把设计意图变成了可执行断言。

### 2.10 R10 · 并发

**A 组 · 同一文章、两个有 `publish` 权限的账号并发发布（5 轮）**

```
第1轮：codes=[11010, 200] → 最终 status=5
第2轮：codes=[11010, 200] → 最终 status=5
第3轮：codes=[11002, 200] → 最终 status=5
第4轮：codes=[11010, 200] → 最终 status=5
第5轮：codes=[11010, 200] → 最终 status=5
```

- 5 轮里**每轮恰好一个成功**，**从不双写成功**；被拒的那个只会是 `11010`（乐观锁）或 `11002`（状态非法）。
- 机制：两个请求都读到 `APPROVED(3)` 时状态机都会放行 → 第二个卡乐观锁 `11010`；
  第二个请求在第一个提交**之后**才读到数据时，状态已是 `PUBLISHED(5)` → 被状态机直接拒 `11002`。
  **两种都是安全的**，所以断言只写"不会双写成功"，不锁死具体码。

**B 组 · 同一作者、两个会话并发 PUT 草稿（5 轮）**

- 每轮至少一个 200，**4/5 轮出现 11010**，未出现任何 5xx。
- **D-05 由此关闭**：此前记的是"11010 复现不了"，实测是**时序依赖**而非缺陷。

## 四、本步发现并修复的缺陷（D-10 ~ D-13）与新增观察（D-14）

### 4.1 D-10（严重）登录失败日志被业务事务一起回滚

**现象**：用错误密码登录，接口正确返回 13003，但 `sys_login_log` **一条失败记录都不增加**
（实测 `total 121 → 121`）。也就是说**库里看不到任何"有人在撞口令"的痕迹**。

**根因**：`AuthServiceImpl#login` 上标了 `@Transactional`，而它的失败路径是
"**先写日志、后抛异常**" —— 异常一出，整个事务回滚，**连那条失败日志一起回滚**。
日志写入天生应该独立于业务事务，而当时的写法没有为它单开事务。

**修法**（不改主干签名，只加方法）：

1. 新增 `service/LoginLogService` + `service/impl/LoginLogServiceImpl`，
   方法标 `@Transactional(propagation = REQUIRES_NEW, rollbackFor = Exception.class)`。
2. `AuthServiceImpl` 改为注入该 **Service 接口**调用它 ——
   ⚠️ **必须经外部 Bean 调用**：`@Transactional` 的同类自调用不走代理，写在本类里等于没加。
3. 该类**不接收密码参数**（从签名上杜绝把凭据写进日志）。

**复验**：`id=123 / chief / login_status=2 / 用户名或密码错误`；失败记录 1 → 2 条。
S20 回归里对应断言 `登录失败也写 sys_login_log（login_status=2 条数 +1）`呈 PASS。

> ⚠️ 顺带说明：修复前先犯了一个**判断错误** —— 我最初的断言写的是 `login_status=0 的条数 +1`。
> 实测发现口径本身是错的（见 D-11），这个错误反而帮忙定位了 D-10。
> 两层错误叠在一起，只有把"日志有没有写进去"和"写进去的值是什么"分开查才理得清。

### 4.2 D-11（一般）`sys_login_log.login_status` 三方口径不一致

| 来源 | 原口径 |
|---|---|
| 库表列注释 + 种子数据 | **1 = 成功 / 2 = 失败** |
| `AuthServiceImpl` 实际传值 | `0` / `1` |
| `SysLoginLog` 实体注释 | `0 失败` |

**修法**：统一到**库表口径 1/2**（库表是运行时真相，且种子数据已经是 1/2）。
新增的 `LoginLogService` 用常量 `STATUS_SUCCESS = 1` / `STATUS_FAIL = 2` 表达，
实体注释同步改正，并注明"**不与 `sys_oper_log.status` 同口径**"（后者是 1 成功 / 0 失败）。

### 4.3 D-12（严重）SPA `history` 模式没有 fallback，所有深链 404

**现象**：`/cms-mis/login` 直接访问或 F5 → **404**。同理 `/articles/list`、`/articles/detail/1` 全都 404。
只有先访问 `/cms-mis/` 再由前端路由跳转才正常 —— 也就是**用户一刷新就掉线**，
而且"发一条链接给同学"必然打不开。

**根因**：前端用 `createWebHistory`（`/cms-mis/articles/list` 这种真路径），
但后端**没有任何把未知非 API 路径 forward 到 `index.html` 的配置**，
Spring MVC 就直接按"没有这个 handler"处理 → S08 建的统一 JSON 404。

**修法**：`SpringMvcConfig` 新增 `addViewControllers`（只加方法，不动既有签名），
把前端的一级路由**逐条白名单** forward 到 `index.html`：
`/login`、`/403`、`/profile`、`/articles/**`、`/categories`、`/tags`、`/users`、`/roles`、`/logs/**`、`/reports`。

> ⚠️ 为什么**不用 `/**` 一把兜住**：那会把 S08 精心做的"统一 JSON 404"冲掉 ——
> 任何写错的接口路径都会返回 200 的 HTML，前端 JSON 解析失败报一堆看不懂的错。
> ⚠️ 为什么是 **forward 而不是 redirect**：redirect 会改地址栏、多一次往返，
> 且会丢掉原始路径（用户再刷新一次又回到 `/index.html`）。
> ⚠️ **维护约束**：前端**每加一个一级路由，必须同步在这里加一行**（已写进方法 Javadoc）。

**复验**（前端脚本第一段）：`/cms-mis/articles/list`、`/login` 直接访问均 200 且返回 `index.html`
（判据是响应体里含 `id="app"`）；`/api/v1/**` 仍是 401 JSON、未知接口仍是统一 JSON 404。

### 4.4 D-13（严重）`DELETE /api/v1/articles/{id}` 契约与手册都要求，代码一直没写

**现象**：前端列表页对"草稿/已驳回"下发了「删除」按钮（含二次确认弹窗与 API 封装），
但后端 `ArticleController` **没有 `DELETE` 端点** → 点了必然落到统一 JSON 404。
同时 `ARTICLE_DRAFT_ONLY(11013)` 这个错误码**全仓零引用**。

**为什么算"严重"而不是"轻微"**：按 §3.1 的口径，"**计划内的接口/能力缺失**"是严重。
依据有两条，都不是我推的：
- `docs/接口契约.md` 第 59 行从 S05 起就列着这个端点（`article:delete`）；
- 手册 F06 明确要求列表页对"草稿/已驳回"下发「删除」，且工具栏还要有"批量删除"。
- `docs/接口分类与鉴权表.md` 也写着"`article:delete` 是文章域 9 个权限码里唯一没被使用的"。

**为什么现在做**：S18 曾把本接口记为"**本轮不实现**"，理由是
"新增删除接口属于**行为变更**，必须有独立用例与回归"。S20 正是**带独立用例的回归步**，
所以在这里补齐并当轮回归，而不是继续挂着。这与 S19 修 D-09 是同一种处理方式。

**修法**：

- `ArticleController#deleteArticle`：`@DeleteMapping("/{id}")` + `@RequirePermission("article:delete")`
  + `@OperLog(type = DELETE)`；不加 `saveParams=false`（没有请求体，不存在撑爆日志表的风险）。
- `ArticleService#deleteArticle` / `ArticleServiceImpl#deleteArticle`：
  `requireArticle` → `checkOwnership`（**要归属**）→ `requireDeletable`（仅 `DRAFT`/`REJECTED`，
  否则 11013；已归档 11011）→ 逻辑删除。
  - ⚠️ **不用 MP 的 `removeById`**：它生成的 SQL 里 SET 子句只有 `deleted=1` 一列，
    `update_by / update_time` **不会被自动填充** → 事后看库表**看不出是谁删的**。
    改用显式列列的 `LambdaUpdateWrapper`（与 S13/S14 的"置空"写法同源），
    WHERE 里显式再带 `deleted = 0`，受影响行数不是 1 就报错（防"并发删两次都报成功"）。
  - ⚠️ **不级联删除**版本与流水（与 S18 的处置表一致），已在测试里固化为断言。
- 测试：`ArticleControllerTest` 新增 **9** 条（作者删自己的草稿 / 已驳回也可删 / 非作者 11003 /
  已发布 11013 / 已归档 11011 / 别人的已归档是 11003 而非 11011 / 未登录 401 / 不存在 11001 /
  不级联版本与流水）。
- 顺带把 `ApiPermissionCoverageTest` 里那条"只打印不强制"的用例**收紧成 `assertEquals`** ——
  9 个权限码现在**全部**对应到端点，"有码无接口"这个状态被彻底消除。

**复验**：单测 312 → **321**；真机回归 R1（第 16 个接口正向）+ R7（10 条逻辑删除断言）全绿。

### 4.5 D-14（轻微 · 观察项）归属过滤后，主编在别人的草稿行上操作列为空

**现象**（S20 前端脚本第四段实测）：主编看**别人的草稿**，操作列是 `[]` —— 一个按钮都没有。
作者本人看同一行是 `["编辑","提交初审","删除"]`。

**成因**：两个口径叠加出来的：① 归属过滤把 `edit/submit/remove`（都是 `ownerOnly`）全收起了；
② 而 `DRAFT` 状态的动作集里**本来就没有「查看」**（F06 按手册口径定的：
手册对草稿只写"编辑、提交初审、删除"）。于是对非作者而言，这一行没有任何可做的动作。

**评级与处置建议**（需组内定，本步不改）：

- 它比修复前**严格更好**：修复前这一行是三个点了必被 11003 拒的"死按钮"，
  现在是"没有按钮" —— 至少不给用户挖坑。
- 但"一个操作列全空"的观感仍然值得改。两个方向：
  **方向 A**（推荐）：给 `DRAFT`/`REJECTED` 补上「查看」（后端详情接口本来就对所有
  有 `article:view` 的角色开放，前端只是没给入口）—— 代价是要在 F06 的 40 格矩阵里
  同步改期望，并且与手册原文有出入，需要在报告里说明；
  **方向 B**：保持现状，接受"别人的草稿在列表页只显示数据、不提供入口"。
- 无论选哪个，都**不要**把 `edit/submit/remove` 的 `ownerOnly` 去掉 —— 那会回到死按钮。
