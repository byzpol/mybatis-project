### ★ 相对实验一新增的 6 个依赖（每个都有明确理由）

1. **`spring-aspects`** —— `@RequirePermission` 与 `@OperLog` 两个切面的织入基础。
   实验一没有 AOP 需求。
2. **`mybatis-spring`** —— 提供 `SqlSessionTemplate` 与 `MapperScannerConfigurer`。
   ⚠️ `mybatis-plus`（非 spring-boot-starter 版）**不会**传递引入它，
   纯 SSM 手写配置必须自声明，否则编译报"程序包 org.mybatis.spring 不存在"（本轮实测踩到）。
3. **`jackson-datatype-jsr310`** —— 不引则 `LocalDateTime` 序列化成 `[2026,10,8,17,25,42]` 数组。
   Spring Boot 里被自动配置掩盖，纯 SSM 必须手动注册。
4. **`jakarta.el` 3.0.4** —— hibernate-validator 6.x 运行时需要 EL 实现解析消息模板。
   缺失时抛 `HV000183: Unable to initialize 'javax.el.ExpressionFactory'`。
   这是**纯 SSM 环境（无 Spring Boot 自动带 EL）下最常见的校验坑**。
5. **`logback-classic` + `slf4j-api`** —— 替代实验一的 log4j 1.2.17。
   log4j 1.x 已停止维护；logback 是 SLF4J 原生实现，与 Spring 5.x 的日志体系天然打通。
6. **`spring-security-crypto`** —— 只取 BCrypt 的 `PasswordEncoder`。
   不引整个 Spring Security 框架（本项目的鉴权是自研注解 + Session）。

## 三、配置四件套的设计要点

### 3.1 `SpringConfig`（根容器）

| 注解 | 为什么必需 |
|---|---|
| `@ComponentScan` 排除 `@Controller` 与 `@EnableWebMvc` | 不排除则同一个 Controller 在父子容器各创建一份实例，子容器用自己那份，父容器那份成"死对象"但仍参与 AOP 代理创建 → 典型症状是 `@Transactional` "看起来没生效"或注入字段为 null |
| `@PropertySource("classpath:db.properties")` | 从类路径读凭据文件。**db.properties 不入库**，仓库里只有 `.example` |
| `@EnableTransactionManagement` | 打开声明式事务开关。⚠️ 它只是开关，还需要一个 `PlatformTransactionManager` Bean 才真正工作 |
| `@EnableAspectJAutoProxy` | ⚠️ **必需**：不写这行，`PermissionAspect` / `WebLogAspect` 就是"普通的、不会被织入的 Bean"，业务照常跑但切面从不执行 —— 静默失效 |

`proxyTargetClass` 保持默认 false（优先 JDK 动态代理）。本项目 Service 全部是"接口 + 实现类"，天然满足要求。

### 3.2 `SpringMvcConfig`（子容器）

```java
// ① 自定义 Jackson 转换器必须插到索引 0
converters.add(0, jacksonMessageConverter);
```
⚠️ 若 `converters.add(...)` 加在末尾，永远轮不到它 —— 默认列表里已经有
`MappingJackson2HttpMessageConverter`，遍历到它就命中并返回了。
症状：时间还是序列化成数组。

```java
// ② 自定义参数解析器也必须插到索引 0
resolvers.add(0, new CurrentUserArgumentResolver());
```
同样道理：通用解析器可能先于我们的解析器返回非 null，导致 `@CurrentUser` 拿到 null。

```java
// ③ 拦截器用"黑名单排除"而不是"白名单添加"
registry.addInterceptor(loginInterceptor)
        .addPathPatterns("/api/**")
        .excludePathPatterns("/api/v1/auth/login", "/api/v1/auth/captcha", "/error", "/favicon.ico");
```
**fail-safe 原则**：新加的接口默认**被拦截**，而不是默认放过。
反着写（只拦已知需要鉴权的路径）时，新接口一旦忘记加进名单，就是一个未受保护的公开接口。

### 3.3 `JdbcConfig`

```java
// ① 不显式调 dataSource.init()
```
若在 `@Bean` 方法里调 `init()`，一旦数据库未启动，Spring 容器启动就**直接失败**，
且报错栈很深（Bean 创建失败 → init 失败 → 连接拒绝）。懒初始化时容器能正常启动，
只有第一次访问数据库才报错，定位更直接。答辩演示时数据库可能后启动，这个选择很重要。

```java
// ② PlatformTransactionManager 必须显式声明
@Bean
public PlatformTransactionManager transactionManager(DataSource dataSource) {
    return new DataSourceTransactionManager(dataSource);
}
```
⚠️ 不写这个 Bean 的症状：`@Transactional` 完全不生效，但**不报错** —— 
`@EnableTransactionManagement` 找不到事务管理器时只是跳过代理创建，不抛异常。
又一个静默失效的坑。

参数注入用**方法参数形式**（`DataSource dataSource`）而不是字段 `@Autowired`，
明确表达"事务管理器依赖数据源"的构造关系。

### 3.4 `MybatisConfig` —— 本类有三个必踩的坑

```java
// 坑 1：必须用 MP 提供的工厂，不是 MyBatis 原生的
MybatisSqlSessionFactoryBean factoryBean = new MybatisSqlSessionFactoryBean();
```
若用 `org.mybatis.spring.SqlSessionFactoryBean`（原生），编译能过、启动正常，
但所有 BaseMapper 自带方法（`selectById` / `insert` / `updateById` / `selectPage`…）
运行时抛 `Invalid bound statement (not found)`。
原因是原生工厂不注册 MP 的注入器（`DefaultSqlInjector`），这些方法根本没被注入配置。

```java
// 坑 2：XML 路径必须与接口包路径一致
.getResources("classpath*:com/lab/cms/mapper/*.xml")
```
写成 `classpath*:mapper/*.xml` 会找不到（实验一实测确认的扫描路径）。

```java
// 坑 3：拦截器顺序 —— 分页必须最后加
interceptor.addInnerInterceptor(new BlockAttackInnerInterceptor());   // 1. 防全表更新
interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor()); // 2. 乐观锁
interceptor.addInnerInterceptor(pagination);                          // 3. 分页 ← 最后
```
MP 官方明确要求分页插件最后添加。原因：分页会改写 SQL（追加 LIMIT 并执行 count），
若它排在前面，改写后的 SQL 会跳过后续插件 —— 症状是"分页查出来总数不对"或"乐观锁从不生效"。

**MP 全局配置注意点**：
- `IdType.AUTO` 而非 `ASSIGN_ID`（雪花 ID 是 19 位 long，超出 JS Number 安全范围会丢精度）
- `setCacheEnabled(false)`（不用二级缓存，避免多实例场景数据不一致）
- `setMapUnderscoreToCamelCase(true)`（数据库全用下划线命名）

### 3.5 `ServletContainersInitConfig`（替代 web.xml）

```java
getRootConfigClasses()    → SpringConfig.class      // Service / Mapper / 事务
getServletConfigClasses() → SpringMvcConfig.class   // @Controller
getServletMappings()      → new String[]{"/"}       // REST 风格标准做法
getServletFilters()       → CharacterEncodingFilter（UTF-8, forceEncoding=true）
```
⚠️ 两个配置类放错位置（都放 `getRootConfigClasses`）会让双容器退化成单容器，
SpringMVC 的 HandlerMapping、拦截器、`@ControllerAdvice` 都不正确工作
—— 症状是"接口 404"或"拦截器不生效"。这是纯 Java 配置（无 web.xml）时最常见的错误。

`setForceEncoding(true)` 是关键：同时强制请求与响应编码，避免只设了 request 而 response 仍用平台默认编码。

### 3.6 `JacksonConfig` —— 必须"两步走"

```java
@Bean ObjectMapper objectMapper()                        // ① 自定义 ObjectMapper
@Bean MappingJackson2HttpMessageConverter converter()    // ② 基于它的转换器
```
⚠️ **只做第 ① 步是不够的**：`@EnableWebMvc` 注册的是**默认的** `MappingJackson2HttpMessageConverter`
（用默认 ObjectMapper）。SpringMVC 不会自动用你的 ObjectMapper 替换掉它
（除非有 Spring Boot 自动配置）。必须手动替换转换器本身，并在 `SpringMvcConfig` 里插到索引 0。

三项配置：
- 注册 `JavaTimeModule` + 三个 `DateTimeFormatter`（LocalDateTime/LocalDate/LocalTime）
- `setSerializationInclusion(NON_NULL)` —— 注意**不用 NON_EMPTY**：
  空集合要保留（前端 `forEach` 安全），字段缺失会导致 `list.map()` 报错
- `FAIL_ON_UNKNOWN_PROPERTIES = false` —— 前端多传字段不导致 400

### 3.7 `CorsConfig`

```java
.allowedOriginPatterns("http://localhost:[*]", "http://127.0.0.1:[*]")
.allowCredentials(true)
```
⚠️ `allowCredentials(true)` 与 `allowedOrigins("*")` **不能同时使用** ——
CORS 规范限制（`Access-Control-Allow-Origin` 不允许通配符携带 Cookie），
Spring 5.3 检测到会直接抛异常。必须用 `allowedOriginPatterns`。

`http://localhost:[*]` 覆盖 Vite 的 5173，也覆盖 5174/5175（端口被占用时 Vite 自动切换）。

**与 Vite proxy 的关系**：两道防线都要保留。proxy 用于本地开发（同源，无 Cookie 问题），
CORS 用于"前端独立部署后直连后端"（答辩时 `npm run build` 的静态包 + Tomcat）。
只做一种，到部署环节会返工。

## 四、主干 18 个类的职责速查

| 类 | 职责 | 关键设计点 |
|---|---|---|
| `Result<T>` | 统一响应体 | 私有构造 + 静态工厂；带 `timestamp`；`isSuccess()` 便于测试断言 |
| `PageResult<T>` | 统一分页出参 | 五个固定字段；构造器全量兜底；`of(IPage)` 转换 |
| `PageQuery` | 统一分页入参基类 | `normalize()` 修非法 page/size/sortOrder；**sortField 不做校验**（须各域白名单） |
| `ErrorCode` | 全局错误码 | 四段位 10xxx/11xxx/12xxx/13xxx/14xxx；message 必须是可直接展示的中文 |
| `BusinessException` | 业务异常 | 继承 RuntimeException；带 `code`；支持带 cause 转换 |
| `GlobalExceptionHandler` | 全局异常处理 | 11 个 `@ExceptionHandler`；业务异常用 WARN，兜底用 ERROR **且必须传异常对象** |
| `SessionConstant` | 全局常量 | final class + 私有构造；角色码常量；字段长度常量与 DB 同步 |
| `LoginUser` | 会话用户模型 | 只读视图的 getter；超管短路只在 `hasPermission` 一处实现 |
| `ArticleStatus` | 文章 10 态枚举 | `code/description/color`；`isFinal/isUnderAudit/isEverPublished/isEditable` |
| `ArticleAction` | 文章 10 动作枚举 | `isAuditAction()` 用于判断是否写审核流水 |
| `OperType` | 操作类型枚举 | 存枚举名（自解释）而非数字 |
| `ArticleStateMachine` | **文章状态机（核心）** | 14 条迁移集中登记；static 块末尾 `assert size==14` Fail Fast；终态单独判并抛专门错误码 |
| `BaseEntity` | 实体基类 | `@TableLogic(value="0", delval="1")` 显式；`deleted` 加 `@JsonIgnore` |
| `AuditMetaObjectHandler` | 审计字段填充 | 用 `strictXXXFill`；拿不到用户时**跳过填充**（null 表示系统操作，不填 0） |
| `RequirePermission` | 权限注解 | 支持 AND/OR；⚠️ 只解决垂直越权 |
| `OperLog` | 日志注解 | `saveParams` 对登录接口必须设 false（防凭据进日志） |
| `CurrentUser` | 用户注入注解 | 支持 `required=false`；另有 `getClientIp()` 静态方法 |
| `PermissionAspect` | 权限切面 | ⚠️ 只解决垂直越权；空权限数组时**拒绝**而非放行（fail-safe） |
| `WebLogAspect` | 日志切面 | `@Around` + `finally`；日志失败必须吞掉；业务异常必须 rethrow；TODO(S05) 写表 |
| `LoginInterceptor` | 登录拦截器 | ⚠️ 必须放行 OPTIONS（预检不带 Cookie） |

## 六·五、S05 阶段对主干的关键修正（⚠️ 必读，影响后续所有模块）

S05 联调的实测暴露出 4 个**静默失效**类缺陷，均已修复。
完整记录见 `docs/S05-联调实测记录.md`，此处只列与"骨架配置"直接相关的两条：

### 修正 1：`MybatisConfig` 必须显式设置 `MetaObjectHandler`

**原注释是错的**（已改正）。原文写"MP 的自动填充依赖 MetaObjectHandler 实现类
（加 @Component 被扫描到即可），此处无需额外开关" —— 这是 Spring Boot starter 的行为。
本项目纯 SSM 环境必须显式设置：

```java
@Bean
public SqlSessionFactory sqlSessionFactory(DataSource dataSource,
                                           MybatisPlusInterceptor interceptor,
                                           AuditMetaObjectHandler auditHandler) throws Exception {
    ...
    factoryBean.setGlobalConfig(globalConfig(auditHandler));
}

private GlobalConfig globalConfig(AuditMetaObjectHandler handler) {
    GlobalConfig gc = new GlobalConfig();
    ...
    gc.setMetaObjectHandler(handler);      // ← 修复点
    return gc;
}
```

未设置时的症状：所有 insert 抛 `Column 'create_time' cannot be null`。

### 修正 2：`SpringMvcConfig` 必须开启 AOP 并导入切面

双容器结构下，根容器的 `@EnableAspectJAutoProxy` **管不到**子容器里的 Controller。

```java
// SpringMvcConfig（子容器）
@EnableAspectJAutoProxy
@Import({WebLogAspect.class, PermissionAspect.class})
public class SpringMvcConfig implements WebMvcConfigurer { ... }
```

对应的，`SpringConfig` 排除 `@Aspect`，避免切面在两个容器各注册一份。

### 修正 3：`AuditMetaObjectHandler.updateFill` 改用 `setFieldValByName`

MP 3.5.5 下 `strictUpdateFill` 在 `updateById` 场景会被绕过（生成的 SET 子句已包含这些列）。
UPDATE 侧改用无条件覆盖；INSERT 侧保留 `strictInsertFill`（保留"显式指定 createTime"的能力）。

### 修正 4：`GlobalExceptionHandler` 让 HTTP 状态码跟随业务语义

新增 `writeStatus(HttpServletResponse, int)`，每个 handler 显式调用。
未登录 → 401、越权 → 403、参数错 → 400、系统异常 → 500；
业务码（10xxx~14xxx）不映射到 HTTP 状态码，回退为 200（理由见 `docs/S05-联调实测记录.md` 第四节）。
