## 二、Element Plus 从"全量引入"改成"按需引入"

F01 用的是官方最省事的方式：`app.use(ElementPlus)` + `import 'element-plus/dist/index.css'`。
F03 换成按需，**只改了一处配置，收益很直接**：

| 指标 | F01 全量 | F03 按需 | 变化 |
|---|---|---|---|
| JS（全部 chunk 合计） | 约 1020 KB | **426 KB**（436,580 B） | −58% |
| CSS（全部 chunk 合计） | 约 361 KB | **114 KB**（117,224 B） | −68% |

配置在 `vite.config.js`：`unplugin-auto-import` + `unplugin-vue-components`，两个都接 `ElementPlusResolver()`。
两个插件分工不同，**这点必须搞清楚，否则会踩坑**：

- `Components` 管**模板里写出来的标签**：`<el-button>`、`<el-menu>` → 自动 import 组件 + 该组件样式。
- `AutoImport` 管**函数式调用**：`ElMessage.success()`、`ElMessageBox.confirm()`、`ElLoading.service()`。

### 踩到的三个坑

**① 函数式调用的样式插件管不到，必须手工 import。**
`ElMessage` / `ElMessageBox` / `ElLoading` 是"用 JS 调出来的"，模板里根本没有对应标签，
`Components` 的解析器没有机会介入，所以样式不会被带进来 —— 表现为**弹窗/提示文字正常但完全没样式**（透明浮在页面上）。
解法是在使用处显式引样式（已在 `api/request.js` 与 `layout/components/Navbar.vue` 里写死并加注释）：

```js
import 'element-plus/es/components/message/style/css'
import 'element-plus/es/components/message-box/style/css'
```

**② 全量的 `app.use(ElementPlus, { locale: zhCn })` 用不了，中文语言包得换地方。**
按需模式下没有那次 `app.use`，语言包的挂载点就没了。改成在 `App.vue` 包一层：

```vue
<el-config-provider :locale="zhCn" :z-index="2000">
  <router-view />
</el-config-provider>
```

**③ `theme.css` 必须在 `App.vue` 之后 import。**
按需引入后 EP 的样式是被各组件"顺带"引进来的，顺序不再可控；而 `theme.css` 里有一批
`--el-color-primary` 之类的覆盖。**CSS 变量同优先级下后加载的赢**，放反了按钮和菜单会显示成
EP 默认的 `#409EFF`，主题整个白改。现已写进 `main.js` 注释（并在实测里加了断言防回归）。

> 详细的配置说明与"为什么不用全量"另见 `docs/ElementPlus按需引入说明.md`。

## 三、⚠️ 权限码存在两套口径，本步一律跟数据库（**需要定的事**）

这是本步最重要的一个发现，属于"不看库就会被坑"的那类。

| 来源 | 文章域权限码 |
|---|---|
| `sql/init.sql` 的 `sys_permission`（20 条，**库里实际有的**） | `article:view` / `article:update` / `article:manage` |
| `docs/接口契约.md` §1.3（评审文档里写的） | `article:list` / `article:edit` / `article:offline` / `article:archive` |

| 角色权限 | `role:manage` |

| 数据统计 | `report:view` |

这个不一致的来龙去脉已写进 `router/index.js` 的注释。**处理建议：以库表为准，
把 `接口契约.md` §1.3 改过来**（改文档比改库安全，库里已经有角色-权限关联数据）。
但这是定口径的事，需要组内确认后再落地 —— 本步只做到"代码与库一致"。

## 四、踩坑

### 4.1 【真 bug，最严重】`baseURL` 写死 `'/api/v1'`，部署到 war 后所有接口 404

**现象**：war 部署到 `/cms-mis` 后，登录页输入正确的账号口令、点登录 ——
**不报错、不提示、表单也没有校验错误、按钮 loading 也正常收了、没有任何遮罩残留**，
就是什么都不发生。这种"完全静默"的表现，第一反应一定是去查后端登录逻辑或密码加密。

**定位手段**：CDP 打开 `Network.enable` 抓真实请求，一眼看到铁证：

```
诊断(网络): ["→ POST http://localhost:8080/api/v1/auth/login",
            "← 404 http://localhost:8080/api/v1/auth/login"]
```

**URL 里少了 `/cms-mis`**。后端的 context path 是 `/cms-mis`，接口真身是
`http://localhost:8080/cms-mis/api/v1/auth/login`，而前端请求打到了 `/api/v1/...`，
Tomcat 里没有 `/api` 这个上下文 → 404。

**根因**：`request.js` 里写的是 `baseURL: '/api/v1'`。以 `/` 开头是**根路径绝对地址**，
浏览器会从域名根开始拼，`BASE_URL` 完全不参与。

**为什么 F02 没抓到**：F02 是在 **vite dev 环境**验的，`BASE_URL = '/'`，
拼出来恰好还是 `/api/v1` —— **dev 下永远是对的，构建部署后才错**。这类
"环境差异导致的静默失效"只有靠真机部署才抓得到，dev 里怎么点都是好的。

**修复**：

```js
baseURL: `${import.meta.env.BASE_URL}api/v1`
// dev  → BASE_URL '/'        → '/api/v1'
// 构建 → BASE_URL '/cms-mis/' → '/cms-mis/api/v1'
```

这条已写进 `request.js` 的 `baseURL` 注释，并明确标注"必须靠真机部署验证才能抓到"。

### 4.2 【真 bug】dev 期 Session Cookie 被丢弃，登录成功但下一个请求 401

**现象**：dev 下登录接口返回 200，响应里**确实带了** `Set-Cookie`，但紧接着的请求就是 401。
因为响应体是成功的 JSON，很容易把排查方向带到"后端 Session 配置错了"或"`withCredentials` 没开"。

**根因**：后端返回

```
Set-Cookie: JSESSIONID=xxx; Path=/cms-mis; HttpOnly
```

这个 `Path` 对生产完全正确（只在 `/cms-mis` 下发送，范围更小更安全）。
但 **dev 期浏览器看到的请求路径是 `/api/v1/*`**，浏览器是按这个路径去匹配 Cookie 的 `Path` 的：
`/cms-mis` 匹配不上 `/api/v1/...` → **Cookie 被直接丢弃、根本不存**。后面的请求自然没有会话。

**修复**：只在 dev 的 proxy 上把 Path 改写掉（生产不经过 proxy，零影响）：

```js
configure: (proxy) => {
  proxy.on('proxyRes', (proxyRes) => {
    const cookies = proxyRes.headers['set-cookie']
    if (!cookies) return
    proxyRes.headers['set-cookie'] = cookies.map((c) => c.replace(/Path=\/cms-mis/gi, 'Path=/'))
  })
}
```

实测修后：`set-cookie: JSESSIONID=...; Path=/; HttpOnly`，登录后能正常带会话。

> 顺带说明：`vite.config.js` 里 `/api` 的 `rewrite: p => '/cms-mis'+p` **是 F02 就有的**
> （F02 的代理 404 那个坑），本步只是给它补了 `configure` 钩子，不是同一个问题。

### 4.3 【真 bug】`request → store → auth → request` 循环依赖

F03 让 `store/user.js` 新增 `login/logout/fetchUserInfo`，要 import `api/modules/auth.js`；
`auth.js` import `api/request.js`；而 F02 的 `request.js` 顶层静态 import 了 `store/user.js` 和 `router`
→ 形成闭环：`request → store → auth → request`。

**修法**：把 `request.js` 里对 store / router 的引用改成**动态 import**，
依赖方向恢复成单向的 `store → api/modules → request`：

```js
// ⚠️ 刻意不在顶层 import @/store/user 与 @/router（打破循环依赖）
async function resolveAppLayer() {
  const [{ useUserStore }, { default: router }] = await Promise.all([
    import('@/store/user'),
    import('@/router')
  ])
  return { useUserStore, router }
}
```

**为什么用动态 import 而不是别的办法**：`request.js` 只在**响应拦截器出错时**才需要
store 和 router（清登录态、跳 `/login`），这是低频路径。动态 import 把这次解析推迟到真正需要时，
既打破了环，也不用为了避开环把上层职责下移。

**构建时的 `[INEFFECTIVE_DYNAMIC_IMPORT]` 警告是预期的**：`store/user.js` 同时被多处静态引用
（Navbar / Sidebar / router / login / placeholder），它本来就在同一个 chunk 里，
动态 import 挪不动它。这条警告只影响分包粒度，不影响正确性。

### 4.4 【视觉排查】折叠态图标没居中、侧边栏冒出横向滚动条

两个都是看截图发现的（不是断言跑出来的），修法记录如下：

**① 折叠后菜单图标挤在左边。**
`el-menu-item` / `el-sub-menu__title` 是 **flex 容器**，`text-align: center` 对它们无效，
必须显式写 `justify-content: center`：

```css
:deep(.el-menu--collapse .el-menu-item),
:deep(.el-menu--collapse .el-sub-menu__title) {
  padding: 0 !important;
  justify-content: center;
}
```

**② 侧边栏底部有一条横向滚动条。**
菜单项内边距 + 图标宽度让内容比 220px 略宽，`el-scrollbar` 就画了一条横向条。
修法是禁掉横向滚动并隐藏该 bar。

### 4.5 【排查教训】"元素存在"不等于"元素可见"

给上面两处加断言时踩了个坑，值得单独记一笔。
第一次写完断言，跑出来：

```
FAIL  折叠态菜单图标水平居中（中心 ≈ 32px）  [32,0,32,0,32,0]
FAIL  侧边栏内无横向溢出内容  overflowX=0 hbar=true
```

看起来像两个功能都没修好。但写了个最小诊断脚本把真实 DOM 打出来之后，真相是**断言写错了**：

```json
{ "cls": "el-icon", "centerX": 32, "display": "flex", "offsetW": 18 }          ← 真图标，居中
{ "cls": "el-icon el-sub-menu__icon-arrow", "centerX": 0, "display": "none", "offsetW": 0 }
{ "cls": "el-scrollbar__bar is-horizontal", "display": "none", "offsetW": 0, "offsetH": 0 }
```

- 图标其实**是居中的**（`centerX=32`，正是 64px 侧栏的正中）。那个 `0` 来自
  **子菜单的箭头图标** `.el-sub-menu__icon-arrow` —— 折叠态下 EP 把它设成 `display:none`，
  而 `getBoundingClientRect()` 对隐藏元素返回**全 0 矩形**，中心自然算成 0。断言把这个隐藏箭头也算进去了。
- 横向 bar **确实已经隐藏**（`display:none`、`offsetW=0`）。问题是 Element Plus 的 Scrollbar
  的**两个 bar 元素永远渲染在 DOM 里**，靠 `v-show`/`display` 控制显隐 ——
  所以 `!!document.querySelector('.el-scrollbar__bar.is-horizontal')` 恒为真，这个判据本身就是错的。

**修正**：判"可见"必须看 computed style，不能看元素是否存在；取图标要先滤掉零尺寸元素。

```js
const icons = [...document.querySelectorAll('.sidebar .el-sub-menu__title > .el-icon:not(.el-sub-menu__icon-arrow)')]
  .filter((e) => e.getBoundingClientRect().width > 0)
const anyHBar = [...document.querySelectorAll('.sidebar .el-scrollbar__bar.is-horizontal')]
  .some((e) => getComputedStyle(e).display !== 'none')
```

改完重跑：`PASS 折叠态菜单图标水平居中 [32,32,32]` / `PASS 侧边栏内无横向溢出内容 overflowX=0 hbar=false`。

**教训**：断言失败时先别改代码，先把真实 DOM 打出来对一遍 ——
"我以为的判据"本身可能就是错的。这和 F02 那次 `?e2e=1` 被 `router.replace` 覆盖掉是同一类问题：
**看不到效果时，先怀疑条件不成立，而不是反复读代码。**

### 4.6 其它两处小坑

- **`remember` 只存用户名**：登录页"记住我"用的是 `localStorage`（key `cms-mis:login:username`），
  **不存口令**。存口令即便加密也是明文级别的风险，课程项目没必要。
- **登录页 catch 块不弹提示**：失败提示已由 `request.js` 的响应拦截器统一弹过一次，
  页面里再弹一次就会变成两条一模一样的错误提示。
- **`logout` / `getCurrentUser` 默认 `silent`**：登出时会话可能已经过期、`me` 的语义就是"探活"
  （未登录返回 401 是**预期结果**）。不静默的话，用户一进站就会看到"登录已过期"的红色提示。

## 五、主题变量体系：两套变量并维护

`theme.css` 同时维护两套变量，**只改一套会出问题**：

| 变量族 | 用途 |
|---|---|
| `--app-*` | 本项目自己的语义变量（文字三级、底/卡/边框、圆角、阴影、侧栏配色、布局尺寸） |
| `--el-color-*` | Element Plus 的变量，覆盖它才能让 EP 组件跟着变 |

主色定为 `#2f6fed`（沉稳蓝），**刻意不用 EP 默认的 `#409EFF`** —— 那个颜色"官方 demo"感最强，
一眼就能看出是没调过的脚手架。

**⚠️ 只改 `--el-color-primary` 是不够的**：EP 的按钮 hover、`primary` 的浅色背景（`light-9`）等
都用派生色变量，不改它们，鼠标一悬停颜色就变回默认蓝。派生色按 EP 的规则
（与白色按 `N/10` 线性混合）算出来，**写了个 Python 脚本算，没有手算**：

```css
--el-color-primary: #2f6fed;
--el-color-primary-light-3: #6d9af2;   /* hover 用 */
--el-color-primary-light-5: #97b7f6;
--el-color-primary-light-7: #c1d4fa;
--el-color-primary-light-8: #d5e2fb;
--el-color-primary-light-9: #eaf1fd;   /* 浅色底用 */
--el-color-primary-dark-2: #2659be;
```

success / warning / danger / info 同法处理。这条已进断言：

```
PASS  主题已覆盖 EP 主色（--el-color-primary=#2f6fed）  #2f6fed
PASS  EP 派生色同时被覆盖（light-3=#6d9af2，防 hover 变回默认蓝）  #6d9af2
```

另外 `theme.css` 里还放了几个通用业务类（`.app-card` / `.page-header` / `.filter-bar` / `.table-toolbar`），
F04~F06 的列表页、详情页直接复用，避免每个页面各写一套留白。

## 六、布局骨架与响应式

### 6.1 侧边栏菜单从路由表生成，不手写数组

菜单项**不是**在 `Sidebar.vue` 里硬编码的数组，而是遍历 `router.options.routes` 里 `/` 的 `children`：

```js
const visible = children.filter(
  (c) => c.meta && c.meta.title && !c.meta.hidden && userStore.hasPermission(c.meta.permission)
)
// 再按 meta.group 归组，保持路由表里的声明顺序
```

路由表的 `meta` 约定（已在 `router/index.js` 里写明）：

| 字段 | 含义 |
|---|---|
| `title` | 菜单名 + 浏览器标题 + 面包屑末项 |
| `group` | 归到哪个菜单分组；**不写就不进菜单**（如 `/profile`） |
| `icon` | 图标名（字符串），由 `Sidebar.vue` 的 `ICONS` 映射表转成组件 |
| `permission` | 需要的权限码；**不写 = 只需登录** |
| `hidden` | 为真则不进菜单，但仍可访问（如 `/profile`） |
| `public` | 免登录（仅 `/login`） |

**好处**：新增一个模块只需在路由表加一条，菜单、面包屑、浏览器标题、权限拦截四处同时生效，
不会出现"页面能访问但菜单忘了加"或"菜单有但面包屑是空的"。

### 6.2 折叠状态与响应式的归属

折叠状态由 `AppLayout.vue` 持有（`userCollapsed` + `narrow` + `collapsed` 计算属性），
prop 下发给 Sidebar，`@toggle` 上报。

**响应式的关键是"只在跨断点的那一瞬间动一次"**：

```js
let wasNarrow = false
function handleResize() {
  const isNarrow = window.innerWidth < 992
  narrow.value = isNarrow
  if (isNarrow && !wasNarrow) userCollapsed.value = true        // 刚变窄 → 自动折上
  else if (!isNarrow && wasNarrow) userCollapsed.value = false  // 刚变宽 → 自动展开
  wasNarrow = isNarrow
}
```

**为什么不能直接写 `collapsed = isNarrow`**：那样用户手动展开后，只要窗口有一点不跨越断点的
尺寸变化（比如拖 1px），就会被强行折回去，手感很差。用 `wasNarrow` 记"上一次是不是窄屏"，
只在真正跨断点时自动动作，其余时间尊重用户的点击。`onBeforeUnmount` 里 `removeEventListener`。

实测覆盖：

```
PASS  900px 宽侧边栏自动折叠到 64px          64
PASS  拖回 1440px 侧边栏自动展开回 220px     220
PASS  点顶栏按钮可手动折叠到 64px            64
PASS  再点一次展开回 220px                   220
```

### 6.3 面包屑的两种项要分清

`首页` 是真链接（点了回文章列表），`文章管理`（分组名）和当前页是纯文字。
样式上用 `:not(.is-link)` 精确区分，**不能用 `:not(:last-child)`** ——
那会把"首页"这个真链接一起干掉。
